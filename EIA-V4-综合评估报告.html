1 执行摘要

总体结论：EIA V4 是一个工程化程度超出典型面试作品水准的 Multi-Agent AI 经营分析平台。 在 产品决策逻辑链（13 条关键决策含否决 AI 建议的思考过程）、安全设计（RLS 行级安全 + SQL 注入防护 + 四层安全体系）、 文档沉淀（27 份文档覆盖全链路）三个维度表现突出。 但存在若干可被面试官精准追问的薄弱点：llm.py 文档与实现矛盾、AGENTS.md 关键数字过时、前端技术栈标注不一致。 综合评分 7.2/10（面试作品基准线 5.5/10，优秀个人项目 8.0/10，企业级产品 9.0/10）。

六维能力雷达图
Top 3 亮点
  1. 13 条关键决策记录 — 每条含"AI 建议 vs 我为什么否决"的思考过程，是面试中最具说服力的叙事素材。特别是 Reflection 重试 1 次（否决 3 次）、DeepSeek 选型（否决 GPT-4o）、V1→V2 推倒重建（否决渐进改进）三条。
  2. RLS 行级安全设计 — sql_runner.py 的括号深度追踪算法、空权限 WHERE 1=0 防泄露、单引号转义 + 列名白名单，展示了对安全问题的深刻理解。
  3. 155 条测试 + 分层策略 — 无依赖 SQLite / @db 真实 PG / @e2e 真实 LLM / 离线评估四层体系，测试环境优雅降级（PG 不可用自动 skip），工程化程度突出。
Top 3 风险
  1. llm.py 文档与实现矛盾 — docstring 称用 ContextVar 无需加锁，实际用 threading.Lock() + 全局变量。面试官会认为"如果是自己写的不会出现这种不一致"，这是最大的原创性质疑风险点。
  2. AGENTS.md 关键数字过时 — 称"17 ORM 模型"实际 16 个，"8 版迁移"实际 10 个。面试官翻 GitHub 第一眼就看到的不一致。
  3. 前端技术栈标注"REACT 18" — index.html footer 标明 React 但实际是原生 JS。面试官会质疑"你到底知不知道你的项目用了什么技术"。

决策 #2（DeepSeek vs GPT-4o）：声称"成本 1/50"但需确认是输入还是输出 token 价格对比。DeepSeek 价格 ¥1/Mtok 输入 vs GPT-4o ¥30/Mtok 输入，确实约 1/30—1/50。但面试官可能追问："中文术语更准"有量化证据吗？建议准备 1-2 个具体案例。

决策 #3（Reflection 重试 1 次）："修复率 60%"和"一次通过率 85%→95%"是估算还是实测？如果面试官追问测量方法，建议坦诚说明是在开发过程中通过观察 20-30 次运行结果得出的经验值。

决策 #11（V4 前端技术）：决策记录称选了 React 18 + TS + Ant Design 5 + Vite，但实际生产前端是 原生 HTML/CSS/JS（app/api/static/app.js 1453 行）。这个不一致面试官翻源码就能发现，是最容易被攻击的点。

2.2 AI 能力边界定义

机制评价面试中的风险
Reflection 质检 4 维度（一致性/逻辑/可操作/完整）设计合理，覆盖了 AI 输出常见的幻觉和逻辑断裂问题。1 次重试是一次性投入 3000-5000 token 换取 60% 修复率，性价比合理。 面试官可能问"4 维度怎么选出来的？为什么不是 6 个或 2 个？"——建议回答：从实际 BadCase 中归纳，而非理论推导。
双模式输出 查询型→表格、分析型→报告，基于 question 中是否含具体数据指标（排名/金额/数量）判断。响应缩短 40% 是真实的产品改进。 低风险。面试官通常认可这种"不为了 AI 而 AI"的设计思路。
数据诚实 Prompt 明确要求 Agent 必须 run_sql 查真实数据，禁止编造。sql_runner 是到达数据库的唯一路径，从架构上杜绝了幻觉数据进入报告。 低风险。这是加分项，展示了"AI 产品经理知道 AI 会犯错"的专业素养。
AI Kill Switch 9 个 Feature Flag + 默认关闭策略 + 一键回退。灰度开关设计成熟。 低风险。面试官可能问"如果 AI 全部不可用，系统还能做什么？"——回答：经营看板（纯 SQL 查询）和缓存结果仍可正常使用。

2.3 用户场景覆盖度

5 个领域 Agent（销售/CRM/财务/库存/供应链）覆盖了连锁零售的核心经营链路：收入端（销售）、客户端（CRM）、利润端（财务）、货品端（库存）、供应端（供应链）。加上 Supervisor 路由和 Aggregator 聚合，形成了完整的"问→查→诊→报"闭环。

102 条评估集（50 lookup + 38 analysis + 14 edge）的问题分布较为合理。lookup 型（"昨天销售额多少"）占比最高，符合零售经营者的实际提问习惯。14 条 edge case（如"上个月没有销售的品类"）体现了对边界场景的思考。

经营看板作为首页：解决了"冷启动焦虑"——用户不需要知道该问什么，打开就能看到关键指标。这是典型的 B 端产品设计思维。

多轮对话/FOLLOWUP：ContextManager 注入历史上下文，会话所有权验证（防跨用户读取），FOLLOWUP 提供追问建议。但 session 级别的上下文管理策略（保留最近几轮？只保留关键实体？）在文档中不够明确。
