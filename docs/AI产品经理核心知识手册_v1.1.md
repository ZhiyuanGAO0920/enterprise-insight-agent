## 第一章：大语言模型（LLM）基础原理

### 1.1 什么是大语言模型？

**定义**：大语言模型（Large Language Model, LLM）是一种基于深度学习的自然语言处理模型，通过在海量文本数据上训练，学习语言的统计规律，从而能够理解和生成人类语言。

**核心特征**：

| 特征 | 说明 | 对PM的启示 |
| --------- | ------------------------ | -------------------- |
| **概率预测** | 模型本质上是"预测下一个词"的概率机器 | 输出不是确定的，每次可能不同 |
| **上下文学习** | 不需要重新训练，通过Prompt就能学习新任务 | 设计好的Prompt = 赋予模型新能力 |
| **涌现能力** | 模型大到一定程度会突然获得新能力（如推理、代码） | 选择模型时要考虑参数量级 |
| **幻觉倾向** | 会生成看似合理但实际错误的内容 | 必须设计校验机制 |

**PM必须理解的一个核心概念**：

> LLM不是"理解"了语言，而是通过学习海量文本中的**统计模式**，学会了如何**合理地组合词语**。它没有一个"世界模型"来验证事实，只是根据概率生成最"像人话"的回复。

这就是为什么LLM会：

- 编造不存在的事实（幻觉）
- 对最新事件一无所知（知识截止）
- 在数学计算上出错（不真正"计算"，只是"猜测"答案的样子）

---

### 1.2 Transformer架构（简明版）

Transformer是几乎所有现代LLM的基础架构（GPT、Claude、DeepSeek等都基于此）。作为PM，你不需要理解数学公式，但需要理解其核心机制。

#### 1.2.1 核心创新：注意力机制（Attention）

**类比理解**：

想象你在读一句话："小明把苹果给了小红，因为她饿了。"

人脑会自动建立关联：

- "她" → 指代"小红"（不是小明）
- "饿了" → 解释"为什么给苹果"

**注意力机制就是让模型也能做这种"关联"**：

- 模型在处理每个词时，会"看"一下句子中其他所有词
- 计算每个词与当前词的相关性（注意力权重）
- 相关性高的词对当前词的理解贡献更大

**对PM的启示**：

- **上下文长度很重要**：模型能"看"到的上下文越长，关联能力越强
- **长文本处理有挑战**：如果Prompt太长，注意力会"分散"，关键信息可能被忽略
- **位置信息**：模型通过位置编码知道词的顺序，所以Prompt中信息的排列顺序会影响输出

#### 1.2.2 Transformer的两部分

```
输入文本 → [编码器] → 理解语义 → [解码器] → 生成输出
```

| 组件 | 作用 | 代表模型 |
| ---------------- | ------ | ---------- |
| **编码器（Encoder）** | 理解输入文本 | BERT（双向理解） |
| **解码器（Decoder）** | 生成输出文本 | GPT（单向生成） |
| **编码器-解码器** | 理解+生成 | T5、BART |

**PM关注点**：

- GPT系列是"自回归"模型：生成一个词后，把这个词加入上下文，继续生成下一个词
- 这解释了为什么**生成是逐词的**，长文本生成会比较慢
- 也解释了为什么**前面的词会影响后面的词**（反之则不会）

### 1.3 Tokenization：模型如何"阅读"

#### 1.3.1 什么是Token？

模型不直接理解"字"或"词"，而是理解**Token**。

**Token是文本的最小处理单位**，可能是：

- 一个英文单词（如 "hello"）
- 一个中文汉字（如 "你"）
- 一个词的一部分（如 "unbelievable" → "un" + "believ" + "able"）
- 一个标点符号（如 "。"）

**常见换算（近似）**：

| 语言    | 1 Token ≈  |
| ----- | ---------- |
| 英文    | 0.75 个单词   |
| 中文    | 0.5 个汉字    |
| 代码    | 0.5 行代码    |

**示例**：

```
"我喜欢人工智能" → 约 6-8 个Token
"I love artificial intelligence" → 约 5 个Token
```

#### 1.3.2 为什么Token很重要？

**对PM的影响**：

| 影响维度      | 具体说明                               |
| --------- | ---------------------------------- |
| **成本**    | API按Token计费，中文比英文贵（同样信息量需要更多Token） |
| **上下文窗口** | 模型的"记忆"限制用Token计量（如4K、128K）        |
| **输入长度**  | Prompt越长，消耗的Token越多，留给回答的Token越少   |
| **语言选择**  | 英文Prompt通常更节省Token，效果也可能更好         |

**实操建议**：

- 写Prompt时尽量简洁，删除冗余信息
- 中文场景下，可以考虑用更精炼的表达
- 监控Token使用量，建立成本意识

### 1.4 上下文窗口（Context Window）

#### 1.4.1 什么是上下文窗口？

**定义**：模型在一次推理中能"看到"的最大Token数量。

**类比**：就像人的工作记忆容量，模型一次只能处理这么多信息。

**主流模型的上下文窗口（2026年8月数据）**：

| 模型 | 上下文窗口 | 约等于 |
| ------------------------ | ---------- | --------- |
| Claude Opus 5 / Sonnet 5 | 1M | ~1500页PDF |
| Claude Haiku 4.5 | 200K | ~300页PDF |
| Gemini 3 Pro | 2M | ~3000页PDF |
| DeepSeek V4 Flash | 1M | ~1500页PDF |
| GPT-5.6 系列 | ~1M | ~1500页PDF |
| Qwen 3.8-Max | ~1M | ~1500页PDF |

> 具体数值随版本迭代变化,以各厂商官方文档为准。

#### 1.4.2 长上下文的挑战

**不是所有长上下文都好用**：

- **"Lost in the Middle"问题**：信息放在Prompt中间时，模型容易"遗忘"
- **注意力稀释**：上下文越长，每个词获得的注意力越少
- **推理成本增加**：处理长上下文需要更多的计算资源

**PM设计建议**：

```
✅ 把最重要的指令放在Prompt的开头或结尾
✅ 避免把关键信息埋在长文档中间
✅ 对于超长文档，考虑分块处理（Chunking）
✅ 关键信息重复提及（开头说一次，结尾再提醒一次）
```

### 1.6 LLM的能力边界（PM必知）

#### 1.6.1 LLM擅长什么？

| 能力 | 示例场景 | 表现 |
| ----------- | ----------- | ------ |
| **文本理解与总结** | 合同审核、会议纪要生成 | ⭐⭐⭐⭐⭐ |
| **创意写作** | 营销文案、邮件撰写 | ⭐⭐⭐⭐⭐ |
| **代码理解与生成** | 代码审查、自动化脚本 | ⭐⭐⭐⭐⭐ |
| **多语言翻译** | 跨语言文档处理 | ⭐⭐⭐⭐⭐ |
| **结构化信息抽取** | 从非结构化文本提取字段 | ⭐⭐⭐⭐ |
| **简单推理** | 逻辑判断、分类 | ⭐⭐⭐⭐ |

#### 1.6.2 LLM不擅长什么？

| 能力 | 为什么不行 | 替代方案 |
| ------------- | ------------- | ---------------------- |
| **精确数学计算** | 本质是概率预测，不是计算器 | 调用计算器API |
| **实时信息获取** | 知识有截止日期 | RAG检索/搜索引擎 |
| **确定性事实验证** | 会编造信息（幻觉） | 接入知识库/数据库 |
| **长程复杂推理** | 推理链太长会出错 | 分步推理（Chain-of-Thought） |
| **理解物理世界** | 没有感官输入 | 多模态模型 |
| **处理私密/敏感数据** | 数据可能用于训练 | 本地部署/私有云 |

#### 1.6.3 幻觉（Hallucination）详解

**什么是幻觉**：
模型生成看似合理但实际上错误或不存在的回答。

**幻觉的类型**：

| 类型 | 示例 | 危险程度 |
| --------- | -------------------------------- | --------- |
| **事实性幻觉** | "张三的出生日期是1990年1月1日"（实际上不是） | 🔴 高 |
| **引用幻觉** | "根据2024年发表在Nature上的研究..."（论文不存在） | 🔴 高 |
| **细节幻觉** | "这个功能在v2.3版本中加入"（实际上没有） | 🟡 中 |
| **过度推断** | 从"用户点击了A"推断出"用户喜欢A" | 🟡 中 |

**B端PM特别注意**：

- 企业场景对准确性要求极高，一个错误的数据可能导致业务损失
- 必须设计**幻觉检测机制**和**人工审核流程**
- 关键信息必须**可追溯、可验证**

## 第二章：RAG系统详解

### 2.1 为什么需要RAG？

#### 2.1.1 LLM的知识局限性

**问题1：知识截止**

- 模型训练后就不再学习新知识
- 模型的知识截止到训练数据的日期（例如训练数据止于2025年的模型，无法回答2026年发生的新事件）
- 无法回答"昨天发生了什么"

**问题2：企业私有知识**

- 模型没有见过企业的内部文档、规章制度、业务数据
- "公司的请假流程是什么？"→ 模型不知道

**问题3：幻觉风险**

- 对于不确定的问题，模型会"编造"看起来合理的答案
- 在企业场景下，这是不可接受的

#### 2.1.2 RAG的解决思路

**核心思想**：不要让模型"死记硬背"，而是给它配一个"外部大脑"（知识库），回答时先查资料再说话。

```
用户提问 → 在知识库中检索相关内容 → 把检索结果+问题一起给模型 → 模型基于检索结果回答
```

**类比**：就像开卷考试，允许学生查资料，而不是要求背诵整本书。

### 2.2 RAG系统架构

#### 2.2.1 整体流程

```
┌─────────────────────────────────────────────────────────────┐
│                        RAG 系统架构                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  离线阶段（Indexing）                                        │
│  ┌──────────┐    ┌──────────┐    ┌──────────────┐        │
│  │ 原始文档  │ → │ 文本分块  │ → │ Embedding编码 │ → 存入向量数据库 │
│  │(PDF/Word)│    │(Chunking)│    │(向量化)       │    │(Vector DB)   │
│  └──────────┘    └──────────┘    └──────────────┘        │
│                                                             │
│  在线阶段（Querying）                                        │
│  ┌──────────┐    ┌──────────┐    ┌──────────────┐        │
│  │ 用户提问  │ → │ 问题向量化 │ → │ 相似度检索    │        │
│  │(Query)   │    │(Embedding)│    │(Top-K召回)   │        │
│  └──────────┘    └──────────┘    └──────────────┘        │
│                                         ↓                   │
│                              ┌──────────────┐              │
│                              │ 构建Prompt    │              │
│                              │(指令+上下文+问题)│            │
│                              └──────────────┘              │
│                                         ↓                   │
│                              ┌──────────────┐              │
│                              │ LLM生成回答   │              │
│                              └──────────────┘              │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

#### 2.2.2 关键组件

| 组件 | 作用 | 代表技术/产品 |
| --------------- | --------- | ------------------------------- |
| **文档加载器** | 读取各种格式的文档 | LangChain Loader、Unstructured |
| **文本分割器** | 把长文档切成小块 | RecursiveCharacterTextSplitter |
| **Embedding模型** | 把文本变成向量 | OpenAI text-embedding-3、BGE、M3E |
| **向量数据库** | 存储和检索向量 | Pinecone、Milvus、Chroma、Qdrant |
| **重排序器** | 对检索结果精排 | Cohere Rerank、BGE Reranker |
| **LLM** | 生成最终回答 | DeepSeek V4、Claude Sonnet 5、GPT-5.6 |

### 2.3 Embedding与向量化

#### 2.3.1 什么是Embedding？

**定义**：Embedding是一种将文本（或图像、音频）转换为**高维向量**（一串数字）的技术。

**核心特性**：语义相似的文本，在向量空间中的距离也相近。

**类比理解**：

想象把所有词语都放在一个"语义地图"上：

- "国王"和"女王"离得很近
- "苹果"（水果）和"香蕉"离得很近
- "苹果"（公司）和"微软"离得很近
- "国王"和"香蕉"离得很远

**向量的维度**：

- 常见维度：768维、1024维、1536维
- 维度越高，表达能力越强，但存储和计算成本也越高

#### 2.3.2 Embedding模型选型

| 模型 | 维度 | 语言 | 特点 | 适用场景 |
| -------------------------- | ------ | ------ | ------------- | --------- |
| **text-embedding-3-small** | 1536 | 多语言 | OpenAI出品，性价比高 | 通用场景 |
| **text-embedding-3-large** | 3072 | 多语言 | 性能更强，价格更高 | 高精度场景 |
| **BGE-M3** | 1024 | 多语言 | 开源，支持100+语言 | 私有化部署 |
| **M3E** | 768 | 中文优化 | 中文Embedding首选 | 中文知识库 |
| **GTE** | 768 | 多语言 | 阿里出品，中文好 | 中文企业场景 |

**选型建议**：

- 有预算且不要求私有化：OpenAI text-embedding-3
- 需要私有化/数据安全：BGE-M3 或 GTE
- 纯中文场景：M3E 或 GTE

#### 2.3.3 相似度计算

**如何比较两个文本的相似度？**

计算两个向量的**余弦相似度**（Cosine Similarity）：

```
相似度 = (向量A · 向量B) / (|向量A| × |向量B|)
```

**结果范围**：-1 到 1

- 1：完全相同
- 0：完全不相关
- -1：完全相反

**实际应用**：

- 设定阈值（如0.7），只返回相似度高于阈值的文档
- Top-K检索：返回相似度最高的K个文档

### 2.4 Chunking（文本分块）策略

#### 2.4.1 为什么需要分块？

**原因**：

- 文档通常很长（几十页PDF），超过模型的上下文限制
- Embedding模型有输入长度限制（如512 tokens）
- 细粒度的块能提高检索精度

#### 2.4.2 常见分块策略

| 策略 | 方法 | 优点 | 缺点 | 适用场景 |
| ---------- | -------------- | ------ | ------ | --------- |
| **固定大小** | 每N个字符/Token一块 | 简单、均匀 | 可能切断句子 | 通用场景 |
| **递归分块** | 先按段落分，太长的再按句子分 | 保持语义完整 | 实现稍复杂 | 推荐默认使用 |
| **语义分块** | 用模型判断语义边界 | 语义最完整 | 计算成本高 | 高精度场景 |
| **文档结构分块** | 按标题/章节分 | 保持文档结构 | 依赖文档格式 | 结构化文档 |

#### 2.4.3 Chunk大小的选择

**Chunk Size的选择是RAG的核心调优参数之一**：

| Chunk Size | 优点 | 缺点 | 适用场景 |
| ---------------------- | -------- | ------- | --------- |
| **小（128-256 tokens）** | 检索精度高 | 可能丢失上下文 | 事实性问答 |
| **中（512-1024 tokens）** | 平衡精度和上下文 | 无明显缺点 | 推荐默认使用 |
| **大（2048+ tokens）** | 保留完整上下文 | 检索精度下降 | 需要完整理解的场景 |

**Overlap（重叠）**：

- 相邻块之间保留一定重叠（如20%）
- 避免关键信息被切分在边界处

**PM决策要点**：

- Chunk大小会显著影响RAG效果，需要在项目中实验调优
- 建议准备几组不同参数的测试数据，对比效果后选择

### 2.5 检索策略

#### 2.5.1 基础检索：相似度搜索

**流程**：

1. 用户提问 → 用Embedding模型编码为向量
2. 在向量数据库中查找最相似的Top-K个Chunk
3. 返回这些Chunk作为上下文

**问题**：

- 只考虑语义相似度，可能遗漏关键词匹配的内容
- 对于专有名词、产品名等，Embedding可能不够精确

#### 2.5.2 混合检索（Hybrid Search）

**思路**：结合语义搜索和关键词搜索

```
最终得分 = α × 语义相似度 + (1-α) × 关键词匹配度
```

**实现方式**：

- 同时维护向量索引和倒排索引（如Elasticsearch）
- 或者使用支持混合检索的向量数据库（如Pinecone、Milvus）

**适用场景**：

- 企业知识库（同时有概念性内容和精确的产品名/代码）
- 客服场景（用户可能用不同方式描述同一个问题）

#### 2.5.3 重排序（Reranking）

**问题**：向量检索的Top-K结果不一定是最相关的

**解决方案**：用更精确的模型对初步检索结果重新排序

```
用户提问 → 向量检索（召回100个候选）→ 重排序模型（精选Top-5）→ 给LLM
```

**常用重排序模型**：

- Cohere Rerank
- BGE Reranker
- 自研重排序模型

**PM关注点**：

- 重排序能显著提升RAG效果，但会增加延迟和成本
- 需要在效果、速度、成本之间权衡

#### 2.5.4 查询重写（Query Rewriting）

**问题**：用户的提问方式与文档中的表述方式不同

**示例**：

- 用户问："怎么请假？"
- 文档写："员工休假申请流程"

**解决方案**：

1. **Query Expansion**：把问题扩展成多个相关表达
2. **Hypothetical Document Embedding（HyDE）**：让模型先猜一个理想答案，再用这个答案去检索
3. **子问题分解**：把复杂问题拆成多个子问题分别检索

### 2.6 RAG效果评估

#### 2.6.1 评估维度

| 维度 | 说明 | 评估方法 |
| --------- | ------------- | ------------ |
| **检索准确性** | 检索到的文档是否包含答案？ | Recall@K、MRR |
| **回答准确性** | LLM的回答是否正确？ | 人工标注、自动评估 |
| **回答完整性** | 是否遗漏了重要信息？ | 对比参考答案 |
| **幻觉程度** | 是否编造了不存在的信息？ | 事实核查 |
| **响应速度** | 从提问到回答需要多久？ | 延迟测试 |
| **成本** | 每次查询的成本是多少？ | Token用量统计 |

#### 2.6.2 自动评估指标

**检索阶段**：

- **Recall@K**：正确答案在前K个检索结果中的比例
- **MRR（Mean Reciprocal Rank）**：正确答案的排名倒数的平均值
- **NDCG**：考虑相关度等级的排序质量指标

**生成阶段**：

- **Faithfulness**：回答是否忠实于检索到的文档（不编造）
- **Answer Relevance**：回答是否与问题相关
- **Context Relevance**：检索到的文档是否与问题相关

**评估工具**：

- **RAGAS**：开源RAG评估框架
- **LangSmith**：LangChain的调试和评估平台
- **TruLens**：LLM应用评估工具

#### 2.6.3 人工评估Checklist

对每个测试用例，检查：

- [ ] 回答是否直接回答了问题？
- [ ] 回答是否包含文档中没有的信息（幻觉）？
- [ ] 回答是否遗漏了文档中的重要细节？
- [ ] 对于不确定的问题，模型是否诚实地说"不知道"？
- [ ] 回答是否引用了正确的信息来源？

### 2.7 B端RAG落地难点

#### 2.7.1 权限隔离

**问题**：不同用户只能访问不同的文档

- 普通员工不能看高管的文档
- A部门不能看B部门的数据

**解决方案**：

1. **索引级隔离**：为每个用户组维护独立的向量索引
2. **过滤机制**：在检索时加入权限过滤条件
3. **行级安全**：文档级别打标签，检索时按标签过滤

#### 2.7.2 数据安全

**问题**：

- 企业敏感数据不能上传到第三方API
- 需要满足等保、GDPR等合规要求

**解决方案**：

1. **私有化部署**：在本地服务器部署开源模型和向量数据库
2. **混合架构**：Embedding用本地模型，生成可用私有API
3. **数据脱敏**：索引前对敏感信息脱敏

#### 2.7.3 多模态文档

**问题**：企业文档不仅有文本，还有表格、图表、图片

**解决方案**：

1. **表格处理**：用专门的表格解析工具（如Camelot）提取结构化数据
2. **图片OCR**：对图片中的文字进行识别
3. **多模态模型**：使用支持图像理解的模型（如 GPT-5.6 / Gemini 3）

### 2.8 2026 RAG前沿：Agentic RAG、GraphRAG与Context Engineering

2.1-2.4 描述的是 2024 年基础 RAG——"检索一次 → 生成一次"的线性流程。到 2026 年，生产级 RAG 的演进集中在三个方向：**检索过程 Agent 化**（Agentic RAG）、**知识表示图谱化**（GraphRAG）、**上下文组装工程化**（Context Engineering）。先声明：2.5.2 混合检索、2.5.3 Rerank **没有过时**——它们是任何 2026 高级 RAG 方案的地基，本节讨论的是地基之上的策略层。

| 演进方向 | 解决什么问题 | 与 2.x 的衔接 |
| ------- | ----------- | ----------- |
| Agentic RAG | 复杂问题需要多次、多源检索 | 2.5.4 查询重写之上，检索进入推理循环 |
| GraphRAG | 需要全局归纳与多跳关联问答 | 2.4 Chunking 之上，知识表示换为图谱 |
| Context Engineering | 上下文放什么、怎么放、怎么省钱 | 覆盖 2.2-2.5 所有环节的组装策略 |

#### 2.8.1 Agentic RAG：让模型决定"查什么、查几次"

**定义**：Agentic RAG = 把"检索"从固定流程步骤变成模型可自主决策的工具调用——检索几次、检索什么对象、要不要追问、何时停止，都由 LLM 在推理循环中决定，而不是固定"检索一次就生成"。

| 维度 | 基础 RAG（2024） | Agentic RAG（2026） |
| ---- | -------------- | ----------------- |
| 检索次数 | 固定 1 次 | N 次循环，模型决策 |
| 检索触发 | 流程预设 | 模型判断"信息不足时"再查 |
| 多跳能力 | 弱（单次 Top-K） | 强（逐跳评估） |
| 成本 | 可控 | 循环放大，必须有上限 |
| 可观测性 | 简单 | 需要检索 trace 可回放 |

> **类比**：基础 RAG 是"查一次字典就开口"，Agentic RAG 是"先查目录、发现线索再查正文、还缺就追问"——像真人做调研。

```
          ┌──────────────────────────────────────┐
          │            Agent 检索循环             │
          └──────────────────────────────────────┘
问题 → 规划（需要什么信息？）
        ↓
   检索工具调用（向量库 / 数据库 / API / 文档，可多次）
        ↓
   评估（现有信息够回答吗？）
     ↙            ↘
 不够 → 再检索     够 → 生成回答
 （循环次数设上限）    （超限 → 降级直接回答）
```

2025-2026 主流变体：

1. **路由型**：先分类问题类型，再选择专用检索器
2. **工具型**：检索即工具调用，与普通工具调用融合（EIA 即此形态）
3. **循环型**：生成后自我评估，不够再检索（反思再查）

**PM 关注点**：

- **可观测性**：循环过程必须可回放（检索了什么、为什么再查），否则质量问题无法排查
- **成本**：循环放大 Token 消耗，必须设检索次数上限与预算
- **兜底**：循环超限后降级为"基于已有信息直接回答"，不让用户等死循环

**与 EIA 的关联**：EIA 的 `run_sql` / `get_table_schema` 工具调用，机制上就是"LLM 自主决定检索对象与检索次数"——查什么表、写什么 SQL、要不要再查 Schema，都是模型在推理循环里决策的。EIA 的检索增强已经是 **Agentic 形态**，只是检索对象是数据库而非文档（面试话术详见作战包）。

#### 2.8.2 GraphRAG：把知识织成图再推理

**定义**：GraphRAG = 先对知识库做实体与关系抽取，构建知识图谱（实体=节点、关系=边），并对图做社区检测生成社区摘要；检索时沿图结构做多跳推理，回答需要全局归纳的问题。

```
文档 → 实体/关系抽取 → 知识图谱构建 → 社区检测 → 社区摘要
                                                ↑
查询 → 意图理解 → 沿图多跳检索（实体→关系→实体） → 生成回答
```

**适用场景对照**：

| 适用                                   | 不适用                             |
| ------------------------------------ | -------------------------------- |
| 实体关系密集型语料（人物/公司/事件关系）              | 事实性检索（查具体数字，向量检索更快）             |
| 多跳关联问答（"A 和 B 有什么关系"）              | 频繁更新的语料（图谱增量维护成本高）              |
| 需要全局归纳（"整体趋势/主题是什么"）               | 已有结构化数据库（**Schema 就是图**，见甄别段）     |

**真实指标（甄别营销话术）**：微软 GraphRAG 论文报告的是 **comprehensiveness（全面性）提升 72%、diversity（多样性）提升 94%**（对比朴素 RAG）——注意这是"回答覆盖率/多样性"维度，**不是"准确率"**。市面上流传的"GraphRAG 多跳推理 99% 准确率"在论文中不存在，属营销话术，面试提到时可主动澄清。

**PM 关注点**：

- **构建成本**：实体抽取 + 社区摘要的 Token 成本通常是文档规模的数倍
- **更新成本**：语料变化需要图谱增量维护，不是一次性构建
- **收益验证**：上线前用 2.6 节 RAGAS 基线对比，升不升以数据说话

**甄别段（结合 EIA）**：EIA 的数据是关系型数据库——**"图"就是 Schema 本身**（表=实体、外键=关系），多跳推理就是 SQL JOIN。对 EIA 做图谱化等于把已结构化的关系模型重新建模一遍，零新增信息、纯成本。判断要不要 GraphRAG，先问：**你的数据是不是"图"？** 不是图的数据，图谱化就是伪需求。

#### 2.8.3 Context Engineering（上下文工程）

**定义**：Context Engineering = 把 LLM 的上下文当作"受控输入系统"来设计——选择放什么、压缩什么、按什么顺序组装、如何复用，用工程手段提高输出质量、降低成本。2025-2026 的主流共识：**RAG 是 Context Engineering 的子集**——RAG 解决"放什么"，Context Engineering 还管"怎么放"。

**技术清单**：

| 技术 | 作用 | PM 关注点 |
| ---- | ---- | ------- |
| Context Selection（上下文选择） | 决定放什么进上下文 | 与 RAG 检索协同 |
| **Prompt Caching**（提示词缓存） | 复用稳定前缀的 KV 计算 | 直接降成本，重点 |
| 结构化压缩 | 长内容压缩为摘要/表格 | 信息密度 vs 丢失 |
| 长上下文动态窗口 | 按任务需要扩缩窗口 | 长不等于好（1.5 节） |
| 位置与顺序策略 | 关键信息放开头/结尾 | 中间遗忘效应 |

**Prompt Caching 详解**：

- **原理**：LLM 逐 Token 生成时，相同前缀的 KV 缓存可复用，只计算新增部分
- **量级**：长前缀场景（系统提示 + 固定知识片段）成本降低约 90%、延迟下降 50% 以上
- **触发条件**：前缀需逐 Token 完全一致（含空格与标点）
- **PM 关注点**：把"稳定前缀"（系统提示、知识库固定片段）设计成缓存友好结构；把缓存命中率当成本指标监控

```
固定前缀（命中缓存，不重复计费）          动态部分
系统提示 │ 知识库固定片段 │ 检索片段(排序) │ 历史对话 │ 用户问题(最后)
```

**PM 关注点**：

- **成本账**：Prompt Caching 直接改变单位经济，长上下文产品（客服、Copilot）必算
- **中间遗忘**：长上下文不等于好——关键指令放开头/结尾，与 1.5 节"不是所有长上下文都好用"呼应

#### 2.8.4 升级判断：2026 技术甄别力（PM 决策框架）

**核心原则**：先定位瓶颈，再选升级手段——不做"为了 2026 而 2026"。

| 数据形态 | 瓶颈表现 | 对应升级手段 |
| ------ | ------ | ---------- |
| 非结构化文档 | 召回不足（同义改写查不到） | Hybrid：BM25 精确召回 + 向量语义召回 |
| 非结构化文档 | 召回够但排序不准 | Reranker 精排（召回 100 → 精排 5） |
| 非结构化文档 | 查询理解差（问题太泛） | 查询重写 / HyDE（2.5.4） |
| 非结构化文档 | 需要全局归纳 | GraphRAG（先评估成本） |
| 所有形态 | 生成幻觉、答非所问 | Context Engineering + 评估闭环（2.6） |

**EIA 的真升级路线**：若未来扩展文档问答场景，检索层标准形态是 **Hybrid Search（BM25 + 向量）+ Reranker**——BM25 用关键词精确召回（PG 全文检索即可实现），向量做语义召回（BGE-M3 继续复用），两者按 2.5.2 的 α 加权或 RRF 融合；Reranker 选 bge-reranker 本地 Ollama（延续 BGE-M3 的本地化零 API 成本逻辑）。**BGE-M3 路线没有过时**——过时的是"纯向量单通道"检索，不是"向量检索"本身。

**反营销话术检查清单**：

| 常见说法 | 真相 |
| ------ | ---- |
| "GraphRAG 多跳推理 99% 准确率" | 论文无此数字（真实指标 72%/94% 覆盖率/多样性） |
| "Agentic RAG 万能" | 循环放大成本，必须有上限与兜底 |
| "必须上图数据库" | 先问数据是不是图——结构化数据 Schema 就是图 |
| "纯向量检索已过时" | 过时的是单通道，混合检索里向量仍是半边天 |

**PM 关注点**：先测再升——升级前用 2.6 节 RAGAS 建立基线，升级后对比验收；评估数据是技术决策的唯一裁判。

## 第三章：Agent架构与实现

### 3.1 什么是AI Agent？

#### 3.1.1 定义

**AI Agent（AI智能体）**：能够**自主感知环境、做出决策、执行动作**的AI系统。

**与传统LLM调用的区别**：

| 维度 | 传统LLM调用 | AI Agent |
| -------- | ------------ | ---------- |
| **交互方式** | 一问一答 | 多轮自主执行 |
| **工具使用** | 无 | 可以调用外部工具 |
| **记忆** | 单次对话 | 长期记忆 |
| **规划** | 无 | 能分解任务、制定计划 |
| **适用场景** | 简单问答 | 复杂任务自动化 |

#### 3.1.2 Agent的核心组件

```
┌─────────────────────────────────────┐
│           AI Agent 架构              │
├─────────────────────────────────────┤
│                                     │
│  ┌─────────┐    ┌─────────────┐   │
│  │  规划   │ → │   工具调用   │   │
│  │Planning │    │ Tool Calling │   │
│  └─────────┘    └─────────────┘   │
│       ↑                ↓           │
│  ┌─────────┐    ┌─────────────┐   │
│  │  记忆   │ ← │   行动执行   │   │
│  │ Memory  │    │   Action    │   │
│  └─────────┘    └─────────────┘   │
│       ↑                            │
│  ┌─────────┐                       │
│  │  环境   │ ← 用户输入/外部反馈   │
│  │Environment                      │
│  └─────────┘                       │
│                                     │
└─────────────────────────────────────┘
```

---

### 3.2 ReAct模式：推理+行动

#### 3.2.1 核心思想

**ReAct** = **Re**asoning（推理） + **Act**ing（行动）

**核心理念**：模型不应该直接给出答案，而应该**先思考、再行动、观察结果、继续思考**...

#### 3.2.2 工作流程

```
用户提问："北京今天的天气怎么样？"

Step 1 - 思考（Thought）
"用户想知道北京今天的天气。我没有实时天气数据，需要调用天气API。"

Step 2 - 行动（Action）
调用工具：get_weather(city="北京")

Step 3 - 观察（Observation）
工具返回："北京今天晴，25°C，北风2级"

Step 4 - 思考（Thought）
"我已经获得了天气信息，可以直接回答用户了。"

Step 5 - 最终回答（Answer）
"北京今天天气晴朗，气温25°C，北风2级，适合外出。"
```

#### 3.2.3 ReAct的优势

| 优势 | 说明 |
| ------- | ---------------- |
| **可追溯** | 每一步思考都可见，方便调试和审计 |
| **可纠错** | 中间步骤出错时可以重新尝试 |
| **可扩展** | 可以通过增加工具来扩展能力 |
| **更可靠** | 复杂任务分步执行，降低出错概率 |

---

### 3.3 Function Calling（工具调用）

#### 3.3.1 什么是Function Calling？

**定义**：让LLM能够识别何时需要调用外部工具，并生成正确的函数调用参数。

**类比**：就像给模型一个"工具箱"，模型根据需要选择合适的工具。

#### 3.3.2 Function Calling的工作流程

```
1. 定义工具（告诉模型有哪些工具可用）
   ↓
2. 用户提问
   ↓
3. 模型判断是否需要调用工具
   ├─ 不需要 → 直接回答
   └─ 需要 → 生成函数调用JSON
          ↓
4. 系统执行函数调用
          ↓
5. 把结果返回给模型
          ↓
6. 模型基于结果生成最终回答
```

#### 3.3.3 工具定义示例

```json
{
  "name": "query_database",
  "description": "查询数据库获取订单信息",
  "parameters": {
    "type": "object",
    "properties": {
      "order_id": {
        "type": "string",
        "description": "订单号"
      },
      "fields": {
        "type": "array",
        "description": "需要查询的字段",
        "items": {
          "type": "string",
          "enum": ["status", "amount", "customer", "date"]
        }
      }
    },
    "required": ["order_id"]
  }
}
```

**PM设计要点**：

- **描述要清晰**：工具description直接影响模型是否正确选择工具
- **参数要精确**：type、enum、required都要定义清楚
- **粒度要合适**：工具太细会增加调用次数，太粗会降低灵活性

#### 3.3.4 B端常见工具类型

| 工具类型      | 示例                                | 适用场景      |
| --------- | --------------------------------- | --------- |
| **数据库查询** | query_database, get_customer_info | 数据查询      |
| **API调用** | call_weather_api, send_email      | 外部服务      |
| **文件操作**  | read_file, write_report           | 文档处理      |
| **计算工具**  | calculator, date_diff             | 精确计算      |
| **搜索引擎**  | web_search, search_knowledge_base | 信息检索      |
| **代码执行**  | run_python, execute_sql           | 数据分析      |

### 3.4 记忆机制

#### 3.4.1 为什么需要记忆？

**问题**：

- LLM本身是无状态的，每次请求都是独立的
- 多轮对话中，模型需要记住之前说过什么
- 复杂任务需要跨会话保持上下文

#### 3.4.2 记忆的类型

| 类型 | 说明 | 示例 | 技术实现 |
| -------- | --------- | ---------- | --------- |
| **短期记忆** | 当前对话的上下文 | 多轮对话中的历史消息 | 直接传入消息列表 |
| **长期记忆** | 跨会话的记忆 | 用户的偏好、历史行为 | 数据库存储 |
| **实体记忆** | 关于特定对象的信息 | 客户资料、产品信息 | 知识图谱 |
| **程序记忆** | 如何完成任务的技能 | 常用工作流、最佳实践 | 预定义的Skill |

#### 3.4.3 短期记忆的实现

```
消息列表格式：
[
  {"role": "system", "content": "你是一个客服助手"},
  {"role": "user", "content": "我想查询订单"},
  {"role": "assistant", "content": "请提供您的订单号"},
  {"role": "user", "content": "订单号是12345"}
]
```

**注意事项**：

- 消息列表会消耗Token，太长会超出上下文限制
- 需要定期总结对话历史，压缩成摘要

#### 3.4.4 长期记忆的实现

**方案1：向量数据库记忆**

- 把重要的对话内容存入向量数据库
- 新对话时先检索相关历史记忆

**方案2：结构化记忆**

- 用数据库表存储用户的属性、偏好
- 如：用户ID、喜欢的风格、常用功能

**方案3：知识图谱记忆**

- 用图数据库存储实体关系
- 如：用户A购买了产品B，产品B属于类别C

**PM设计要点**：

- 长期记忆需要考虑**隐私和安全**：用户的数据如何存储？谁能访问？
- 需要设计**记忆更新机制**：什么时候更新记忆？如何验证记忆的准确性？

### 3.5 多Agent协作

#### 3.5.1 为什么需要多Agent？

**单Agent的局限**：

- 一个Agent同时具备所有能力，会变得复杂且容易出错
- 不同任务需要不同的专业技能

**多Agent的优势**：

- **专业化**：每个Agent负责一个领域
- **并行化**：多个Agent可以同时工作
- **可扩展**：新增能力只需添加新Agent

#### 3.5.2 多Agent架构模式

**模式1：主管-工人（Supervisor-Worker）**

```
        ┌─────────────┐
        │  Supervisor │ ← 主管Agent：分配任务
        │   (主管)     │
        └──────┬──────┘
               │
      ┌────────┼────────┐
      ↓        ↓        ↓
┌────────┐ ┌────────┐ ┌────────┐
│Worker 1│ │Worker 2│ │Worker 3│
│(研究员)│ │(写手)  │ │(审核员)│
└────────┘ └────────┘ └────────┘
```

**模式2：流水线（Pipeline）**

```
输入 → [Agent A: 数据清洗] → [Agent B: 分析] → [Agent C: 报告生成] → 输出
```

**模式3：协作讨论（Collaborative Discussion）**

```
多个Agent围绕一个问题进行多轮讨论，最终达成共识
```

#### 3.5.3 B端多Agent场景示例

**智能客服系统**：

```
用户问题
  ↓
[意图识别Agent] → 判断问题类型
  ↓
├─ 订单查询 → [订单Agent] → 查询数据库 → 回答
├─ 技术支持 → [技术Agent] → 检索知识库 → 回答
├─ 投诉建议 → [工单Agent] → 创建工单 → 确认
└─ 复杂问题 → [主管Agent] → 分配给人工客服
```

## 第四章：Prompt工程完全指南

### 4.1 Prompt基础

#### 4.1.1 什么是Prompt？

**Prompt**（提示词）是用户给LLM的输入，用于指导模型生成期望的输出。

**Prompt可以包含**：

- 任务指令（你要做什么）
- 上下文信息（相关背景）
- 输入数据（要处理的内容）
- 输出格式要求（怎么输出）
- 约束条件（不要做什么）

#### 4.1.2 Prompt的基本结构

```
【角色定义】你是一个专业的B端产品经理

【任务指令】请分析以下用户需求，提取核心痛点和功能建议

【上下文】我们是一个SaaS企业服务平台，主要服务中小企业

【输入数据】
用户反馈：
"我们团队有50人，目前用Excel管理客户信息，经常找不到最新联系方式，
希望能有一个系统统一管理，最好能和钉钉打通。"

【输出格式】
请以JSON格式输出：
{
  "core_pain_points": ["痛点1", "痛点2"],
  "feature_suggestions": ["功能建议1", "功能建议2"],
  "priority": "高/中/低",
  "user_segment": "用户分层"
}

【约束条件】
- 不要输出JSON以外的内容
- 痛点数量不超过5个
- 使用中文
```

---

### 4.2 核心Prompt技法

#### 4.2.1 Zero-Shot Prompting（零样本提示）

**定义**：直接给出任务，不提供示例。

**适用场景**：模型已经具备该能力的任务。

**示例**：

```
请总结以下文本的主要观点：

[文本内容]
```

**优点**：简单直接
**缺点**：对于复杂或特殊格式的任务，效果可能不佳

#### 4.2.2 Few-Shot Prompting（少样本提示）

**定义**：提供几个输入-输出的示例，让模型"学习"期望的模式。

**适用场景**：需要特定格式、风格或模式的输出。

**示例**：

```
请将以下用户反馈分类为"功能请求"、"Bug反馈"、"咨询"或"投诉"

示例1：
输入："希望增加导出PDF的功能"
输出：功能请求

示例2：
输入："系统登录一直报错，显示500"
输出：Bug反馈

示例3：
输入："这个功能和竞品A有什么区别？"
输出：咨询

现在请分类：
输入："你们的服务太差了，我要退款！"
输出：
```

**技巧**：

- 示例数量：一般2-5个即可
- 示例质量：选择有代表性的、边界清晰的例子
- 示例多样性：覆盖不同情况

#### 4.2.3 Chain-of-Thought（思维链，CoT）

**定义**：让模型"一步一步思考"，在给出最终答案前先展示推理过程。

**核心发现**：让模型"说出"推理过程，能显著提升复杂推理任务的准确率。

**标准CoT示例**：

```
Q: 一个会议室有8排椅子，每排12把。已经坐了45人，还剩多少空位？
A: 让我们一步一步思考：
   1. 首先计算总椅子数：8排 × 12把/排 = 96把椅子
   2. 已经坐了45人，所以占用了45把椅子
   3. 空位数 = 总椅子数 - 已占用 = 96 - 45 = 51
   因此，还剩51个空位。
```

**自动CoT（Auto-CoT）**：
对于批量任务，可以让模型先自己生成几个推理示例，然后用这些示例来指导后续回答。

**适用场景**：

- 数学计算
- 逻辑推理
- 复杂分析
- 多步骤决策

**B端PM应用**：

```
请分析以下客户需求，判断我们应该优先做哪个功能：

需求A：[描述]
需求B：[描述]
需求C：[描述]

请按照以下框架分析：
1. 战略契合度（1-5分）
2. 用户影响面（1-5分）
3. 技术可行性（1-5分）
4. 商业价值（1-5分）
5. 综合评分和推荐优先级

请展示你的推理过程，然后给出最终建议。
```

#### 4.2.4 Self-Consistency（自一致性）

**定义**：对于同一个问题，让模型生成多个答案，然后选择出现次数最多的答案。

**适用场景**：对准确性要求极高的场景（如医疗、金融）。

**实现方式**：

- 使用较高的temperature参数生成多个回答
- 统计各答案的出现频率
- 选择最一致的答案

#### 4.2.5 Tree-of-Thoughts（思维树，ToT）

**定义**：对于复杂问题，让模型探索多条推理路径，评估每条路径的前景，选择最优路径。

**类比**：就像下棋时的"思考几步"，不只是线性推理，而是分支探索。

**适用场景**：

- 需要探索多种方案的问题
- 创意生成
- 复杂决策

### 4.3 Structured Output（结构化输出）

#### 4.3.1 为什么需要结构化输出？

**问题**：模型输出的格式不稳定

- 有时用列表，有时用段落
- JSON格式可能不完整或有语法错误
- 前后不一致，难以解析

**解决方案**：明确指定输出格式，并要求模型严格遵守。

#### 4.3.2 结构化输出方法

**方法1：明确指定格式**

```
请以以下JSON格式输出，不要添加任何其他内容：
{
  "status": "success/error",
  "data": {
    "field1": "value1",
    "field2": "value2"
  },
  "message": "说明信息"
}
```

**方法2：使用JSON模式（JSON Mode）**

```python
# OpenAI API示例
response = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[{"role": "user", "content": prompt}],
    response_format={"type": "json_object"}  # 强制JSON输出
)
```

**方法3：使用结构化输出（Structured Outputs）**

```python
from pydantic import BaseModel

class ProductAnalysis(BaseModel):
    pain_points: list[str]
    features: list[str]
    priority: str
    effort: str

response = client.beta.chat.completions.parse(
    model="gpt-5.6-terra",
    messages=[{"role": "user", "content": prompt}],
    response_format=ProductAnalysis  # 直接输出Pydantic模型
)
```

#### 4.3.3 结构化输出的最佳实践

| 原则 | 说明 |
| ---------- | ------------------ |
| **明确字段定义** | 每个字段都要说明类型、用途、约束 |
| **提供示例值** | 让模型理解期望的数据格式 |
| **处理空值** | 明确说明字段为空时如何表示 |
| **枚举值限定** | 对于有限选项的字段，列出所有可能的值 |
| **嵌套结构清晰** | 复杂对象要分层定义 |

### 4.4 减少幻觉的策略

#### 4.4.1 策略1：明确知识边界

```
请基于以下文档内容回答问题。如果文档中没有相关信息，
请明确回答"根据提供的资料，我无法回答这个问题"。

[文档内容]

问题：[用户问题]
```

#### 4.4.2 策略2：要求引用来源

```
请回答以下问题，并在回答中标注信息来源：
- 如果是来自提供的文档，请标注[文档名：段落]
- 如果是你的常识，请标注[常识]
- 如果不确定，请明确说"不确定"

[文档内容]

问题：[用户问题]
```

#### 4.4.3 策略3：分步验证

```
请按照以下步骤回答问题：
1. 先列出与问题相关的所有事实
2. 检查这些事实之间是否有矛盾
3. 对于不确定的事实，标注"待验证"
4. 基于确定的事实给出回答

问题：[用户问题]
```

#### 4.4.4 策略4：多模型交叉验证

```
让多个不同的模型回答同一个问题，然后：
- 如果答案一致，可信度较高
- 如果答案不一致，需要人工介入判断
```

#### 4.4.5 策略5：Self-Check（自我检查）

```
请先回答问题，然后：
1. 检查你的回答中是否有与事实不符的内容
2. 检查是否遗漏了重要信息
3. 如果有不确定的内容，请明确标注

问题：[用户问题]
```

    "优先级": "紧急/高/中/低",
    "建议处理方式": "具体建议",
    "需要跟进": true/false
  }
}

约束：
- 分类要准确，如果不确定，标注"待确认"
- 情感分析要客观，基于文本内容
```

### 4.7 Prompt评测方法论（实战核心）

> 这一节是大多数手册里没有的内容，也是AI PM和"只会写Prompt"的人之间最大的分水岭。会写Prompt是入门，会**系统评测和迭代**Prompt才是核心能力。

#### 4.7.1 为什么需要评测体系？

**核心问题**：Prompt改了之后，你怎么知道是变好了还是变坏了？

传统软件改了代码，跑一遍单元测试就知道有没有破坏原有功能。但Prompt是自然语言，改一个字可能：

- 让某类问题的回答变好了
- 同时让另一类问题的回答变差了
- 你完全不知道

没有评测体系的Prompt迭代，本质上是**盲目试错**。

#### 4.7.2 评测集（Golden Set）的构建

**什么是评测集**：一组精心构造的"问题-期望回答"对，用来衡量Prompt或模型版本的效果。

**评测集的构成原则**：

| 题型 | 比例 | 作用 |
| -------- | ------ | --------------------- |
| **标准场景** | 50% | 覆盖最高频的正常使用情况，确保基础能力稳定 |
| **边界场景** | 30% | 数据缺失、输入极短/极长、多领域混合查询 |
| **对抗场景** | 20% | 历史上出过问题的BadCase，防止回归 |

**构建流程**：

```
第一步：定义评测维度
  → 你这个AI功能要考核什么？（准确性/完整性/格式/逻辑性）

第二步：收集种子问题
  → 真实用户问过的问题 + 你预判会出问题的情况

第三步：标注期望输出
  → 不一定是"完整正确答案"，而是"期望具备的特征"
  → 示例："应该包含具体金额"、"不能出现未提及的人名"

第四步：确定评分方式
  → 二元评分（Pass/Fail）：简单、可自动化
  → 多维评分（1-5分）：细粒度，但需要人工

第五步：冻结基线
  → 当前版本跑一次评测集，记录基线分数
  → 之后每次Prompt修改都和这个基线比较
```

**实战示例（以AI周报生成为例）**：

```
评测集结构：
├── 标准场景（10条）
│   ├── 任务数据完整的项目周报
│   ├── 有里程碑完成的项目周报
│   └── 有延期任务的项目周报
├── 边界场景（6条）
│   ├── 本周只有1条任务更新（数据稀疏）
│   ├── 项目跨越多个部门（复杂结构）
│   └── 任务名称包含特殊字符
└── 对抗场景（4条）
    ├── 曾经导致幻觉的数据结构（回归测试）
    └── 曾经格式输出错误的输入样式
```

#### 4.7.3 Prompt迭代日志：每次修改都要记录

**格式模板**：

```
## Prompt迭代记录 v1.x → v1.y

### 变更内容
[具体改了哪几行，用diff格式标注]

### 变更原因
[是因为BadCase触发、还是主动优化、还是成本考虑]

### 验证方式
[跑了评测集的哪几条？结果如何？]

### 效果对比
| 指标     | v1.x   | v1.y   | 变化     |
| ------ | ------ | ------ | ------ |
| 评测集通过率 | 78%    | 85%    | +7%    |
| 重新生成率  | 30%    | 22%    | -8%    |
| 平均编辑量  | 240字   | 180字   | -25%   |

### 遗留问题
[这次迭代还没解决什么？]

### 教训
[这次迭代学到了什么可复用的经验？]
```

**为什么要记录"教训"**：因为Prompt工程有很多反直觉的规律（比如"加了更多约束反而输出更乱"），不记录就会重复踩坑。

#### 4.7.4 BadCase复盘：从错误中系统学习

**BadCase的定义**：AI输出的结果，和你预期有明显差距的案例。

**BadCase的价值**：每一个BadCase都是"评测集扩充"的机会——复盘完之后，把这个Case加入对抗场景，防止回归。

**标准复盘流程（五步法）**：

```
Step 1：现象描述
  "用户问了什么，AI输出了什么，哪里不对"
  → 要具体到句子级别，不要说"质量差"

Step 2：根因诊断
  从外到内逐层排查：
  ① 数据问题？（输入数据缺失、格式异常）
  ② Prompt问题？（指令歧义、约束缺失）
  ③ 模型问题？（该模型在这类任务上能力本就有限）
  ④ 架构问题？（根本不适合这种方案，需要重设计）

Step 3：修复方案
  针对根因的具体修改，可以是：
  - 补充Prompt约束
  - 调整数据预处理逻辑
  - 增加输出后校验

Step 4：验证
  用修复后的版本重新跑这个BadCase，
  同时跑完整评测集，确认没有引入新问题

Step 5：教训提炼
  "这类问题的共性是什么？如何预防下一个同类BadCase？"
```

**BadCase分级**：

| 级别 | 定义 | 处理优先级 |
| ------ | -------------------- | ------------ |
| **P0** | 事实错误（出现未提及的人名/数据/事件） | 立即修复，阻塞发布 |
| **P1** | 逻辑错误（因果关系错误、虚假关联） | 当次迭代必须修复 |
| **P2** | 格式问题（输出结构不符合预期） | 排期修复 |
| **P3** | 体验问题（措辞不够专业/流畅） | 积累到一定数量再集中优化 |

#### 4.7.5 回归测试：防止"越改越坏"

**核心原则**：每次修改Prompt，必须跑完整评测集，不能只验证"改动点"。

原因：Prompt是一个整体，改了A部分的措辞，可能意外影响了B部分的输出——这种副作用在没有评测集的情况下完全察觉不到，等到用户反馈才发现，代价巨大。

**回归测试的操作规范**：

```
修改Prompt前：记录当前评测集得分（基线）
修改Prompt后：跑完整评测集
对比结果：
  ├── 整体分数提升 + 无新增失败 → 可以发布
  ├── 整体分数提升 + 有新增失败 → 评估失败的重要性再决定
  ├── 整体分数持平 + 无新增失败 → 可以发布（保守）
  └── 整体分数下降 → 回滚，重新分析
```

## 第五章：AI产品交互设计范式

### 5.1 AI产品的三种交互模式

#### 5.1.1 生成式（Generative）

**特征**：用户触发，AI一次性生成完整内容

**示例**：

- 点击"生成报告"按钮，AI输出完整报告
- 输入关键词，AI生成营销文案

**适用场景**：

- 内容创作（文案、代码、邮件）
- 文档生成（报告、合同、简历）
- 创意发散（头脑风暴、设计思路）

**设计要点**：

- 提供清晰的输入引导
- 支持生成后的编辑
- 提供重新生成的选项
- 显示生成进度

#### 5.1.2 对话式（Conversational）

**特征**：以聊天界面为载体，多轮交互

**示例**：

- 智能客服聊天窗口
- AI助手对话界面
- 多轮表单填写

**适用场景**：

- 信息查询（知识库问答）
- 任务执行（预订、下单）
- 复杂配置（引导式设置）
- 咨询建议（个性化推荐）

**设计要点**：

- 明确AI的身份和能力边界
- 提供快捷操作按钮
- 支持消息回溯和上下文查看
- 处理长对话的总结和重置

#### 5.1.3 嵌入式（Embedded）

**特征**：AI能力无缝融入现有功能，不显式展示AI界面

**示例**：

- 输入框的自动补全
- 文档编辑时的智能纠错
- 表格的自动填充建议
- 搜索框的智能推荐

**适用场景**：

- 效率提升（减少用户操作）
- 质量保障（实时纠错、建议）
- 个性化（根据上下文智能调整）

**设计要点**：

- AI建议要低调，不打断用户流程
- 提供接受/忽略选项
- 让用户有控制权
- 渐进式引入，避免突然变化

---

### 5.2 渐进式披露（Progressive Disclosure）

#### 5.2.1 核心原则

**不要一次性展示所有AI能力，而是根据用户需要逐步展示。**

#### 5.2.2 四级渐进策略

| 级别 | 展示方式 | 示例 | 适用场景 |
| ----------- | ---------------- | ------------- | --------- |
| **L1：静默辅助** | AI在后台工作，用户无感知 | 输入时的自动保存、智能纠错 | 所有场景的基础层 |
| **L2：轻量建议** | 以 subtle 的方式提供建议 | 输入框下方的智能补全 | 用户可能需要帮助时 |
| **L3：主动辅助** | 用户触发后AI主动工作 | 点击"智能生成"按钮 | 用户明确需要帮助时 |
| **L4：深度交互** | 完整的AI对话界面 | 打开AI助手侧边栏 | 复杂任务、多轮交互 |

#### 5.2.3 B端产品设计示例

**场景：合同审核系统**

```
L1（静默）：用户上传合同后，后台自动提取关键条款

L2（轻量）：在合同文本中，高风险条款自动高亮，hover显示风险提示

L3（主动）：用户点击"智能审核"，AI生成审核报告

L4（深度）：用户打开"AI法务助手"，可以追问：
  - "这个违约金条款是否合理？"
  - "和行业标准对比如何？"
  - "建议怎么修改？"
```

---

### 5.3 可解释性设计（Explainable AI）

#### 5.3.1 为什么需要可解释性？

**B端场景的特殊要求**：

- 企业决策需要知道"为什么"
- 合规审计需要追溯决策依据
- 错误时需要定位问题根源

#### 5.3.2 可解释性设计模式

**模式1：显示置信度**

```
AI建议：建议将优先级设为"高"
置信度：92%（基于历史数据：类似需求平均3天内被采纳）
```

**模式2：展示推理过程**

```
AI分析结论：该客户有80%概率会流失
推理过程：
  1. 近30天登录次数：0次（低于平均值5次）
  2. 上次付费距今：120天（超过平均续费周期90天）
  3. 客服工单数：5个（满意度评分平均2.3/5）
```

**模式3：提供依据来源**

```
AI回答：公司的年假天数是15天/年
信息来源：
  - 《员工手册》第3章第2节
  - 有效期：2024年1月1日至今
  - 点击查看原文
```

**模式4：对比展示**

```
AI建议：选择方案B
对比分析：
| 维度 | 方案A | 方案B（推荐） | 方案C |
| 成本 | 高   | 中       | 低   |
| 效果 | 中   | 高       | 低   |
| 风险 | 中   | 低       | 高   |
```

---

### 5.4 错误处理与边界情况

#### 5.4.1 AI出错的常见类型

| 错误类型      | 示例         | 设计对策         |
| --------- | ---------- | ------------ |
| **幻觉**    | 生成了不存在的事实  | 显示信息来源、置信度   |
| **理解偏差**  | 误解了用户意图    | 提供澄清选项、多轮确认  |
| **超时**    | 生成时间过长     | 显示进度、支持取消    |
| **内容违规**  | 生成了敏感内容    | 内容过滤、安全兜底    |
| **系统错误**  | API调用失败    | 友好的错误提示、重试机制 |
| **拒绝回答**  | 模型拒绝回答某些问题 | 解释原因、提供替代方案  |

#### 5.4.2 兜底设计原则

```
1. 降级 gracefully
   - AI不可用时，回退到传统功能
   - 部分失败时，展示已成功的部分

2. 让用户掌控
   - 始终提供"人工介入"的选项
   - 允许用户修改AI的结果

3. 透明沟通
   - 明确告知用户AI的限制
   - 出错时解释原因，不甩锅

4. 快速恢复
   - 一键重试
   - 保存用户输入，避免重复劳动
```

#### 5.4.3 B端场景的兜底方案示例

**场景：AI生成报告**

| 情况 | 兜底方案 |
| ----- | ------------------------------- |
| 数据不足 | "当前数据不足以生成完整报告，建议补充以下数据：[列表]" |
| 生成超时 | "报告生成中，预计还需要2分钟。您可以先查看已生成的部分。" |
| 结果质量低 | "AI生成的内容可能需要人工校验，建议重点检查：[提示点]" |
| 系统错误 | "报告生成遇到临时问题，请重试或联系管理员。您的输入已保存。" |

### 5.5 人机协作（Human-in-the-loop）

#### 5.5.1 协作模式

**模式1：AI建议，人决策**

```
AI生成3个方案 → 人选择或修改 → 执行
适用：方案选择、内容审核、审批流程
```

**模式2：人发起，AI执行**

```
人下达指令 → AI自动执行 → 人验收结果
适用：数据查询、报告生成、批量操作
```

**模式3：人机协作**

```
人做一部分 → AI辅助做一部分 → 人做另一部分
适用：文档编辑、代码开发、设计工作
```

**模式4：AI监控，人处理异常**

```
AI自动处理常规情况 → 异常情况交给人 → 人处理后AI学习
适用：客服、运维监控、质量控制
```

#### 5.5.2 B端场景的人机协作设计

**场景：智能审批系统**

```
L1：AI自动审批（规则明确、风险低的申请）
  → 通过率：60%

L2：AI预审 + 人工复核（中等风险的申请）
  → AI给出风险提示和建议 → 审批人确认或修改
  → 占比：30%

L3：人工审批 + AI辅助（高风险或复杂的申请）
  → AI整理相关资料、生成分析报告 → 审批人决策
  → 占比：10%
```

### 6.4 AI产品成本模型

#### 6.4.1 Token成本计算

**计费方式**：

- 按输入Token + 输出Token分别计费
- 不同模型价格不同

**计算公式**：

```
单次成本 = (输入Token数 × 输入单价) + (输出Token数 × 输出单价)
日成本 = 单次成本 × 日调用次数
月成本 = 日成本 × 30
```

**示例计算**：

```
场景：客服问答
模型：DeepSeek V4 Flash（2026-08 定价）
输入：平均500 Token
输出：平均300 Token
日调用：1000次

单价：
- 输入：$0.14 / 1M Token
- 输出：$0.28 / 1M Token

单次成本 = (500 × $0.14/1M) + (300 × $0.28/1M)
         = $0.00007 + $0.000084
         = $0.000154

日成本 = $0.000154 × 1000 = $0.154
月成本 = $0.154 × 30 = $4.6
```

#### 6.4.2 成本优化策略

| 策略 | 方法 | 效果 |
| ------------ | --------- | ---------- |
| **模型降级** | 简单任务用小模型 | 成本降低50-90% |
| **缓存** | 缓存常见问题的回答 | 命中时成本为0 |
| **Prompt压缩** | 减少输入Token | 直接降低输入成本 |
| **响应截断** | 限制最大输出长度 | 控制输出成本 |
| **批量处理** | 合并多个请求 | 减少API调用次数 |
| **本地部署** | 高频场景用开源模型 | 固定成本替代变动成本 |

#### 6.4.3 成本监控

**建议指标**：

- 单次平均Token消耗
- 单次平均成本
- 日/周/月总成本
- 成本占收入比例

### 6.7 AI产品运维：传统产品没有的新挑战

> 这一章是企业级AI产品落地后最容易踩的坑，也是传统PM转型后最容易忽视的盲区。传统SaaS上线后，功能不会"自己变差"；但AI产品会——即使你什么都没改。

#### 6.7.1 模型漂移（Model Drift）：你的产品在悄悄变差

**什么是模型漂移**：

你依赖的外部LLM（GPT-5.6、DeepSeek V4 等）在你不知情的情况下，被供应商更新了版本。新版本在某些能力上可能更强，但也可能让你精心调好的Prompt表现变差——而且这个变化是**无通知、无changelog的**。

**具体表现**：

- 某天开始，用户对AI周报质量的投诉突然增多
- 你没有改任何代码，但Prompt的输出风格明显变了
- Reflection质检通过率从85%悄悄跌到70%，你一周后才发现

**为什么危险**：不同于代码bug（有明确的时间点和变更记录），模型漂移是**渐进式的、隐蔽的**，没有监控就不会发现。

**应对策略**：

```
策略一：建立模型版本监控
  → 每天定时跑一批固定的评测用例（"金丝雀测试集"）
  → 对比分数趋势，超过阈值自动报警
  → 这套体系和评测集（4.7节）打通，复用同一份测试数据

策略二：Prompt版本和模型版本双重锁定
  → 记录"Prompt v2.3"在"DeepSeek-V4-Flash-0731"这个版本上的基线分数
  → 当供应商推新版本时，先用新版本跑评测集，再决定是否切换

策略三：多模型降级备案
  → 不依赖单一供应商，备选2-3个模型
  → 提前测好备选模型的效果，确保切换时不会断崖式下降
  → 设计LLM Provider抽象层，让模型切换只需改配置而非改代码
```

**LLM Provider抽象层的设计思路**：

```
# 错误的做法：代码里直接写死模型调用
response = openai_client.chat.completions.create(
    model="deepseek-v4-flash", ...)

# 正确的做法：通过配置切换
LLM_PROVIDER = config.get("llm_provider")  # 从环境变量读取

if LLM_PROVIDER == "openai":
    response = call_openai(prompt)
elif LLM_PROVIDER == "deepseek":
    response = call_deepseek(prompt)
elif LLM_PROVIDER == "qwen":
    response = call_qwen(prompt)
```

这个看起来简单的设计，在模型出问题时可以**5分钟内完成降级**，而不是等工程师改代码重新部署。

#### 6.7.2 Prompt版本管理：AI产品特有的"代码管理"

**为什么Prompt需要版本管理**：

传统产品的"版本管理"是管代码，AI产品还需要管Prompt——因为Prompt是AI功能效果的核心决定因素，它的变更同样需要可追溯、可回滚。

**Prompt的四个版本状态**：

| 状态 | 含义 | 操作权限 |
| ------------------- | --------- | ------------- |
| **Draft（草稿）** | 正在编写，未经评测 | PM可编辑 |
| **Testing（测试中）** | 正在跑评测集 | 只读 |
| **Staging（预发布）** | 评测通过，等待上线 | 只读 |
| **Production（生产中）** | 线上运行版本 | 只读，需走发布流程才能替换 |

**版本命名规范**：

```
格式：[Agent名称]-v[大版本].[小版本].[补丁版本]
示例：sales_agent-v2.3.1

大版本：Prompt结构性重写（角色/框架调整）
小版本：新增或删除约束条件
补丁版本：措辞调整、格式微调
```

**回滚机制**：

生产环境的Prompt必须随时可以一键回滚到上一个版本。原因：AI产品的上线不像传统功能那样"测完就稳了"，有时候用户真实行为触发的edge case在测试阶段根本没覆盖到，需要快速回滚止损。

#### 6.7.3 成本异常监控：AI产品独有的财务风险

**为什么成本会突然异常**：

传统SaaS的运营成本（服务器、带宽）是相对稳定的。但AI产品的Token成本是**按使用量实时计费的变动成本**，以下情况会导致成本暴涨：

- 某个用户发送了一个超长输入（大型企业的项目数据量远超预期）
- Multi-Agent系统的某个节点进入了无限重试循环
- 缓存机制失效，所有请求都走了LLM而不是缓存
- 上线了一个新功能，调用频次远超预估

**成本监控体系**：

```
指标层级一：实时监控（分钟级）
  → 当前小时的Token消耗速率
  → 单次请求的Token上限告警（超过阈值立即报警）
  → 异常高消耗用户/租户识别

指标层级二：日常监控（天级）
  → 日均Token消耗 vs 上周同期
  → 各Agent/功能的Token消耗分布
  → 单次平均成本趋势

指标层级三：成本归因分析（周级）
  → 哪些功能/用户贡献了最多成本？
  → 成本/收入比是否在健康范围？
  → 是否有优化空间（比如某类问题命中缓存率极低）
```

**成本保护机制设计**：

| 机制 | 实现方式 | 防护场景 |
| ------------- | ----------------- | -------------- |
| **单次Token上限** | 超过阈值自动截断Context | 超长输入导致单次成本暴涨 |
| **用户级日限额** | 每个用户每天最多消耗N个Token | 恶意或异常用户 |
| **租户级月限额** | 每个租户按套餐限制总量 | 超用引起成本超支 |
| **成本预警** | 日成本超过预算X%时自动通知 | 提前发现异常趋势 |
| **降级策略** | 达到限额时自动切换到小模型 | 保障服务可用性的同时控制成本 |

#### 6.7.4 数据隐私与合规：B端AI产品的生死线

**B端AI产品的特殊合规压力**：

C端产品的合规要求主要是"用户同意"，B端产品面对的是企业客户，合规压力要严苛得多：

- 客户合同里可能明确写了"数据不得传输至境外服务器"
- 金融、医疗、政府类客户有行业监管要求（等保二级/三级）
- 数据泄露不只是声誉损失，还可能涉及违约赔偿

**PII（个人身份信息）脱敏**：

AI功能处理的数据里可能包含PII（姓名、手机号、身份证、邮箱等）。在把数据发送给外部API之前，必须做脱敏处理：

```
脱敏策略：
  姓名：张三 → 张**
  手机：13812345678 → 138****5678
  身份证：110101199001011234 → 110101****1234
  邮箱：zhangsan@company.com → z***@company.com

注意：脱敏后的数据发送给LLM，LLM生成内容里不能反推出原始信息
→ 在Prompt里明确约束："不要还原或推测脱敏字段的原始值"
```

**数据不出境的架构选择**：

| 场景 | 推荐方案 | 说明 |
| --------- | --------------------- | ---------- |
| 客户数据敏感度中等 | 私有化API（如DeepSeek自部署版） | 数据在客户私有云处理 |
| 客户数据极度敏感 | 开源模型本地部署（Qwen/LLaMA） | 完全不依赖外部网络 |
| 客户数据敏感度低 | 商业API + 合同约束 | 最灵活，成本最低 |

**合规Checklist（B端AI产品上线前必查）**：

- [ ] 是否获得了用户对AI处理数据的明确同意？
- [ ] 是否有数据不出境的技术保障（私有化或合同约束）？
- [ ] AI生成的内容是否有来源标注和人工确认机制？
- [ ] 是否有完整的审计日志（谁在什么时间用AI处理了什么数据）？
- [ ] 是否有数据删除机制（客户要求删除时，AI记忆里的数据能清掉吗）？
- [ ] 是否评估过适用的行业监管要求（等保/GDPR/个保法）？

#### 6.7.5 AI产品运维仪表板：你需要监控什么

**区别于传统产品监控（CPU/内存/响应时间）**，AI产品还需要监控：

```
AI质量类指标：
  ├── Reflection通过率（质检指标）
  ├── 幻觉率（事实准确率抽样）
  ├── BadCase率（用户负反馈/人工标注）
  └── 各Agent错误率分布

成本类指标：
  ├── 单次平均Token消耗
  ├── 日/月总成本 vs 预算
  ├── 成本/收入比
  └── 各功能成本分布

效果类指标：
  ├── 草稿采纳率（生成后有没有被用）
  ├── 用户编辑量（改动越多说明质量越差）
  ├── 重新生成率（用户不满意的直接信号）
  └── 功能留存率（第N周还在用的用户比例）

系统类指标：
  ├── P50/P95延迟（首Token时间 + 完整生成时间）
  ├── 模型API可用性
  └── 缓存命中率
```

**核心原则**：AI产品的运维，本质上是在持续回答一个问题——**"今天的AI，比昨天的AI更好还是更差？"**——而这个问题只有通过持续的量化监控才能回答，靠感觉不行。

**Q3：如何设计一个Prompt来减少幻觉？**

1. 明确知识边界：要求模型只基于提供的信息回答
2. 要求引用来源：让模型标注信息出处
3. 分步验证：先列出事实，再检查矛盾
4. 设计兜底机制：不确定时明确说"不知道"
5. 人在回路：关键信息人工审核
```

#### 7.1.2 产品思维类

**Q4：你熟悉的B端产品中，哪个功能最适合引入AI？为什么？**

**参考回答框架**：

```
1. 选择具体功能（最好是你做过的）
2. 分析痛点：
   - 当前用户遇到什么困难？
   - 人工处理有什么局限？
3. AI方案：
   - 用AI解决什么问题？
   - 技术可行性如何？
4. 效果预期：
   - 效率提升多少？
   - 用户体验如何改善？
5. 风险控制：
   - 出错怎么办？
   - 如何评估效果？
```

**Q5：AI产品与传统产品有什么不同？**

**参考要点**：

```
1. 输出不确定性：传统产品输出确定，AI产品输出概率性
2. 评估方式：传统产品看功能是否实现，AI产品看效果是否达标
3. 迭代方式：传统产品迭代功能，AI产品迭代模型+Prompt
4. 用户教育：AI产品需要让用户理解能力边界
5. 伦理合规：AI产品需要考虑更多安全和合规问题
6. 成本结构：传统产品固定成本为主，AI产品变动成本（Token）为主
```

#### 7.1.3 项目经验类

**Q6：请介绍一个你做过的AI相关项目。**

**STAR法则**：

```
S（Situation）：背景
- 什么业务？什么场景？什么问题？

T（Task）：任务
- 你的职责是什么？目标是什么？

A（Action）：行动
- 你做了什么？
- 技术选型理由？
- Prompt怎么设计的？
- 遇到过什么困难？怎么解决的？

R（Result）：结果
- 量化结果（准确率提升XX%、效率提升XX倍）
- 用户反馈
- 你的收获
```
