## 10 分钟版（总监面 / 终面，约 1500 字）

> **（0-2 分钟）博卡的底色**
>
> "我先从博卡讲起吧，因为我觉得那段经历塑造了我做产品的底层思维。我在博卡做了将近 4 年，独立负责核心产品的 10 多个子系统。这个产品是一个美业连锁的 SaaS ERP+CRM，服务全国 10 万家门店。
>
> 我想讲三个我在这段经历里形成的能力，因为它们后来在做 AI 产品的时候全用上了。
>
> 第一个是需求判断力。我当时管着将近 800 条需求，来源有 6 个渠道——销售提的、客户直接找的、钉钉、微信、还有我自己走查发现的。我建立了一套三维度优先级打分体系——客户影响面乘以实现成本乘以战略价值。结果很有意思——销售催得最急的需求，按这套体系打分后排在 15 名开外，而排第一的功能影响 50 多家门店。把数据摊在评审会上，销售自己就不争了。在这 800 条需求里我作废了 100 多条——不是这些需求不合理，是不该做进标准版。定制功能在我的版本里只占 2%。保护产品方向不被稀释，这个判断力是练出来的。
>
> 第二个是复杂业务规则的产品化。美容美发行业的会员权益特别复杂——储值卡、疗程卡、抵用券、资格权益，每种权益的消费规则、退款规则、跨店结算规则都不一样。我把 12 个核心场景梳理出来，统一成一个财务模型。功能使用率从 15% 提升到 68%，客户投诉降了 45%。这件事让我学会一件事：复杂不是借口。越是复杂的业务，越需要一个简洁的产品模型。
>
> 第三个是安全和权限意识。博卡的产品要过大型连锁客户的 security review。我梳理了 23 个敏感模块的分级脱敏规则——财务数据、会员手机号、员工薪资——哪一级角色能看到什么、能不能导出、能不能修改。有一个权限参数叫 UR021，两年里经历了 4 次迭代——从改余额到改权益到改备注到改套餐——每次都是在不破坏已有规则的前提下扩展。这个'默认安全、逐层授权'的思维，后来在我做 AI 产品的时候直接帮我发现了 3 个数据泄露漏洞。
>
> **（2-3 分钟）转向 AI**
>
> "离开博卡后我做了两年金融方向，主要是补商业视角。然后从去年开始，我把精力聚焦在 AI 产品上。为什么选这个方向？因为我在博卡解决的问题——多角色权限、数据安全、复杂业务规则的产品化——这些在 AI 产品领域同样是刚需，而且做的人很少。现在的 AI 产品圈子里，大部分人是从技术切入的，懂 Prompt、懂 RAG、懂 Agent 编排，但不懂怎么把一个 AI 产品做到企业级——怎么让客户信任、怎么保证数据安全、怎么处理多租户。我觉得这是我的机会。"
>
> **（3-6 分钟）EIA V4 的核心决策**
>
> "我自己独立做了一个项目来验证这个想法，叫 Enterprise Insight Agent V4。它是一个面向连锁零售的 AI 经营分析平台。简单说就是——老板用中文问'华东区销售为什么下降'，系统 60 秒内给出一份带图表、带数据溯源、带可执行建议的诊断报告。
>
> 我想重点讲三个产品决策，因为它们能体现我做 AI 产品的思路。
>
> *第一个，为什么用 10 个 Agent 而不是 1 个。* 我做了实测——把 5 个领域的 Schema 塞进一个 System Prompt，加上工具调用往返、SQL 结果，单次上下文烧到 12000 token。我发现一个具体的问题：Finance Agent 的 SQL 算出退款率是 3.2%，但到了报告里被写成了 8.7%。我不确定是 SQL 错了还是 LLM 理解错了，所以我做了三个对照实验——先审计原始 SQL，确认 SQL 没错；然后把其他 Agent 的输出全部去掉，只给 Finance 数据，错误消失了；最后我做位置效应测试，把 Finance 数据从第三个位置移到第一个，准确率从 80% 提升到 95%。结论是：LLM 在长上下文后半段注意力衰减，把两个相似的数值搞混了。这个实验让我确信 Multi-Agent 是必要的——不是为了架构好看，是为了解决真实的数据准确性问题。
>
> *第二个，评估体系是怎么演化的。* Reflection Agent 的 4 个质检维度，不是我一开始就设计好的。初始只有 2 个——数据一致性和问题覆盖完整性。后来跑了离线评估集，发现了两个 BadCase。一个是报告把'退款率上升'和'供应商准时率下降'并列，暗示因果关系——但实际上退款率上升是促销引流来的新用户退货率高，跟供应商毫无关系。这催生了'逻辑严谨性'维度。另一个 BadCase 是报告给的建议是'提升门店运营效率'——说了等于没说。这催生了'建议可操作性'维度，要求建议必须包含谁、做什么、预期效果。所以这个评估体系不是设计出来的，是从失败案例里长出来的。
>
> *第三个，我实际发现了三个安全漏洞。* 最严重的一个：我用 zhangsan 账号登录——他是华东区域经理，理论上只能看到华东 22 家门店的数据。但我发现他能看到全部门店的数据。我不是靠跑测试发现的，是逐行读代码发现的。`inject_store_filter` 函数第 68 行——当 store_ids 为空列表时，函数直接返回原始 SQL，不加任何 WHERE 过滤。这背后的产品思维——默认拒绝、显示授权——是我在博卡做了 4 年权限体系后形成的肌肉记忆。"
>
> **（6-8 分钟）方法论沉淀**
>
> "做完 V4 后我做了一件事——不是继续加功能，而是把整个过程沉淀下来。我写了 13 条关键产品决策记录，每条都记录了'当时考虑了哪些方案、为什么选这个、如果重来一次还会不会这么选'。我提炼了 7 条 AI 产品设计原则——够好就行不追求最优、灰度开关可进可退、输出自适应不做信息过载、数据诚实禁止编造、防御性设计默认拒绝、BadCase 驱动迭代不靠直觉、AI 的边界在哪用户需要知道。每一条原则后面都有一个具体的决策或 BadCase 作为来源。我还做了 3 次完整的 BadCase 闭环复盘，每一次都包含了问题发现、诊断过程、实验验证、修复方案、教训沉淀。
>
> 我在乎的不是 EIA V4 做了多少功能、用了多少 Agent。我在乎的是——如果下一次做一个全新的 AI 产品，我能不能更快地做出正确判断。这些方法论就是我的答案。"
>
> **（8-10 分钟）为什么匹配**
>
> "回到为什么我觉得自己适合这个岗位。我的判断是，目前 AI 产品领域有两个阶段的人——第一阶段的人在研究怎么写好 Prompt、怎么搭好 RAG、怎么做出 Demo；第二阶段的人在研究怎么评估 AI 输出的质量、怎么在企业级场景下管理 AI 的风险、怎么让 AI 产品的迭代不靠直觉而靠体系。我在博卡的 4 年让我天然具备了第二阶段需要的一些底层能力——权限、安全、多租户、复杂业务规则。而 EIA V4 让我把这些能力在 AI 场景下验证了一遍。我不是转型做 AI，我是把已有的产品功底应用到 AI 这个新领域。"
>
> "谢谢，以上就是我的自我介绍。"

# 第三章：核心回答公式

## 产品决策回答公式

```
业务问题
    ↓
我考虑了方案 A 和方案 B
    ↓
A 的好处/代价，B 的好处/代价
    ↓
我为什么选了 B（不是"B 更好"，是"在 XX 约束下 B 更合适"）
    ↓
实验验证
    ↓
结果
    ↓
如果重来一次会不会还这么选
```

## 绝对避免的回答模式

```
技术选型 → 技术实现 → 技术结果  ❌
```

每个技术名词后面必须跟一个产品理由。

# 第四章：EIA V4 项目全景

## 产品定位

经营分析从「导出 Excel → 手工分析 → 写报告（半天）」变为「自然语言提问 → AI 分析 → 报告输出（60 秒）」

## 核心数据

| 指标 | 数值 |
|------|------|
| Agent 节点 | 11（Supervisor + 5 领域 + Aggregator + Chart Advisor + Report + Reflection + Memory） |
| 业务域 | 5（销售/会员/财务/库存/供应链） |
| Demo 数据 | 100 门店 / 50,925 订单 / 5,000 会员 |
| API 端点 | 36 个 |
| 测试 | 155 条 |

# 第五章：13 个关键产品决策案例

### 决策 1：放弃单 Agent，选择 Multi-Agent ★ 必讲

**背景**：5 个领域 Schema 超 3000 token，单次分析烧到 12000 token

**方案 A**：单 Agent + Function Calling——一个 LLM 持有全部 Schema，自己决定调用哪些工具

**方案 B**：Multi-Agent——Supervisor 路由 + 5 领域 Agent 并行

**为什么选 B**：三个具体原因——①上下文竞争：长上下文后半段注意力衰减，退款率 3.2% 被错误引用为 8.7%，三个对照实验验证根因（审计 SQL→隔离上下文→位置效应测试）②故障隔离：CRM 挂了不污染 Sales/Finance ③迭代效率：Sales Prompt 迭代 7 版、CRM 只改 2 版，独立 Prompt 改一个不需重测全部

**如果重来**：高频查数据型用单 Agent（降延迟），跨领域分析型用 Multi-Agent（保准确率），Supervisor 自动判断

---

### 决策 2：Reflection 最多重试 1 次 ★ 必讲

| 重试 | 修复率 | 额外 Token | 判断 |
|------|:-----:|-----------|------|
| 0 次 | — | 0 | 25% 报告有问题，不可接受 |
| 1 次 | ~60% | 3000-5000 | **最优** |
| 2 次 | ~75% | 6000-10000 | 边际递减 |
| 3 次 | <80% | 9000-15000 | 越改越差 |

**核心判断**：超过 1 次未通过通常是底层数据矛盾，不是报告写得不好。应让用户看到带未通过标记的报告，而非无限循环

---

### 决策 3：流式优先于缓存

**背景**：V3 的分析流程是先调非流式端点（查 Redis 缓存，命中秒返），未命中再降级为流式。这意味着首次查询时用户盯着静态进度条等 60-90 秒

**方案 A**：缓存优先——先查 Redis，命中秒返，未命中走流式（V3 方式）

**方案 B**：流式优先——直接走 SSE 流式，首个 token 到达时并行检查缓存（V4 方式）

**为什么选 B**：
1. 95%+ 查询是新问题，缓存命中率极低——"缓存优先"的优势在实际使用中几乎不存在
2. 用户对"看流式进度条"的容忍度远高于"看静态进度条等 60 秒"——这是用户体验的质变，不是量变
3. 缓存返回和首 token 的时间差实测只有 2-3 秒——用户感知不到

**代价**：缓存命中场景多等一个 token 的延迟；流式和缓存是两套链路，流式挂了没有降级路径

**如果重来**：统一为同一个端点，根据 Accept 头自动切换流式/非流式，加超时降级

**面试金句**："不是技术升级，是用户等待体验的重新设计。静态进度条是'等待'，流式进度是'进展'——两个心理状态完全不同。"

---

### 决策 4：Schema 三层适配器

**背景**：每家零售企业的数据库表名和列名不一样——有的叫 `orders`，有的叫 `t_sales_order`，有的叫 `sale_record`。如果不解决适配问题，每次部署都需要改代码。

**方案 A**：让客户技术人员直接改代码里的 SQL 模板

**方案 B**：三层适配器——① Schema 自动发现（系统自动扫描 `information_schema`）② YAML 语义映射（客户技术人员一次性标注：哪张表是订单、哪张表是会员）③ Prompt 动态生成（根据映射自动替换表名和列名）

**为什么选 B**：A 需要客户技术人员懂 Python + SQLAlchemy + 我们的 Prompt 模板——门槛太高。而且每次版本升级，客户改过的代码会和我们的更新冲突。B 只有第二层需要人工介入，而且只需做一次——YAML 不是代码，不会跟版本升级冲突。

**商业逻辑**：年费 3-5 万的定价下，派实施工程师驻场的成本会让毛利率变负。"零驻场部署"不是产品亮点，是商业模式的必要条件。

**如果重来**：加一个"Schema 健康检查"——在映射阶段就检测客户数据库是否符合预期（比如必需的表是否存在、列类型是否兼容），避免上线后才发现不兼容。

**面试金句**："这个设计的出发点不是技术优雅，是成本结构。技术架构跟着商业模式走，不是反过来的。"

---

### 决策 5：双模式输出

**背景**：管理者晨会看数据追求效率（"昨天销售 Top 3 是谁"），周会做决策需要信息深度（"为什么 B 店客单价连续下滑"）。用同一套输出格式同时满足两种场景，要么信息过载，要么信息不够。

**方案 A**：统一输出完整报告（含数据概览、根因诊断、建议）——适合分析型，但查询型用户觉得啰嗦

**方案 B**：统一输出简洁数据表格——适合查询型，但分析型用户觉得肤浅

**方案 C**：双模式——Supervisor 先判断问题类型，查询型只输出表格 + 简短总结，分析型输出含根因和可执行建议的完整报告

**为什么选 C**：输出格式应该匹配用户场景，而不是匹配 AI 的能力。这个判断来自对用户场景的分析——不是"AI 能输出什么"，而是"用户在这个场景下需要什么"。

**验证**：查询型问题（"Top 3 门店"）输出约 400 token，分析型（"华东区下降原因"）输出 2000-4000 token。如果反过来——查询型输出 2000 token 报告——用户会觉得"AI 在废话"。

**面试金句**："单一输出格式无法同时满足两种场景。产品经理的工作不是选择 A 或 B，是定义什么时候用 A、什么时候用 B。"

---

### 决策 6：经营看板作为登录首页

**背景**：V3 登录后直接进入聊天页——一个空白输入框。新用户面对这个界面不知道能问什么，也不知道系统能做什么。这叫"冷启动焦虑"——产品提供了能力，但用户不知道能力边界在哪。

**方案 A**：保持登录后进聊天页（V3 方式）

**方案 B**：登录后默认进经营看板页——6 个 KPI 卡片、趋势折线图、区域占比环形图、门店 Top 10 排名

**为什么选 B**：看板解决了三个问题——①告诉用户"系统能告诉你什么"（降低认知门槛）②给用户一个"我能继续深入问什么"的提示（从看到的数据自然延伸出问题）③让用户第一次登录就有"这个产品挺专业"的印象（体验锚点）。这不是功能升级，是用户激活路径的重新设计。

**验证**：看板页的 KPI 都带环比箭头——今日销售额 vs 昨日，绿色上升红色下降。这个细节让静态数字变成了"可判断的信息"。

**面试金句**："用户面对空白输入框不知道能做什么。看板把'我该问什么'变成了'我看到了什么，我想深入问什么'。"

---

### 决策 7：欢迎页动画

**背景**：用户打开产品第一眼看到什么，直接影响对产品的专业度判断。直接弹登录框像内部工具，有一个欢迎页像产品。

**方案 A**：保持直接显示登录弹窗

**方案 B**：加一个深色背景 + 网格动画 + 浮动粒子 + 渐变标题 + CTA 按钮的欢迎页（200 行 CSS + 50 行 JS）

**为什么选 B**：成本极低（从已有的 intro.html 复制过来），但提供的是一个"专业产品"的体验锚点。ROI 最低的功能——没有它产品照样用，但有了它产品给人的第一印象完全不同。

**明确边界**：这是个人项目的"包装层"，在企业产品中优先级会排后。但成本够低的时候，做比不做好。

**面试金句**："这个功能是 ROI 最低的——但成本也最低。200 行 CSS 换来一个'专业产品'的第一印象，值得。"

---

### 决策 8：取消分析按钮

**背景**：流式分析可能耗时 60-90 秒，用户在等待中可能改变主意或发现输入错误。没有取消功能意味着用户只能干等。

**方案 A**：不加取消——分析开始后必须等结束

**方案 B**：加红色取消按钮——分析进行中，提交按钮变为红色"取消"，点击后 `AbortController.abort()` 中止 SSE 流

**为什么选 B**：实现成本极低（约 20 行 JS），但对用户体验的提升显著——用户有了控制权，即使不用也会因为"有这个选项"而感到更安心。这是"感知可控性"的产品设计。

**边界处理**：取消后保留已接收的部分 token 内容 + "已取消"提示。不删除流式气泡——用户已经看到的东西不该消失。

**面试金句**："实现成本只是 20 行代码，但给用户的'可控感'是无价的。'取消'按钮的价值不只在于被点击，还在于'它存在'。"

---

### 决策 9：角色快捷问题

**背景**：V3 的快捷问题是硬编码的 6 个固定问题（"各门店销售额排名""近 30 天销售趋势"等），不管什么角色看到的一样。但店长关心的是自己的店，区域经理关心的是自己的区域。

**方案 A**：保持固定问题

**方案 B**：根据角色动态展示——admin 看"各区域经营对比""供应商准时率排名"，zhangsan（华东经理）看"我负责区域的销售趋势""区域门店排名"，lisi（店长）看"我们店昨日概况""本店会员消费排行"

**为什么选 B**：实现成本极低（约 10 行 JS，三套问题数组），但体现的产品深度远超成本。"同一产品，不同角色看到的内容不同"——这个洞察本身就是行级安全思维在 UI 层的延伸。

**面试金句**："店长和区域经理打开同一个产品，看到的推荐问题不同。区区 10 行代码，但让产品从"我做了功能"升级到"我理解用户"。"

### 决策 10：会话持久化

**背景**：JWT token 存在 JS 变量里，用户刷新页面就丢了——等于自动退出登录。这是所有 SPA 都会遇到的基础体验问题。

**方案 A**：不做处理——刷新即退出，用户重新登录

**方案 B**：token 存 localStorage，刷新时自动恢复了会话。验证方式：页面加载时读取 localStorage → 用 `/dashboard/today-summary` 轻量 API 验证 token 是否过期 → 有效则跳过登录直接进看板页

**为什么选 B**：这不是"锦上添花"——是"不做的代价是灾难"。用户刷新页面后发现退出登录，会认为产品有 bug。而且 localStorage 方案在安全性和便捷性之间找到了平衡——token 只在本地存储，退出登录时清除并调用服务端黑名单注销。

**如果重来**：改用 httpOnly cookie（防 XSS 窃取），但需要后端配合修改。当前方案对 Demo 阶段足够。

**面试金句**："不是'做了更好'——是不做的代价太大。用户刷新就退出，那是产品的信任失败。"

---

### 决策 11：PDF 导出 + 降级

**背景**：用户希望把分析报告导出为 PDF 发给老板或存档。后端用 WeasyPrint 渲染 PDF，但 WeasyPrint 需要 GTK 系统库——Windows 上安装很复杂，Linux Docker 里 OK。

**方案 A**：只支持 WeasyPrint——安装不了就不提供 PDF

**方案 B**：WeasyPrint 优先，失败时自动降级为 Markdown 下载

**为什么选 B**：用户的目标是"拿到报告"，PDF 是最佳格式但 Markdown 是可接受的替代。降级不是失败，是用户体验的保障——比"导不出来"好一万倍。前端按钮逻辑：调后端 API → 200 则下载 PDF → 非 200 则 toast"PDF 服务不可用，已降级为 Markdown 下载"并自动下载 .md。

**面试金句**："用户的目标是'拿到报告'，PDF 是最好的格式但 Markdown 是可接受的替代。降级不是失败——是用户体验的保障。"

---

### 决策 12：Prompt YAML 外部化 + 热重载

**背景**：Prompt 写在 Python 代码里，每次修改需要重启服务。在迭代 Prompt 的初期，这是致命的——改了 2 个字要等 30 秒重启，一天改 20 次就是 10 分钟浪费在启动上。

**方案 A**：Prompt 留在 Python 硬编码里

**方案 B**：Prompt 移到 YAML 文件，三级 fallback：客户定制（`customer_schema.yaml`）→ YAML 外部化（`prompts/yaml/*.yaml`）→ Python 硬编码（兜底）。YAML 支持热重载（`/api/v1/prompts/reload`），改完即刻生效

**为什么选 B**：YAML 分离后，Prompt 的迭代效率提升了几个数量级。改一个字、加一条规则都不需要重启。三级 fallback 的设计逻辑：客户定制是第一优先级（不同客户的字段名不同）、YAML 是默认配置、Python 硬编码是兜底（确保即使 YAML 文件损坏，系统也不崩溃）。

**如果重来**：加 Prompt 效果监控——每次热重载后自动跑评估集，对比准确率变化，发现问题自动回滚到上一版本。

**面试金句**："改两个字等 30 秒重启，一天改 20 次就是 10 分钟。热重载不是为了技术优雅，是为了迭代效率。"

### 决策 13：三层评估体系

**背景**：AI 产品的质量怎么衡量？不能用传统软件的"功能测试"方式——同一个问题两次回答可能不同，同一个答案不同用户可能一个觉得准确一个觉得不行。

**方案**：不是单一指标，是三层体系——

**第一层：离线评估集**。20 条标准问题（覆盖查询型和分析型），每条有预期输出格式和关键数据点。每次改 Prompt 后跑一遍，对比准确率变化。局限：基于 demo 数据，真实客户数据会暴露边界

**第二层：Reflection Agent 在线质检**。每次分析完成后自动运行，从 4 个维度审核。不是"替代人工"，是"降低人工抽检的频率"。重试上限 1 次——超过 1 次未通过通常不是报告写得不好，是底层数据有问题

**第三层：用户反馈闭环**。每条报告底部有 👍👎 按钮，用户反馈写入 `user_feedback` 表。如果某类问题点踩率持续偏高 → 检查对应 Agent 的 Prompt → 更新 → 离线评估集复测 → 上线

**为什么这样设计**：单一评估方式在 AI 产品中不够——离线评估能测"标准情况"，但在线质检能捕获"长尾异常"，用户反馈能反映"真实满意度"。三层互补，每层覆盖另一层的盲区。

**当前局限**：离线评估集只有 20 条，覆盖不了所有边界。Reflection 本身也是 AI，会有误判。用户反馈样本量为 0（demo 阶段无真实用户）。但体系框架已经建立——数据进来后框架自动运转。

**面试金句**："AI 质量不是'测出来的'，是'体系化管出来的'。三层评估就是这套管理体系。"

### 决策 14：为什么用 n8n 做定时调度而不是自己写 cron

**背景**：V4 需要两个定时任务——每 8 小时检测经营异常、每周一早 9 点生成周报。最简单的方案是 Python APScheduler 几行代码解决。为什么引入了 n8n 这个额外服务？

**方案 A**：V4 内部用 APScheduler 定时执行
**方案 B**：用 n8n 做定时调度，通过 HTTP 调 V4 的 API

**为什么选 B**——三个非功能需求：

1. **运维可视化**：n8n 自带执行历史、失败重试、手动触发面板。如果自己写 cron，这些需要额外搭一套监控——对于 5 容器的部署规模来说性价比太低。

2. **扩展性**：现在只有 2 个工作流。但未来如果客户想自定义触发条件——比如"退款率 > 15% 时立即通知"——n8n 里加一个 Webhook 节点就能搞定，不用改 V4 代码。定时逻辑和业务逻辑解耦。

3. **非技术人员友好**：如果未来客户的运营人员想自己调整告警频率（比如从 8 小时改成 4 小时），n8n 的 UI 比改代码门槛低得多。这是在为"客户自助配置"留接口。

**代价**：多了一个 Docker 容器；n8n 的 Environment Variables 功能是企业版付费的，免费版只能把密钥硬编码在工作流 JSON 里——生产环境下需要用 n8n Credential 或者切回自己的 cron 方案。

**如果重来**：小规模部署（< 5 个定时任务）继续用 n8n。如果定时任务数量超过 20 个或者需要严格的 SLA 保障，切回 APScheduler + Prometheus 监控。

**面试金句**："n8n 在我的架构里确实只做了定时调度。但选它不是因为'需要工作流引擎'——是因为'运维可视化 + 扩展性 + 非技术人员友好'三个非功能需求。知道一个工具解决了什么非功能问题，比知道用了什么工具更重要。"

**面试官追问"n8n 免费版限制你怎么解决的"**：
> "密钥硬编码在 JSON 里——测试环境可以，生产环境不可接受。下一步要么买 n8n 企业版，要么把定时任务迁回 V4 内部的 APScheduler。这个决策还没做，取决于客户对'自助配置告警规则'的需求有多强。如果客户不需要自助配置，n8n 就是过度设计，我会砍掉它。"

# 第六章：3 个 BadCase 完整复盘

### BadCase 1：退款率数据张冠李戴（注意力衰减）

**问题**：Finance SQL 算出退款率 3.2%，报告写成 8.7%

**诊断三步**：①审计原始 SQL→3.2%，SQL 没错 ②隔离上下文只给 Finance 数据→准确 ③位置效应测试：Finance 移到最前面→准确率 80%→95%

**根因**：三个 Agent 输出超 6000 token，LLM 后段注意力衰减，相似数值混淆

**修复**：数字加单位标签（"退款率：3.2%"），Reflection 新增数据一致性维度

**教训 → 原则**：关键数字永远带标签，不裸传

---

### BadCase 2：虚假因果推断（逻辑跳跃）

**问题**：Report 将"退款率上升"与"供应商准时率下降"暗示为因果

**诊断**：退款率上升集中在促销期——是促销引流新用户退货率高，跟供应商无任何关系

**修复**：Reflection 新增"逻辑严谨性"维度，专项检查虚假关联

**教训 → 原则**：AI 应该报告事实，不应该编故事。催生了双模式输出——查询型不给 AI 编故事的机会

### BadCase 3：行级安全数据泄露（空列表不过滤）★ 必讲

**问题**：zhangsan 华东经理能看到全部门店数据

**诊断**：不是测试发现的——读代码发现的。`inject_store_filter`：`if not store_ids: return sql`——空列表不设防。第二个 bug：`get_user_store_ids` 无记录时返回 `None`（全量）

**修复**：空列表注入 `WHERE 1=0`；无记录返回 `[]`（默认拒绝）

**教训 → 原则**：默认拒绝，显示授权。来自博卡时期 23 个敏感模块分级脱敏规则的经验迁移

# 第七章：AI 产品经理高频 Q&A（50 题）

## AI 基础

**Q：什么是 LLM？如何选模型？**
基于 Transformer 的大规模语言模型，通过预测下一个 token 生成文本。选模型看三角：成本/延迟/质量。V4 用 DeepSeek-Chat——中文好、便宜（¥1/百万 token 输入）、支持 Function Calling。路由决策用 temperature=0 保一致，报告生成用默认 temperature。

**Q：什么是 Token？什么是上下文窗口？**
Token 是 LLM 处理的最小文本单元，中英文不等长。上下文窗口是 LLM 一次能处理的最大 token 数。V4 用 DeepSeek 64K。实际中 5 个领域 Schema + 工具调用往返 + SQL 结果单次约 12000 token——离上限很远，但长上下文后半段注意力衰减是真实问题（见 BadCase 1）。

**Q：什么是幻觉？怎么降低？**
LLM 生成看似合理但不符合事实的内容。V4 用四层防御：①SQL 溯源面板（每条结论可追溯原始查询）②Reflection 四维质检 ③Prompt 约束（"不要编造数据，只根据实际查询结果分析"）④前端信任分级（✅数据层/⚠️分析层/💡建议层）。诚实地说——做不到 100% 消除，但可以把它约束到"用户可判断"的程度。

**Q：什么是 RAG？什么是 Embedding？**
RAG = 检索增强生成——先从知识库检索相关内容，再注入 LLM Context 生成答案。Embedding 将文本转为固定维度向量，用于语义搜索。V4 用 BGE-M3（1024 维），跑在本地 Ollama 上——零 API 成本。但不是通用 RAG——是"客户数据库 Schema 适配 + 历史相似 SQL 检索"的垂直场景。

**Q：Agent 和 Workflow 的区别是什么？什么时候用 Agent，什么时候不用？**
Agent 自主决策下一步（路径不确定），Workflow 固定步骤（路径确定）。用 Agent：复杂任务需要根据中间结果调整策略，如"华东区销售下降"需要 Supervisor 先判断激活哪些 Agent。不用 Agent：简单数据查询（单 SQL 即回答）、确定性规则（用传统 if-else）。V4 Supervisor 的双重设计——先尝试 Agent 路由，失败兜底全激活——就是这个权衡的体现。

**Q：什么是 Function Calling？什么是工具调用？**
Function Calling 是 LLM 以结构化 JSON 输出，指定要调用的函数和参数。工具调用是 Agent 通过 API 调用外部工具。V4 每个 Agent 有两个工具：`get_table_schema`（获取表结构）和 `run_sql`（执行查询，自动注入 store_ids 行级过滤）。工具闭包在 Agent 创建时注入权限上下文——安全是设计出来的，不是后来加的。

**Q：什么是 MCP？什么是 A2A？**
MCP = Model Context Protocol，AI 与外部工具/数据源的标准通信协议。A2A = Agent-to-Agent，多 Agent 协作协议。V4 用 LangGraph 的 Send 机制实现 Agent 间通信——Supervisor 通过 `activated_agents` 列表告诉框架激活哪些 Agent，并行结果通过 StateGraph 的归约器自动合并。没直接用 MCP/A2A 因为它们还在快速演进中——LangGraph 的抽象层给了我们切换的灵活性。

## AI 产品设计

**Q：如何设计一个 Agent？**
先定义边界（一个领域一个 Agent），再定义输入输出 Schema，最后设计工具。V4 的做法：①从业务领域拆分（销售/会员/财务/库存/供应链）②每个 Agent 有独立 System Prompt + SQL 工具 ③工具闭包注入权限上下文（store_ids）④独立的故障处理（异常返回 agent_errors，不污染其他 Agent）。决策记录：为什么是 5 个领域而不是 3 个或 7 个——3 个覆盖不全（会员和库存缺位），7 个太细（供应链和采购重叠），5 个是实际测试后收敛的。

**Q：如何设计 RAG 和知识库？**
三层架构：标准 SOP 层（低频更新）+ 经验层（FAQ/案例，定期更新）+ 实时数据层（订单/库存，实时接口）。放弃纯向量检索——专业术语（如"疗程账户""储值权益折算"）在通用 Embedding 下语义不稳定，BM25 精确关键词匹配更可靠。规则兜底保障底线准确率。V4 的"知识库"本质是客户数据库 Schema + 历史相似 SQL 检索——不是通用文档问答，是垂类数据查询。

**Q：如何设计评估体系？**
三层：离线评估集（20 条标准问题）→ Reflection 在线质检（4 维度）→ 👍👎 用户反馈。不是一次性设计的——从 2 个预定义维度（一致性、完整性）起步，通过 2 个 BadCase 追加 2 个维度（逻辑严谨性、建议可操作性）。核心方法论：发现一个问题 → 抽象为评估维度 → 上线验证 → 纳入质检体系。目前最大局限：20 条评估集基于 demo 数据，真实客户数据会暴露边界。

**Q：如何设计提示词？怎么管理 Prompt 版本？**
三级 fallback 体系：客户定制 > YAML 外部化 > Python 硬编码。YAML 支持热重载（`/api/v1/prompts/reload`），改 Prompt 不用重启服务。每个 Agent 的 Prompt 独立管理——Sales 改 7 版不需要重测 CRM。目前局限：版本管理只有静态 `1.0.0` 版本号 + CHANGELOG.md，没有自动 A/B 对比和效果监控。下一步需要 Prompt 效果 dashboard（对比不同版本在评估集上的准确率变化）。

**Q：如何控制成本？**
四层成本控制：①流式优先——单次分析从 2 次 LLM 调用压缩到 1 次（成本减半）②Reflection 重试上限 1 次——避免无限循环烧 token ③Redis 缓存——同问题 5 分钟内秒返 ④CostTracker——每个请求记录 token 消耗和成本，可追溯。典型分析约 26,650 token（¥0.037），复杂分析约 122,950 token（¥0.19）。不是"最便宜"，是"在保证质量的前提下控制成本"。

**Q：如何做权限设计？为什么 AI 产品的权限更重要？**
AI 产品的权限设计有两个维度传统 SaaS 没有的：①LLM 可以"编造"数据绕过权限检查——如果 Prompt 里写了"你是管理员可以看到所有数据"，LLM 可能真的相信 ②SQL 注入过滤——Agent 自己生成的 SQL 不能信任，需要白名单审查 + 行数上限 + 权限注入。V4 的做法：SQL 注入层（`inject_store_filter` 自动在 WHERE 注入）+ Prompt 注入层（System Prompt 追加"你只能查询 XX 门店的数据"）。双重过滤——即使 LLM 忽视了 Prompt 限制，SQL 层也会强制过滤。

**Q：如何做需求优先级？AI 产品的需求优先级跟传统产品有什么不同？**
传统产品：客户影响面 × 实现成本 × 战略价值。AI 产品多加一维度——"不确定性的可控程度"。有些需求本身很有价值，但 LLM 在这个场景下的输出质量太不稳定，优先级反而要排后。V4 的例子：库存预测 Agent 没做，不是因为不重要，是因为 LLM 做数值预测的准确率不够——应该用传统 ML 模型而非 LLM。判断一个场景适不适合 LLM，比判断它重不重要更重要。

## Agent 专题

**Q：为什么选择 Multi-Agent 而不是单 Agent + Function Calling？**
三个具体原因，不是架构偏好：①上下文窗口竞争——5 个领域 Schema 超 3000 token，长上下文后半段注意力衰减（做了三个对照实验验证）②故障隔离——CRM 挂不污染 Sales/Finance ③迭代效率——独立 Prompt 改一个不需重测全部。详见决策 1。

**Q：Supervisor 的作用是什么？如果 Supervisor 判错了怎么办？**
Supervisor 负责规划路由——根据用户问题决定激活哪些 Agent。用 LLM + 关键词兜底 + temperature=0 确保路由一致。如果 LLM 调用失败——兜底激活全部 5 个 Agent（宁可多查，不可漏查）。如果路由误判（该激活的没激活）——用户反馈 + 后续迭代 Prompt。目前最准确的场景是"单一领域查询"（如"退款率最高的门店"→ 只激活 Finance），最不准确的场景是"模糊的综合问题"（如"经营情况怎么样"→ 全激活）。

**Q：Reflection 的 4 个维度怎么来的？为什么选这 4 个？**
2 个预定义（一致性、完整性）+ 2 个 BadCase 驱动（逻辑严谨性、建议可操作性）。见 BadCase 1 和 2 的完整复盘。

**Q：Aggregator 的设计逻辑是什么？**
纯 Python 代码聚合，不消耗 Token。只合并有实际输出的 Agent——如果 CRM 返回 None（挂了），跳过不编造。设计决策：不在 Aggregator 层做任何 LLM 推理——推理留给 Report Agent。Aggregator 的职责只有一个：把并行结果拼起来，不丢失信息。

**Q：Agent 如何评估、扩展、治理和监控？**
评估：离线评估集 + Reflection 在线质检 + 用户反馈。扩展：新增 Agent 只需加一个节点函数 + 注册到 StateGraph，不影响现有 Agent。治理：8 个 Feature Flag 独立控制每个功能的开关；Prompt 热重载支持快速修正。监控：CostTracker 记录每个 Agent 的 token 消耗；APM Tracer 记录节点执行耗时 + trace_id 全链路追踪。

## 企业级 AI

**Q：多租户怎么设计？RBAC 和 RLS 有什么区别？**
多租户通过 `tenant_id` 列隔离（非 Database-per-tenant——初期规模不需要）。RBAC 是角色级权限（谁能做什么操作），RLS 是行级安全（用户能看到哪些数据行）。V4 的 RBAC 五级（总部/大区/区域/门店/员工），RLS 通过 SQL 注入 + Prompt 注入双重过滤。

**Q：数据隔离怎么保证？缓存策略怎么设计？**
数据隔离三层：①SQL 注入 `store_id IN (...)` ②Prompt 注入限制描述 ③缓存键包含 user_id + tenant_id + store_ids，防止跨用户缓存污染。缓存策略：Redis 5 分钟 TTL——不是越长越好，经营数据有实效性。Dashboard 缓存键区分 `None`（全量）vs `[]`（无权限）vs 具体列表，防止碰撞导致数据泄露。

**Q：你发现的安全漏洞中最严重的是哪个？**
行级安全数据泄露（BadCase 3）。zhangsan 华东区域经理能看到全部门店数据——根因是 `inject_store_filter` 空列表时不过滤 + `get_user_store_ids` 无记录时返回 None。修复后：默认拒绝，显示授权。这个漏洞的严重性在于它可以让一个店长看到竞争对手门店的数据——在连锁零售行业这是商业机密级别的泄露。

**Q：如果客户要求部署在他们自己的服务器上，怎么保证安全？**
私有化部署方案：Docker Compose 5 容器，支持 Docker Secrets（不暴露密码明文）。客户数据库和系统数据库分离——Agent 通过 `customer_schema.yaml` 连接客户数据库，系统元数据存在独立的 PostgreSQL 中。审计日志 180 天保留（用户/IP/操作/耗时）。已知局限：算法备案未实施，PII 数据遮蔽未做——这是合规底线，V5 优先级。

**Q：SQL 安全怎么做？如何防止 Agent 执行危险操作？**
三重防护：①SQL 白名单——禁止 DDL/DML（DROP/DELETE/UPDATE/INSERT），只允许 SELECT ②字符串剥离——移除注释符（`--`/`/*`）防止绕过白名单 ③行数上限 1000 + 结果截断。Agent 的 `run_sql` 工具不是直接执行用户输入——是执行 LLM 生成的 SQL，但过滤逻辑对两者同样适用。

## 商业化与战略

**Q：这个产品的目标客户是谁？TAM 多大？**
国内连锁零售企业，年营收 1-50 亿的中型连锁。国内连锁零售百强年营收超 2 万亿，假设 1% 企业愿意付费，每家 3-20 万/年，TAM 在 10-50 亿。短期：先拿 5 个免费客户验证 PMF。定价：SaaS 订阅制，基础版 3 万/年（5 用户），专业版 10 万/年（20 用户）。比传统 BI（帆软 50 万起步）便宜，比通用 AI（ChatGPT Plus $20/月）贵——反映了垂直 AI 的真实价值。

**Q：如果竞品用 LangChain 做了类似的东西，你的护城河是什么？**
三层：①客户 Schema 适配——每家零售企业数据库结构不同，自动发现 + YAML 映射 + Prompt 动态生成不是通用方案能覆盖的 ②垂直 Prompt 工程——18 个 Prompt 是几十次实际测试迭代出来的，经验抄不走 ③客户关系——私有化部署后数据在你这里跑 6 个月，迁移成本极高。技术栈不是护城河——LangGraph/FastAPI/ECharts 都是开源的。

**Q：这个产品最大风险是什么？**
模型依赖单一供应商（DeepSeek）——如果涨价或服务中断，产品直接停摆。V5 路线图第一条：LLM Provider 抽象层。第二是数据安全——客户上传数据时的 PII 遮蔽还没做，这是合规底线。第三是没有真实客户验证——目前只有 demo 数据，不知道真实客户的问法和数据结构会暴露什么边界。

**Q：如果给你 3 个月和一个工程师，你会做什么？**
不做新功能。找 1-2 家真实企业做 POC，验证评估体系在真实数据下是否依然有效。同时：①LLM Provider 抽象层（降低供应商风险）②PII 数据遮蔽（合规底线）。关键原则：先验证 PMF，再补功能。这是"做产品"和"做工程"的优先级判断。

**Q：你怎么定义这个产品的成功？**
短期：有 3 个客户愿意付费续约（验证 PMF）。中期：客户每周至少用 3 次（验证使用频率），分析准确率 > 85%（验证质量）。长期：产品能独立养活一个 5 人团队。但诚实地——目前没有真实客户数据，这些指标还需要验证。

**Q：为什么从 B 端 SaaS 转型做 AI？**
不是转型，是自然延伸。博卡 4 年解决的核心问题——多角色权限、数据安全、复杂业务规则产品化——这些底层能力在 AI 产品里同样需要，而且更稀缺。AI 领域不缺会调 Prompt 的人，缺懂多租户隔离、审计日志、行级安全的人。我的定位不是"转型做 AI"，是"把 B 端产品功底应用到 AI 产品落地"。

**Q：n8n 在你的系统里做什么？为什么不用 cron？**
当前阶段 n8n 只做定时调度——每 8 小时触发告警检测、每周一触发周报生成。功能上几行 Python APScheduler 就能替代。但我选 n8n 有三个非功能需求：①运维可视化（执行历史、失败重试、手动触发——省一套监控面板）②扩展性（未来客户自定义触发条件只需加节点，不碰 V4 代码）③非技术人员友好（运营想改告警频率，n8n UI 比改代码门槛低）。代价：多一个 Docker 容器，免费版 Environment Variables 功能不可用需硬编码密钥。如果未来客户不需要自助配置，我会砍掉 n8n 迁回 APScheduler。

**Q：飞书/钉钉/企微通知是怎么接的？**
两层架构：n8n 定时调 V4 的 `/alerts/check`，检测到异常后 `send_notification()` 遍历 `.env` 里配置的三个 webhook URL，各发各的。三平台消息格式在 `WebhookChannel` 类里按平台分派——飞书用 interactive card（蓝色标题卡片），钉钉和企微用 markdown。配置只需在 `.env` 填一个 URL。实际接入时发现飞书的安全设置有关键词校验——消息里必须含"经营"关键词才放行，这是一个实际踩过的坑。

## 第一部分：项目背景（0-5 分钟）

> "我先花一分钟交代一下背景——为什么做这个项目、解决什么问题。
>
> 连锁零售的老板每天面对几十家门店、上万笔订单、几千个会员。想看个数据，比如'上个月哪家店卖得最好''最近退款率为什么高了'，得找数据分析师——先导出 Excel，再做透视表，再写分析报告。半天过去了。
>
> 老板不懂 SQL，运营不会写 Python，但每个人都想知道这些答案。这就是我看到的痛点——不是'老板不想做数据分析'，而是'获取分析结果的成本太高了'。
>
> 所以 V4 的产品定位很简单：用中文提问，60 秒拿到带图表的诊断报告。你问'华东区销售为什么下降'，系统自动调动多个 AI Agent——查销售数据、查会员数据、查退款数据——最后给你一份含数据概览、根因诊断、可执行建议的完整报告。
>
> 这个项目经历了四个版本。V1 是概念验证——线性流水线，验证'自然语言→SQL→报告'这条路跑不跑得通。V2 引入 Multi-Agent 并行——把销售、会员、财务三个领域拆成独立 Agent，让它们同时查数据库。V3 扩展到 8 个 Agent，加了多轮对话和图表。V4 是我现在展示的这个版本——10 个 Agent、企业级安全、经营看板、流式进度、155 条测试。每个版本都解决上一版暴露的核心问题。"

**这段讲完后的停顿点**：面试官可能会问"为什么从 V2 到 V3 要加 Agent"或"你是怎么判断该加什么的"——这是你进入第二部分架构设计的自然过渡。

---

## 第二部分：架构设计（5-10 分钟）

> "架构上我做一个最重要的决策——用 Multi-Agent 而不是单 Agent。这个决策不是架构偏好，是实测出来的。我讲三个具体的原因。
>
> 第一个是上下文窗口竞争。5 个领域的 Schema——销售、会员、财务、库存、供应链——加起来超过 3000 token。单 Agent 方案要把这 3000 token 全部塞进 System Prompt，加上工具调用的往返、SQL 结果，每次分析烧到 12000 token。问题不是 token 贵——是 LLM 在长上下文后半段注意力会衰减。
>
> 我做过三个对照实验来验证这个假设。先审计原始 SQL——Finance Agent 的 SQL 算出来退款率是 3.2%，但报告里被写成了 8.7%。SQL 没错，说明问题在 LLM 理解环节。然后我做隔离实验——把 Report Agent 的输入改成只给 Finance 的输出，删除 Sales 和 CRM 的内容，错误消失了。第三步做位置效应测试——把 Finance 数据从第三个位置移到第一个位置，准确率从 80% 提升到 95%。同一个 LLM、同样的数据、只是调了顺序——结论很清楚，就是注意力衰减。
>
> 第二个原因是故障隔离。单 Agent 方案下，CRM 查数据库抛异常，整个对话上下文被污染——LLM 会基于错误信息继续推理。Multi-Agent 下每个 Agent 有独立的 State，CRM 挂了只影响 CRM 的输出。Aggregator 看到 CRM 的 None 会跳过，报告里写'会员数据暂不可用'，而不是编造一个数字。
>
> 第三个原因是迭代效率。这个项目做了四个版本，Sales Agent 的 Prompt 迭代了 7 版，CRM 只改了 2 版。独立 Prompt 意味着改一个 Agent 只需要重测对应的评估集——如果捆在一起，每次改一个字就要全量重测。

**这段讲完后的停顿点**：面试官可能会追问注意力衰减的实验细节（"你怎么确定不是 SQL 写错了"）——你有 BadCase 1 的完整故事可以回答。

## 第三部分：评估体系（10-15 分钟）

> "架构解决的是'怎么做'的问题，评估体系解决的是'怎么知道做得好不好'的问题。AI 产品的评估跟传统软件完全不同——传统软件的功能测试是确定性的，输入 A 必然输出 B。但同一个分析问题问两次，LLM 可能给出不同措辞的报告，哪个更好？你没法用 pass/fail 来判断。
>
> 所以我建了三层评估体系。
>
> 第一层：离线评估集。20 条标准问题，覆盖查询型和分析型。每条有预期输出格式和关键数据点——比如'各门店销售额排名'必须返回表格、必须包含门店名和销售额两列、数据必须和数据库一致。每次改 Prompt 后跑一遍，对比准确率变化。这套评估集让我在迭代 Prompt 时知道自己是在往前走还是往后退。
>
> 第二层：Reflection Agent 在线质检。每次分析完成后自动运行，从 4 个维度审核报告质量。这 4 个维度不是我一拍脑袋定的——初始只有 2 个，后面 2 个是通过 BadCase 驱动出来的。
>
> 我给你讲一个具体的例子。有一次跑离线评估集，我发现一个报告把'华南区退款率上升'和'某供应商准时率下降'并列在一起，用了'因此''所以'这样的因果词，暗示两者有关联。但我回溯数据发现——退款率上升集中在促销期间，是促销引流来的新用户退货率高，跟供应商毫无关系。这是 LLM 的经典问题：把相关性当因果性。
>
> 这个 BadCase 让我在 Reflection 里加了一个新维度——'逻辑严谨性'——专门检查报告是否将两个独立现象暗示为因果关系。后来又加了一个'建议可操作性'维度——因为发现有的报告给的建议是'提升门店运营效率'，说了等于没说。现在要求建议必须具备'谁、做什么、预期效果'三个要素。
>
> 还有一个重要的产品决策：Reflection 审核不通过后重试几次？我做了对比实验——重试 0 次，25% 的报告有明显质量问题；重试 1 次，修复率约 60%，多耗 3000-5000 token；重试 2 次报，修复率提升到 75% 但边际收益递减；重试 3 次，开始陷入'越改越差'的循环。我选了 1 次——不是因为 1 次完美，是因为超过 1 次通常不是报告写得不好，而是底层数据本身就矛盾，Reflection 怎么改都过不了。
>
> 第三层：用户反馈闭环。每条报告底部有 👍👎 按钮，用户反馈数据写入 user_feedback 表。如果某类问题点踩率持续偏高，检查对应 Agent 的 Prompt，更新，离线评估集复测，上线——形成闭环。
>
> 这个评估体系的演化过程本身，我觉得比体系本身更有价值。它说明了 AI 产品的一个核心方法论：不是一次性设计完美的体系，而是通过发现问题不断迭代。用 BadCase 驱动改进，而不是靠直觉。"

**这段讲完后的停顿点**：面试官可能会问"评估集只有 20 条是不是太少了"——诚实回答：是的，这是当前局限。基于 demo 数据，真实客户数据会暴露边界。下一步 POC 的首要任务就是验证评估标准。

---

## 第四部分：安全治理（15-20 分钟）

> "接下来我想讲安全——这部分可能是我在整个项目里最自豪的，因为它体现了一种产品思维。
>
> 我实际发现了三个安全漏洞。最严重的一个：我用 zhangsan 账号登录——他是华东区域经理，理论上只能看到华东 22 家门店的数据。但我发现他的报告里有华北门店的数据。
>
> 怎么发现的？不是靠跑测试，是逐行读代码。我看到 `inject_store_filter` 函数里有一个逻辑——当 store_ids 为空列表时，函数直接返回原始 SQL，不加任何 WHERE 过滤。这意味着如果一个用户没有任何门店访问记录，或者系统因为某种原因查不到他的权限，他会看到所有门店的数据。
>
> 第二个 bug 是 `get_user_store_ids`——当用户没有任何 UserStoreAccess 记录时，它返回的是 None——None 在这个上下文里表示'全量访问'，而不是'拒绝'。默认全量访问和默认拒绝是完全相反的安全姿态。
>
> 我做的修复是两处：空列表时注入 WHERE 1=0 强制零结果；无记录时返回空列表——默认拒绝，显示授权。
>
> 为什么我能在代码里发现这个问题？不是因为我懂安全——是因为我在博卡做了 4 年权限体系。博卡的产品要过大型连锁客户的 security review，我梳理过 23 个敏感模块的分级脱敏规则——财务数据、会员手机号、员工薪资——哪一级角色能看什么、能不能导出、能不能修改。'默认安全、逐层授权'这个原则，是那个时候刻进我产品思维里的。当我在 AI 项目里看到 `if not store_ids: return sql` 这一行时，直觉告诉我——这里不对，应该有默认拒绝。
>
> 企业级 AI 产品的安全不是一个功能模块，而是一种设计习惯。这个习惯来自长期的 B 端 SaaS 经验——而这是很多纯 AI 背景的产品经理不具备的。这也是我认为自己的差异化价值所在。"

**这段讲完后的停顿点**：面试官可能会追问"还有其他安全漏洞吗"——诚实承认：member 表缺少 store_id，CRM 查询会员时会绕过 RLS，是已知技术债。

## 第五部分：产品决策（20-25 分钟）

> "前面讲了架构、评估、安全——这些是'做了什么'。这部分我想讲'为什么这样做'，选几个关键决策展开。
>
> 第一个是流式优先。V3 的方式是先查缓存——命中秒返、没命中再走流式。V4 我改成了流式优先。原因是——95%以上的查询都是新问题，缓存命中率极低。'缓存优先'在概念上听起来很好，实际中很少被触发。更重要的是——用户盯着静态进度条等 60 秒和看着流式进度条更新 60 秒，是完全不同的心理体验。前者是'等待'，后者是'进展'。
>
> 第二个是 Schema 适配器的设计。每家零售企业的数据库表名不一样——有的叫 orders，有的叫 t_sales_order。如果靠改代码适配，每次部署都需要一个懂 Python 的工程师驻场。年费 3 到 5 万的定价下，驻场成本会让毛利率变负。所以我设计了三层适配器——系统自动发现表结构、客户技术人员在 YAML 里做一次性标注、然后系统自动生成适配后的 Prompt。只有第二层需要人工，而且只需一次。这个设计的出发点不是技术优雅，是成本结构。
>
> 第三个是双模式输出。用户晨会看数据时——'昨天 Top 3 门店是谁'——他们只想要表格，不需要六段分析报告。但周会决策时——'为什么华东销售下降'——他们需要根因诊断和可执行建议。用同一套输出格式同时服务这两种场景，要么信息过载、要么信息不够。所以我设计 Supervisor 的第一个判断就是：这是查询型问题还是分析型问题？查询型只出表格加简短总结，分析型出完整报告。输出格式应该匹配用户场景，而不是匹配 AI 的能力。"

**这段讲完后的停顿点**：面试官可能会问"你是怎么判断查询型还是分析型的"——回答：Supervisor 用 LLM 判断，关键词兜底。如果用户问"最高""最多""最大""第一"等最高级词 → 查询型。如果问"为什么""分析""原因" → 分析型。

## 第六部分：方法论沉淀（25-30 分钟）

> "最后一部分我想讲一下——做完这个项目我沉淀了什么。
>
> 我是 V4 之后没有继续加功能。我做了一件事——把整个过程里的产品决策、失败案例、设计原则整理出来。因为我意识到功能会过时，但做判断的方法可以复用。
>
> 第一份产出：13 条关键产品决策记录。每条记录了'当时考虑了哪些方案、为什么选这个、如果重来一次会不会还这么选'。比如放弃单 Agent——如果重来，我会加入混合方案：高频查数据型走单 Agent 降低延迟，跨领域分析型走 Multi-Agent 保证准确率。
>
> 第二份：7 条 AI 产品设计原则。每条都可以追溯到一个具体的决策或 BadCase。比如'够好就行不追求最优'——来自 Reflection 重试 1 次而非 3 次的决策；'防御性设计默认拒绝'——来自发现数据泄露漏洞的经历；'BadCase 驱动迭代不靠直觉'——来自评估体系从 2 维演化到 4 维的过程。
>
> 第三份：3 次 BadCase 闭环复盘。每一次都是'发现问题→诊断根因→设计实验→验证假设→实施修复→沉淀教训'的完整链路。我不是在展示我多厉害——恰恰相反，我在展示我从失败里学到了什么。AI 产品领域，失败比成功更有教育意义。
>
> 如果你给我 3 个月和一个工程师，我不会做 V5、不会加第 11 个 Agent。我会找 1-2 家真实的连锁零售企业做 POC，验证这套评估体系在真实数据下是否依然有效。如果无效，我会回来修改评估标准。如果有效，我会开始考虑定价和商业化。因为我知道——功能是永远做不完的，但验证产品是不是在解决真问题，是所有产品决策的前提。
>
> 谢谢。"

## 讲稿使用指南

**不要逐字背诵整篇**。这样做的效果会很僵硬——面试官能听出来你在背书。

**正确用法**：
1. 记住六部分的**顺序**（背景→架构→评估→安全→决策→方法论）
2. 每部分记住**一个核心故事**（黑体标注的部分）
3. 每部分讲完后**停下来**，给面试官追问的空间
4. 如果面试官不追问，继续下一部分

**关键标志词**（帮你记住每部分的入口）：
- 第一部分："我先花一分钟交代背景..."
- 第二部分："架构上我做了一个最重要的决策..."
- 第三部分："架构解决'怎么做'，评估解决'怎么知道做得好不好'..."
- 第四部分："我想讲安全——这可能是我最自豪的部分..."
- 第五部分："前面讲了'做了什么'，现在讲'为什么这样做'..."
- 第六部分："最后我想讲——做完项目我沉淀了什么..."

**如果面试官中途打断**：跟着他的问题走——这是好事。讲完后自然回到被打断的部分继续。这篇讲稿是模块化的，每部分可以独立讲。如果某部分被跳过（比如面试官说"这部分我已经了解了"），直接跳到下一部分。

# 结语

你不是"会写 Prompt 的产品经理"，也不是"转型中的 SaaS PM"。

你是**能把企业级产品能力与 AI 产品判断力结合起来，形成可落地、可评估、可治理的 AI 产品的产品经理**。

这不是"技能组合"——这是一个新的产品经理品类：**AI 应用产品经理（偏企业级）**。
