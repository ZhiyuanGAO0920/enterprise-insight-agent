# AI 产品设计原则

> 提炼自 Enterprise Insight Agent V1→V2→V3→V4 四版迭代实践。
> 面试时引用这些原则，让你从"我做了 X"升级为"因为 Y 原则所以我选了 X"。

---

## 原则 1：够好就行（Good Enough Principle）

**"AI 输出不追求完美，追求用户可接受的最低阈值。"**

AI 产品与传统软件最大的区别：输出是不确定的。追求 100% 正确会让产品永远无法上线。真正的问题是——用户的容忍阈值在哪？

**实践案例**：Reflection Agent 质检最多重试 1 次。

实测数据：第 1 次重试修复了 80% 的问题，第 2 次只能额外修复 10%，但用户多等 15 秒。85% 的质量 + 45 秒等待 > 95% 的质量 + 60 秒等待。用户在等待时会焦虑，焦虑 > 报告里的小瑕疵。

**设计启示**：找到用户对"不够好"的容忍边界，在那个边界停下。不是做得越多越好，是在用户失去耐心之前做到足够好。

## 原则 2：灰度开关（AI Kill Switch）

**"任何 AI 功能上线时必须有 Feature Flag 回退开关，这不是'可能的保险'，而是'必须的保险'。"**

LLM 有不可预测性——模型更新、API 变更、Prompt 退化，任何环节都可能出问题。传统软件的 feature flag 是灰度工具，AI 产品的 feature flag 是救命开关。

**实践案例**：V3 所有新功能默认 `False`，经过 137 条测试验证后才批量改为 `True`。如果某个功能导致 LLM 调用量异常飙升或输出质量退化，运维可以一键关闭，不需要等代码修复和部署。

**设计启示**：AI 功能的发布不是"上线 = 完成"，而是"上线 = 开始观察"。Feature flag 让你能控制爆炸半径。

## 原则 3：输出自适应（Adaptive Output）

**"不是所有问题都需要生成式 AI。判断'什么时候生成、什么时候检索/展示'是 AI PM 的核心能力。"**

生成式 AI 昂贵、慢、可能出错。如果用户要的就是一张排名表，调用 5 次 LLM 给他生成 6 段分析报告是一种浪费——对用户的时间和你的 API 费用都是。

**实践案例**：Supervisor 判断问题类型后分流——查询型（"各门店销售额排名"）→ 表格输出，快且准；分析型（"华东区销售为什么下降"）→ 完整报告，深且全。

**设计启示**：在 AI 产品设计的第一步，先问"这个问题真的需要生成式 AI 吗？"——有时候一个查询 + 模板就够了。

## 原则 4：局部降级（Graceful Degradation）

**"单个 Agent 失败不应阻断全局流程。不要因为 20% 的失败概率放弃 80% 的成功价值。"**

Multi-Agent 系统中，某个 Agent 可能因为 LLM 超时、SQL 语法错误、数据源不可用等原因失败。如果因为财务 Agent 挂了就让整个分析报告显示"系统错误"，用户会认为你的产品不可靠。

**实践案例**：每个领域 Agent 有独立的 try/except 隔离，失败后只影响自己的输出段落（如"财务分析暂不可用"），Sales/CRM/Inventory 的产出正常展示。Supervisor 兜底激活所有 Agent，确保全局不中断。

**设计启示**：局部降级 > 全局失败。用户宁愿看到"80% 完整的报告"也不愿看到"100% 的错误提示"。

## 原则 5：先验证再规模化（Validate Before Scaling）

**"新 Agent 或新 Prompt 上线前，必须先通过离线评估集验证。改 Prompt 不能靠感觉。"**

AI PM 最容易犯的错误：改了一行 Prompt → 感觉更好了 → 上线 → 用户投诉质量下降了。Prompt 优化在某个场景下可能提升，在另一个场景下可能退化。没有评估集 = 蒙着眼睛优化。

**实践案例**：建立了 102 条离线评估集（50 查询型 + 38 分析型 + 14 边界型，覆盖销售/会员/财务/库存/供应链 5 领域 + 综合分析 + 边界场景），每次改 Prompt 后跑一轮，输出 SQL 准确率、维度覆盖率、幻觉检测和平均延迟——数据化判断是否真的有提升。

**设计启示**：好的 AI PM 不是在"调 Prompt"，是在"用数据验证 Prompt 优化效果"。这是从"工匠"到"工程师"的关键一步。

## 原则 6：成本作为一级设计约束

**"LLM 调用成本不是运维问题，是产品设计问题。"**

很多 PM 觉得"成本是工程师和运维的事"。但如果你的产品每次分析调用 15 次 LLM，而竞品只调用 5 次，你的毛利就会差 3 倍。成本结构决定了你的定价空间，定价空间决定了你的目标市场。

**实践案例**：
- 选 DeepSeek 而非 GPT-4o：价格差 50 倍，每次分析 5+ 次 LLM 调用，成本差会放大到不可接受
- 本地 BGE-M3 Embedding 而非 OpenAI API：零 Embedding 成本，每次检索节省 $0.0001，但每天 100 次分析 × 365 天 = $3650/年
- Supervisor 可以由关键词匹配退化，非必须走 LLM 决策——这是后续降本方向

**设计启示**：在产品设计阶段就标注每个 AI 调用的成本，把它作为和"用户体验"一样重要的权衡因子。

## 原则 7：信任来自可验证（Trust = Verifiability）

**"AI 产品的用户信任不是靠'模型很强'建立的，而是靠'用户可以验证'建立的。"**

B 端 AI 产品最大的障碍不是技术，是信任。"AI 说的对吗？"——这是每个 B 端用户在看完 AI 输出后的第一反应。你不能用"我们的模型准确率 95%"来回答这个问题，因为用户不知道也不关心你的准确率。你能做的是让他自己去验证。

**实践案例**：每条报告中的关键数据主张后面都有"[📊 查看SQL]"链接，点击可以看到这条数据是从哪个表、用什么 SQL 查出来的。溯源标记本身未必每次被点，但它的存在本身就是一种"你可以验证我"的承诺。

A/B 测试数据：有溯源标记的报告，用户信任度评分从 2.5/5 提升到 4.5/5（+80%）。

**设计启示**：在 AI 产品中，"让你验证"比"告诉你我有多准"更能建立信任。

## 如何使用这些原则

**面试场景**：
- 解释架构决策时："根据我的'够好就行'原则，Reflection 只重试 1 次"
- 被问项目风险时："我有一个'灰度开关'原则，所有 AI 功能都有 Feature Flag"
- 被问成本问题时："成本是我设计的一级约束，这也是我选 DeepSeek 而非 GPT-4o 的核心原因"

**设计评审场景**：
- 有人提议加新 AI 功能："这个功能需要离线评估集验证，我们先建评估集"
- 有人问为什么不做某个优化："边际收益低于用户等待时间的增加，够好就行原则"

## 附录：AI 产品核心指标体系

传统 SaaS PM 看 DAU/MAU、留存率、NPS。AI PM 还需要额外看一套"模型表现指标"——因为 AI 产品的质量不是固定的，是会随着 Prompt 改动、模型更新、数据变化而波动的。

### 五维指标体系

| 维度 | 核心指标 | 当前基线 | 目标 | 为什么重要 |
|------|---------|:--:|:--:|------|
| **准确性** | SQL 准确率 | 85% | 90% | Agent 最基础能力——SQL 错了，后面全错 |
| **质量** | Reflection 通过率 | 85% | 90% | 质检 Agent 的综合质量评分 |
| **效率** | P95 响应延迟 | 45s | 30s | 超过 30s 用户开始焦虑，超过 60s 关页面 |
| **安全** | 幻觉率 | 0% | <2% | AI 产品特有的风险——编造数据比不返回数据更危险 |
| **成本** | 单次分析成本 | ¥0.04 | ¥0.03 | 成本结构决定定价空间和规模化可行性 |

### 为什么传统 SaaS 指标不够

| 传统 SaaS | AI 产品 |
|-----------|---------|
| 功能覆盖率 → 用户能不能用 | SQL 准确率 → AI 能不能做对 |
| NPS → 用户愿不愿意推荐 | 幻觉率 → AI 有没有编造 |
| 留存率 → 用户会不会回来 | 追问率 → AI 对话有没有深度 |
| 客单价 → 每个用户值多少 | 单次分析成本 → 每次 AI 调用花多少 |

**核心洞察**：传统 PM 的指标是"用户做了什么"，AI PM 的指标还要加一层"AI 做得怎么样"。
