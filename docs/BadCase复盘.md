# Bad Case 复盘

> AI PM 面试必问："你遇到过 AI 犯错的情况吗？你怎么处理的？"
> 以下是 4 个真实 Bad Case，每个都完整记录了发现→诊断→修复→验证→教训的闭环。

---

## Case 1：Agent 把"全部门店排名"截断成 Top 20

### 现象
用户问"各门店销售额排名"（期望 100 行完整排名），Agent 返回了 20 行表格，末尾显示"仅展示 TOP 20"。

### 诊断
1. 查看 Agent 生成的 SQL：`SELECT ... FROM store LEFT JOIN orders ... ORDER BY sales DESC LIMIT 20`
2. LLM 在生成 SQL 时自动加了 `LIMIT 20`——它在 Prompt 中没有被明确告知"全部门店查询不加 LIMIT"
3. SQL 执行正确返回了 20 行——问题在 LLM 的 SQL 生成阶段，不在执行阶段

### 修复
在 Supervisor 节点增加关键词检测：
```python
ranking_keywords = ["所有", "全部", "全部门", "排名", "排行", "列表", "清单"]
if any(kw in question for kw in ranking_keywords):
    question += "\n[系统指令] 确保列出全部数据行，不允许截断"
```

### 验证
修复后用"全部门店销售额排名"测试 5 次，全部返回 100 行完整数据。

### 教训
**LLM 默认行为是"过度安全"——宁可少给数据也不错给。** 传统软件开发中，开发者会故意给你全部数据；LLM 的默认倾向恰恰相反：它倾向于"截断+告知"。AI PM 需要在 Prompt 中对抗这种倾向——对于"全部/所有"类查询，必须显式告诉 LLM "不要截断"。

## Case 2：RLS 注入破坏 store 表查询

### 现象
用户（店长，只有 5 家门店权限）问"我可以查询哪几家门店"，Agent 返回错误："SQL 执行失败"。

### 诊断
1. 查看 Agent 错误日志：`[SQL_ERROR] column "store_id" does not exist`
2. 追踪到 `inject_store_filter()`：LLM 生成的 SQL 是 `SELECT * FROM store`，RLS 注入了 `WHERE store_id IN ('18','19','20','21','22')`
3. 但 `store` 表的主键列叫 `id`，不叫 `store_id`——RLS 注入用了错误的列名

### 修复
新增 `_detect_store_column()` 函数，根据 SQL 中的表名自动选择正确的过滤列：
- `FROM store` → 用 `id`
- `FROM orders/inventory` → 用 `store_id`
- `FROM member/supplier` → 不注入（这些表没有门店列）

### 验证
修复后，store_001 问"我可以查询哪几家门店"，正确返回 1 家门店（而非 SQL 错误）。

### 教训
**AI 系统的 Bug 往往出现在"两个子系统交界处"。** RLS 注入（安全子系统）和 SQL 生成（Agent 子系统）分别都经过了测试，但它们的交互没有被覆盖。传统测试覆盖的是单个模块，AI PM 需要额外关注"AI 决策 × 传统规则"的交叉场景测试。

## Case 3：追问建议与报告内容不相关

### 现象
用户问"华东区销售为什么下降"，Agent 返回了一份完整的华东区销售分析报告，但末尾的 3 个追问建议是"会员总数是多少""退款率最高的门店是哪个""各区域销售额对比"——这些追问与华东区报告的相关性很弱，用户无一点击。

### 诊断
1. Report Agent 的追问生成指令是："在报告末尾生成 3 个建议追问问题"
2. 这个指令太模糊——LLM 生成了"通用的、任何场景下都能用的追问"，而非"基于本次分析数据的有深度追问"
3. "会员总数是多少"——任何报告后都可以问，用户不会有点击冲动

### 修复
将追问生成指令改为具体约束：
```
生成 3 个建议追问问题。要求：
1. 至少 1 个基于报告中的具体数据
2. 至少 1 个涉及报告中"异常"或"风险"的深层原因
3. 问题之间不重复，覆盖不同维度
```

### 验证
A/B 测试：修复前追问点击率 40%，修复后 100%（10/10 测试中至少有一个追问被点击）。

### 教训
**AI 的"建议"类输出，质量瓶颈不在广度而在相关性。** 泛化的 Prompt 产生泛化的建议，约束的 Prompt 产生精准的建议。这不是模型能力强弱的问题，是 Prompt 设计问题。AI PM 的核心能力之一是"把模糊的产品需求翻译成 LLM 能精确执行的约束指令"。

## Case 4：权限为空时静默放行 → 越权查看全部门店数据（V2 末期）

> 本案例发生于 V2 开发末期，原始记录未随 V2→V3 重构保留，2026-08-07 依据代码演进痕迹重建（V2 `sql_runner.py:62-63` 空权限放行 → V4 `sql_runner.py:154-168` `WHERE 1=0` 兜底）。

### 现象
zhangsan（华东区域经理，应只能访问华东 22 家门店）测试时，查询门店数据返回了全部 100 家门店——行级过滤完全失效。

### 诊断

1. 追踪 SQL 执行日志：Agent 生成的查询**没有被注入任何门店过滤条件**，直达数据库执行
2. 阅读 `sql_runner.py` 找到根因：`inject_store_filter()` 开头是 `if not store_ids: return sql`——**权限列表为空时直接返回未过滤的原始 SQL**
3. `run_sql()` 只在 `store_ids is not None` 时才调用注入；权限解析失败或未接线的查询路径传入 `None` / 空列表时，查询零过滤执行，全量数据返回
4. 安全边界只做在了「接口权限校验」（谁能调用），没有做在「数据行级」（每次查询自动限定数据范围）——两个安全层脱节，漏掉一个环节就是越权

### 修复

1. **空权限强制返回空**：权限列表为空时注入 `WHERE 1=0`（覆盖已有 WHERE / GROUP BY 等子句 / 简单查询三种 SQL 形态），**宁查不到，不查全部**
2. **行级过滤统一收口**：所有 Agent 查询路径统一经过 `run_sql` 的 RLS 注入；权限解析失败按空权限处理，而非静默放行
3. **Prompt 层双保险**：Agent System Prompt 追加权限范围描述，引导 LLM 只分析授权门店

### 验证
zhangsan 重新登录后：查询门店排名仅返回华东 22 家；admin 仍返回全量 100 家。该验证流程后续固化为 Demo 录制脚本（`record_demo.py`：zhangsan 登录验证数据隔离——华东 22 店 vs 全量）。

### 变体残留 1：UNION 查询绕过 RLS（2026-08-10 对抗式审查发现，已修复）
空权限修复只覆盖了**单条 SELECT**。实测 `SELECT * FROM orders UNION SELECT phone, NULL FROM member`（空权限）→ 注入器在**末尾**追加 `WHERE 1=0`，PG 中该条件只约束最后一个 SELECT，**orders 全表无约束返回**——Case 4 的变体形态，BadCase 3 复盘时未覆盖集合运算场景。有权限时同理：`WHERE store_id IN (...)` 只约束最后分支，门店经理 UNION 一下即读全表。

**修复**：`run_sql` 用字符串/注释感知的扫描器检测最外层 `UNION/INTERSECT/EXCEPT`，命中直接返回 `[SQL_ERROR]`（RLS 无法跨分支完整注入），由 Agent 重写为单查询。

**教训**：行级过滤的测试用例必须包含**所有 SQL 子句形态**——集合运算（UNION）、注释、字符串字面量、子查询。只测"标准形态"的修复会在变体上复发。

### 变体残留 2：注入器正则不感知字符串与注释（2026-08-10，已修复）
原 `inject_store_filter` 用正则 `\bWHERE\b` / `\bGROUP BY\b` 定位注入点：
- **字符串截断（已实测 3 例）**：`WHERE note = 'a GROUP BY b'` → 字符串内的 GROUP BY 被当作子句边界 → 注入后括号不闭合、SQL 语法损坏 → 查询失败 + LLM 重试白烧 token
- **注释干扰**：注释内的 WHERE 干扰外层定位，注入点可能被注释吞掉 → RLS 过滤缺失

**修复**：重写为统一字符扫描器 `_locate_outer_clauses`（字符串字面量 / `--` 行注释 / `/* */` 块注释 / 括号深度全感知），12 个用例实测全过（含字符串内 UNION 不误拒）。

### 教训
1. **"修过"不等于"修全"**：Case 4 的空权限修复在 UNION 变体上复发——修复后必须回归所有 SQL 形态
2. **同类 bug 会复制粘贴**：audit.py 修过裸 `"/"` 并留了警告注释，tenant.py 还是犯了同样的错——修复要全局搜索同类模式
3. **配置风险是真实风险**：微信 Demo 后门、n8n 默认密钥、CORS `*`——都是"没配置就是漏洞"，启动时校验 + 警告是零成本防线
4. **对抗式审查的正确姿势**：发现必须带 `文件:行号` 坐实；能实测的必须实测（正则分析会漏 UNION 这种语义漏洞，实测才会暴露）
