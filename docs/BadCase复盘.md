# Bad Case 复盘

> AI PM 面试必问："你遇到过 AI 犯错的情况吗？你怎么处理的？"
> 以下是 3 个真实 Bad Case，每个都完整记录了发现→诊断→修复→验证→教训的闭环。

---

## Case 1：Agent 把"全部门店排名"截断成 Top 20

### 现象
用户问"各门店销售额排名"（期望 100 行完整排名），Agent 返回了 20 行表格，末尾显示"仅展示 TOP 20"。

### 诊断
1. 查看 Agent 生成的 SQL：`SELECT ... FROM store LEFT JOIN orders ... ORDER BY sales DESC LIMIT 20`
2. LLM 在生成 SQL 时自动加了 `LIMIT 20`——它在 Prompt 中没有被明确告知"全部门店查询不加 LIMIT"
3. SQL 执行正确返回了 20 行——问题在 LLM 的 SQL 生成阶段，不在执行阶段

### 修复
在 Supervisor 节点增加关键词检测：
```python
ranking_keywords = ["所有", "全部", "全部门", "排名", "排行", "列表", "清单"]
if any(kw in question for kw in ranking_keywords):
    question += "\n[系统指令] 确保列出全部数据行，不允许截断"
```

### 验证
修复后用"全部门店销售额排名"测试 5 次，全部返回 100 行完整数据。

### 教训
**LLM 默认行为是"过度安全"——宁可少给数据也不错给。** 传统软件开发中，开发者会故意给你全部数据；LLM 的默认倾向恰恰相反：它倾向于"截断+告知"。AI PM 需要在 Prompt 中对抗这种倾向——对于"全部/所有"类查询，必须显式告诉 LLM "不要截断"。

## Case 2：RLS 注入破坏 store 表查询

### 现象
用户（店长，只有 5 家门店权限）问"我可以查询哪几家门店"，Agent 返回错误："SQL 执行失败"。

### 诊断
1. 查看 Agent 错误日志：`[SQL_ERROR] column "store_id" does not exist`
2. 追踪到 `inject_store_filter()`：LLM 生成的 SQL 是 `SELECT * FROM store`，RLS 注入了 `WHERE store_id IN ('18','19','20','21','22')`
3. 但 `store` 表的主键列叫 `id`，不叫 `store_id`——RLS 注入用了错误的列名

### 修复
新增 `_detect_store_column()` 函数，根据 SQL 中的表名自动选择正确的过滤列：
- `FROM store` → 用 `id`
- `FROM orders/inventory` → 用 `store_id`
- `FROM member/supplier` → 不注入（这些表没有门店列）

### 验证
修复后，store_001 问"我可以查询哪几家门店"，正确返回 1 家门店（而非 SQL 错误）。

### 教训
**AI 系统的 Bug 往往出现在"两个子系统交界处"。** RLS 注入（安全子系统）和 SQL 生成（Agent 子系统）分别都经过了测试，但它们的交互没有被覆盖。传统测试覆盖的是单个模块，AI PM 需要额外关注"AI 决策 × 传统规则"的交叉场景测试。

## Case 3：追问建议与报告内容不相关

### 现象
用户问"华东区销售为什么下降"，Agent 返回了一份完整的华东区销售分析报告，但末尾的 3 个追问建议是"会员总数是多少""退款率最高的门店是哪个""各区域销售额对比"——这些追问与华东区报告的相关性很弱，用户无一点击。

### 诊断
1. Report Agent 的追问生成指令是："在报告末尾生成 3 个建议追问问题"
2. 这个指令太模糊——LLM 生成了"通用的、任何场景下都能用的追问"，而非"基于本次分析数据的有深度追问"
3. "会员总数是多少"——任何报告后都可以问，用户不会有点击冲动

### 修复
将追问生成指令改为具体约束：
```
生成 3 个建议追问问题。要求：
1. 至少 1 个基于报告中的具体数据
2. 至少 1 个涉及报告中"异常"或"风险"的深层原因
3. 问题之间不重复，覆盖不同维度
```

### 验证
A/B 测试：修复前追问点击率 40%，修复后 100%（10/10 测试中至少有一个追问被点击）。

### 教训
**AI 的"建议"类输出，质量瓶颈不在广度而在相关性。** 泛化的 Prompt 产生泛化的建议，约束的 Prompt 产生精准的建议。这不是模型能力强弱的问题，是 Prompt 设计问题。AI PM 的核心能力之一是"把模糊的产品需求翻译成 LLM 能精确执行的约束指令"。
