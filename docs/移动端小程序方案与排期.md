# 移动端小程序方案 V1.0 + 排期估算

> **文档版本**：v1.0（2026-07-31）
> **技术路线**：微信小程序（原生开发）
> **MVP 范围**：看数 + 问数（今日快报 / 经营看板 / AI 对话分析 / 历史记录 / 报告分享）
> **前提**：现有 Web 端 V4.6 全部 API 可直接复用，后端改造量最小化

---

## 1. 背景与目标

### 1.1 背景

V4 平台当前仅提供 Web 端（浏览器响应式适配）。但产品核心用户——连锁零售的老板和区域经理——**高频使用场景在手机**：通勤路上看今日销售、巡店间隙问一句"华东区为什么下滑"、把报告直接转发到微信工作群。

Web 响应式无法满足的三件事：
1. **触达**：老板不会主动打开网址/保存书签，但 100% 天天用微信；
2. **推送**：浏览器无法主动提醒"今日销售异常"，微信订阅消息可以；
3. **分享**：报告分享到微信聊天/企业微信群，原生分享卡片体验远优于 H5 链接。

### 1.2 目标

| 指标 | 目标值 |
|------|--------|
| v1.0 上线周期 | ≤ 5 周（单人开发，账号审核并行） |
| 后端 API 改造量 | 仅登录绑定 1 个领域（其余 0 改造） |
| 首屏打开耗时 | ≤ 2s（微信小程序冷启动标准） |
| 问数到出报告 | 与 Web 一致（P95 ≤ 60s，SSE 流式） |
| 用户日均使用 | 老板/区域经理高频场景全覆盖 |

### 1.3 范围

**v1.0 包含（In Scope）**：

- [x] 微信一键登录 + 首次账号绑定（复用现有 JWT + RBAC + 门店行级权限）
- [x] 今日快报首页（今日销售额/订单/会员/异常提醒）
- [x] 经营看板（多图表数据看板）
- [x] AI 对话分析（自然语言问数，SSE 流式 9 步进度，图表渲染，追问建议，反馈）
- [x] 历史分析记录（分页列表 + 详情）
- [x] 报告分享（小程序分享卡片 + H5 链接 + 长图，全部复用现有 `/share/{token}` 能力）

**v1.0 不含（Out of Scope，见 §7 路线图）**：

- [ ] 订阅消息推送预警（v1.1）
- [ ] 周报小程序内生成/下载（v1.1）
- [ ] 企业管理后台移动化（永远不做，保留 Web）
- [ ] iOS/Android 独立 App（v2.0 视需求用 uni-app 迁移）
- [ ] 钉钉/飞书/企微原生小程序内嵌（PRD 已明确 Out of Scope，仅 Webhook 推送）

## 2. 产品定义

### 2.1 用户画像

| 角色 | 场景 | 核心诉求 |
|------|------|----------|
| 老板 | 通勤/出差途中看经营 | 30 秒看清今日经营、异常即预警、报告随手转发 |
| 区域经理 | 巡店间隙问数 | 自然语言问"XX 区域为什么下滑"，拿诊断+建议 |
| 店长 | 门店日报 | 看自己门店数据（RLS 行级权限自动过滤） |

### 2.2 核心用户故事

1. 作为老板，我打开小程序就能看到今日销售额/订单量/异常门店，不用点任何按钮。
2. 作为区域经理，我用语音/文字问"华东区本周销售下降原因"，小程序流式展示分析进度，1 分钟内出带图表和行动建议的报告。
3. 作为任何人，我把报告生成卡片分享到微信群，同事点开即可阅读（免登录）。
4. 作为店长，我只看到自己门店的数据（权限自动继承 Web 端配置）。

## 3. 技术架构

### 3.1 总体架构

```
┌────────────────────────────── 微信小程序端 ─────────────────────────────┐
│  pages/                                                                 │
│  ├─ login（登录/绑定）  ├─ home（今日快报）  ├─ dashboard（看板）        │
│  ├─ chat（AI 助手）     ├─ history（历史）   └─ report-detail（报告）    │
│                                                                          │
│  components/  ec-canvas(ECharts) · rich-text(markdown渲染) · report-card │
│  utils/       request(拦截器) · sse(enableChunked解析) · markdown · share │
└──────────────┬───────────────────────────────────────────────────────────┘
               │ HTTPS + JWT（Bearer Token）
┌──────────────▼───────────────────────────────────────────────────────────┐
│  现有 V4.6 后端（零改造复用）                                              │
│  /auth/login /auth/verify            ── 登录（新增 wechat 绑定 2 个端点）  │
│  /dashboard/today-summary /overview  ── 首页快报 / 看板                  │
│  /analysis/analyze-stream (SSE)      ── AI 流式问数（phase/step/done）   │
│  /analysis/history /history/{id}     ── 历史记录                          │
│  /analysis/share /share/{token}      ── 分享（H5 免登录只读，已移动适配） │
│  /feedback/submit /session/create    ── 反馈 / 多轮会话                  │
│  中间件：JWT + RBAC + RLS（门店行级）+ 审计日志 —— 全链路自动生效          │
└──────────────────────────────────────────────────────────────────────────┘
```

### 3.2 登录与账号绑定（唯一的新后端改造）

现有登录是"用户名+密码 → JWT"。小程序端采用**微信一键登录 + 首次绑定**：

```
流程 A（老用户）：wx.login() → code
  → POST /api/v1/auth/wechat-login {code}
  → 后端调微信 code2Session 换 openid
  → 查绑定表：已绑定 → 直接签发 JWT（复用现有 RBAC/RLS）
  → 未绑定 → 返回 200 + `need_bind: true`（前端跳绑定页）

> ⚠️ 历史坑（2026-07-31 修复）：原约定"未绑定返回 4021 状态码"——**4021 不是合法 HTTP 状态**（合法 100-599），uvicorn/h11 拒绝写入响应直接断开连接，真机表现为"登录失败"（TestClient 宽松未暴露）。已改为 200 + need_bind 标记。
> Demo 模式（WECHAT_APPID 为空）openid 固定为 `demo_wechat_dev_user`：wx.login code 一次性有效，若基于 code 哈希则每次登录都是新 openid，绑定永不命中 → 每次都要重新绑定。

流程 B（首次绑定）：输入现有账号密码
  → POST /api/v1/auth/wechat-bind {code, username, password}
  → 后端校验账号密码 → 写入绑定表（openid ↔ user_id）→ 签发 JWT
```

**后端改造清单（最小）**：

| # | 项目 | 工作量 |
|---|------|--------|
| 1 | 新表 `user_wechat_bindings`（openid 唯一索引）+ Alembic 迁移 013 | 0.5 人天 |
| 2 | 新端点 `POST /auth/wechat-login`、`POST /auth/wechat-bind`（含 code2Session 调用、错误处理） | 1 人天 |
| 3 | 配置项 `WECHAT_APPID` / `WECHAT_SECRET`（.env，默认空 = 功能关闭，不影响 Web） | 0.5 人天 |
| 4 | 新增 pytest：登录/绑定/未绑定/已绑定复用/错误 code（约 4 条） | 0.5 人天 |

> 说明：绑定后 token 携带 `user_id`，与 Web 登录完全同源——RBAC 权限、门店行级过滤（RLS）、审计日志**自动生效，零改造**。多租户同理。

### 3.3 流式对话适配（技术难点 1）

Web 端用浏览器 `EventSource` 消费 SSE。小程序 `wx.request` 不支持 EventSource，采用 **`enableChunked: true` + 手动解析 SSE 帧**：

```
POST /api/v1/analysis/analyze-stream（带 JWT）
  wx.request({ enableChunked: true, onChunkReceived: 增量解析 })
  帧格式：data: {json}\n\n（后端已加 X-Accel-Buffering: no，不会被网关缓冲）
  事件类型：phase（节点开始）→ step（节点完成）→ done（最终报告）
  前端渲染：9 步进度条（复用 Web 端 LABELS）+ 报告流式输出
```

**⚠️ 开发前置：技术预研 Spike（1 人天，排期见 §5）**。`enableChunked` 在部分安卓机型/微信版本上不稳定且调试困难（无 Chrome DevTools 抓包），正式开发前必须用真实 FastAPI 后端 + 真机验证：网络抖动恢复、超时中断、事件帧解析。验证通过才走流式方案。

> **📌 Spike 实测结论（2026-07-31，已执行）**：`enableChunked` 在微信开发者工具（基础库 3.17.0）+ 真实 FastAPI 后端实测**失败**——
> ① 不设 `responseType: 'arraybuffer'` 时 `onChunkReceived` 完全不触发；
> ② 设置后请求**不结束**（服务端已完成并保存记录，客户端 `success`/`fail` 均不触发，数据流断开）；
> ③ 服务端已验证 SSE 流完整（curl 复现 phase/step/done 全部到达，HTTP 200）。
> 另踩坑：WXS 不支持 `Number()`/`String()` 函数调用（编译报错）。
> **V1.0 决策：默认走同步 `/analysis/analyze`（`config.streamEnabled = false`）**，实测 16s 返回完整报告；
> 同步模式用胶囊计时器（"⏱ Ns"）弥补无进度条的等待感。流式代码保留在 `streamEnabled` 开关后，待真机验证后再启用。

**降级路径（按可靠性排序）**：

1. **同步 `/analysis/analyze`**（已存在，60s 内返回完整报告）——Spike 失败或基础库 < 2.20.1 时的首选兜底，体验损失仅"无 9 步进度条"；**✅ V1.0 已落地为默认路径**（2026-07-31，见上）；
2. 轮询模式（每 2-3s 查增量结果）——**需要新增后端任务端点 `GET /analysis/task/{id}`（+1-2 人天），V1.0 不默认实施**，仅当流式+同步都无法满足时再追加。

### 3.4 图表渲染（技术难点 2）

后端报告是 Markdown，内含 `<div class="chart-container" data-chart='{ECharts option JSON}'>` 图表标记。

- 采用 **echarts-for-weixin**（canvas 版 ECharts 5，官方维护）；
- 解析报告 HTML → 提取 `data-chart` JSON → 按 type（bar/line/pie）渲染 canvas 图表；
- **按需引入** ECharts 模块（不引全量），预计 echarts 部分 ~200KB。

**分包策略（评审建议吸收，主包体积是生死线）**：

```text
主包（<500KB）    登录/绑定、首页快报、TabBar 骨架、request/sse 工具、公共组件
分包 1「ai」      问数对话页、报告详情页、echarts-for-weixin、towxml（体积大头）
分包 2「share」   分享落地页（轻量，独立分包便于直开）
```

- TDesign 组件**按需注册**（`usingComponents` 逐个引用，不全量引入）；
- 分包体积限制：单个分包 ≤ 2MB，主包 ≤ 2MB（目标主包 < 500KB）；

### 3.5 Markdown 渲染

用 **towxml**（小程序生态最成熟）渲染 Markdown + 内嵌 HTML，支持代码块/表格/图表容器。安全策略：与 Web 端一致做 HTML 清洗（purify 逻辑等价实现），图表容器不走 HTML 注入，单独用 canvas 组件渲染。

### 3.6 分享链路（零后端改造）

**安全现状（后端已内置，无需新增）**：

- 分享 token 默认有效期 **30 天**（`SHARE_TTL_DAYS`），过期自动 404；
- 可随时 `DELETE /analysis/share` 取消分享，原链接立即失效；
- 公开接口 `/share/{token}` **只返回 question + report 正文**，不含 SQL、数据来源、Agent 中间结果——数据泄露面已收窄；
- 生成分享需 `history:view` 权限，RBAC 已约束谁可以分享。

**分享三种形态**：

| 方式 | 实现 | 现状 |
|------|------|------|
| H5 链接分享 | 复用 `POST /analysis/share` 生成链接 → `share.html`（已移动端适配、支持长图） | ✅ 已有 |
| 小程序分享卡片 | `onShareAppMessage` 携带 token → 小程序内分享落地页读 token → 调 `/analysis/share/{token}`（公开只读） | 新增前端页 |
| 长图 | 复用现有 html2canvas 逻辑生成报告长图 → 保存/转发 | ✅ 已有（H5 端） |

**小程序内分享落地页设计**（评审建议吸收）：不做长篇 Markdown 平铺，做成**结论卡片式**——顶部突出核心结论（如"华东区销售下降 15%"）、关键数字、分享人 + 时间，"查看完整报告"折叠展开；PC 端打开时引导跳转 H5 版本。

### 3.7 安全

- 传输：HTTPS + 微信 request 合法域名白名单（需备案域名 + TLS 证书）；
- 鉴权：全部接口走 JWT Bearer，与 Web 同一套；
- 数据边界：RLS 门店行级过滤自动生效，店长只能看自己门店；
- 审计：现有审计中间件自动记录小程序端操作（同源 token，无需改造）；
- 登录风险：绑定接口加频控（现有 rate_limit 复用）。

### 3.8 技术选型明细

| 项 | 选型 | 理由 |
|----|------|------|
| 开发方式 | 原生小程序（WXML/WXSS/JS） | 无跨端需求；原生性能/调试最优；单人可维护 |
| UI 组件库 | TDesign Miniprogram（腾讯官方） | 与微信风格一致，B 端表格/卡片组件齐全 |
| 图表 | echarts-for-weixin（按需引入） | 后端 data-chart JSON 零转换直接渲染 |
| Markdown | towxml | 小程序生态最成熟的富文本渲染 |
| 语音转文字 | 微信原生 `RecorderManager` + **同声传译插件**（微信官方 ASR） | 无需自建 ASR 服务；录音 → 本地转文字 → 文本入对话框，不传音频到后端（后端保持纯文本输入，AI 能力边界不变） |
| 状态管理 | 轻量 store（小程序原生 + 自封装） | 页面少，不引入重型框架 |
| 构建 | 微信开发者工具 + npm | 原生工程，无额外构建链 |
| 后端 | 全部复用 FastAPI V4.6 | 见 §3.2 改造清单 |

## 4. 页面与信息架构

TabBar **两个主入口：首页（今日快报）/ AI 助手（对话问数）**，第三个 Tab 为「我的」（含历史记录、反馈、退出登录）。

> **设计决策（评审建议吸收）**：老板的诉求是"看"和"问"，不会去翻结构化的历史列表——历史记录降级为**「我的」页入口 + 问数页顶部"最近会话"下拉（最近 3-5 条，断点续聊）**，主入口保持聚焦。看板并入首页（首页 Tab 内可切换"今日快报 / 经营看板"两个视图）。

| 页面 | 路径 | 说明 | 依赖 API |
|------|------|------|----------|
| 登录/绑定 | pages/login | 微信一键登录；首次输入账号密码绑定 | 新增 wechat-login/bind |
| 首页 | pages/home | Tab 1：今日快报（红绿灯指标卡 + 异常卡片置顶）+ 经营看板视图切换 | /dashboard/today-summary、/dashboard/overview |
| AI 助手 | pages/chat | Tab 2：对话流 + 输入（语音转文字）+ 最近会话下拉 + 9 步进度 + 流式报告 + 追问 chips + 反馈 | /analysis/analyze-stream、/session/create、/feedback/submit |
| 我的 | pages/mine | Tab 3：历史记录入口、我的反馈、版本信息、退出登录 | /analysis/history |
| 报告详情 | pages/report-detail | 完整报告（图表 + 数据来源 + 追问） | /analysis/history/{id} |
| 分享落地 | pages/share（分包） | 小程序内免登录读报告（结论卡片式，见 §3.6） | /analysis/share/{token} |

**首页"红绿灯"视觉规范（评审建议吸收）**：

- 销售额/订单/会员三个核心指标卡：与昨日/同期对比，涨跌用 绿/红 色块 + 箭头 + 百分比，一眼判断经营健康度；
- 异常提醒（断货/退款激增等）**独立卡片置顶**（非小红点），点击跳转问数页自动携带该问题（如"分析今日退货率最高的 5 个门店"），形成"看→问"闭环；
- 弱网/加载中：骨架屏 + "正在获取今日经营数据…"。

**问数页体验规范（评审建议吸收）**：

- LLM 首 token 前：思考中骨架屏（"正在分析销售数据…"），**不显示空白**；
- 收到 token 后：打字机效果 + 闪烁光标，配合 9 步进度条（阶段完成时轻微震动反馈，Vibration API）；
- 输入框上方气泡引导："试试问：今日华东区销售为何下降？"——引导完整提问，减少无效多轮 → 降低 Token 成本；
- 报告底部：追问 chips + "有帮助/没帮助"反馈（细分原因：数据不准/建议太空/图表看不懂，反馈数据是后续优化 Prompt 的 BadCase 素材）。

## 5. 排期估算

### 5.1 假设

- **单人开发**（作者本人），每天有效开发 4-6 小时；
- 后端改造与小程序开发**并行**（先做后端 2 个端点，1-2 天即完成，不阻塞）；
- 微信小程序账号注册/认证与开发**并行**（最长前置项，立即启动）；
- 不含测试人力（沿用现有 pytest 体系 + 真机手工验收）。

### 5.2 里程碑

| 阶段 | 工作项 | 工期（人天） | 前置依赖 |
|------|--------|:---:|---------|
| **0. 前置准备** | 企业主体小程序注册 + 微信认证（¥300/年）+ AppID/AppSecret 获取；服务器域名 ICP 备案 + HTTPS + request 合法域名配置 | **并行 0**（日历 5-10 天，不可控） | 企业资质 |
| **1. 后端登录绑定** | 迁移 013 + wechat-login/bind 端点 + 配置 + 4 条 pytest | 2.5 | 无（立即开始） |
| **2. SSE 技术预研（Spike）** | 真机验证 `enableChunked` 流式接收：网络抖动恢复、超时中断、事件帧解析；失败则确定降级到同步 `/analyze`（见 §3.3） | 1 | 真实后端 |
| **3. 前端基建** | 项目骨架 + 分包配置（主包/ai 包/share 包）+ TDesign 按需注册 + request 拦截器（token/401/错误 toast）+ 路由/TabBar | 1.5 | 账号 AppID（可先用测试号） |

## 8. 验收标准（v1.0 发布门禁）

1. 新用户 3 分钟内完成微信登录 + 绑定，老用户 10 秒内进入首页；
2. 首页快报首屏 ≤ 2s；看板图表全部渲染成功；
3. AI 问数：10 个典型问题（含跨领域/追问/异常数据），P95 ≤ 60s，报告图表正确渲染，追问 chips 可点击继续；
4. 历史记录分页正确，详情与 Web 端一致；
5. 分享：卡片 + H5 链接 + 长图三条链路均可用，免登录可读；
6. 权限：店长账号仅见本门店数据（RLS 生效）；审计日志记录小程序操作；
7. 后端 pytest：183 + 4（新增 wechat 登录）= 187 条全部通过；
8. 真机：iOS + Android 主流机型（含低版本微信）无阻断性 BUG。

## 附：与 Web 端的关系

- **不是替代，是互补**：Web 保留重操作（管理后台、Prompt 管理、监控、Schema 配置）；
- **同源同权**：同一账号体系、同一份数据、同一套权限——小程序是 Web 的"移动前哨"；
- **后端演进原则**：小程序不产生新领域逻辑，只复用 API；新增能力（订阅推送）同样先做 API 再考虑多端。
