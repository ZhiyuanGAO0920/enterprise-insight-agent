## 1. 一句话定位

**EIA V5** 是面向连锁零售企业的 **Multi-Agent AI 经营分析平台**：用户用中文提问，系统在 60 秒内返回一份诊断报告——数据概览 + 根因诊断 + 可执行建议。

> "BI 工具让你做出好看的报表，我们让你不用做报表。"

- **11 个 Agent 节点**协作：1 个 Supervisor 路由 + 5 个领域 Agent 并行分析 + 5 个后处理节点
- **零门槛**：不写 SQL、不拖拽、不懂数据结构也能问
- **私有化**：Docker 一键部署，数据不出企业
- **可验证**：有测试基线、有评估体系、有金丝雀漂移监控——不是 demo 玩具

**V5 收官一句话**：从"会分析数据的 Multi-Agent"升级为**"能验证自己分析结果、可证明多租户安全、成本受控的 Enterprise Analytics Agent"**。

## 4. 系统架构

### 4.1 Agent 拓扑（11 节点全链路）

```
Supervisor（规划路由，temperature=0）
    ↓ LangGraph Send 并行扇出
[sales] [crm] [finance] [inventory] [supply_chain]   ← 5 领域 Agent 并行
    ↓ 扇入
Aggregator（纯 Python 聚合，零 Token 消耗）
    ↓
Chart Advisor（ECharts 图表推荐）→ Report Agent（SSE 流式输出）
    ↓
Reflection Agent（4 项质量契约质检，最多重试 1 次）
    ↓
Save Memory（pgvector 1024 维，BGE-M3 本地 Embedding）
```

| 节点 | 职责 |
|---|---|
| **Supervisor** | 路由决策：理解问题 → 决定激活哪些领域 Agent |
| **Sales / CRM / Finance / Inventory / SupplyChain** | 销售 / 会员 / 财务 / 库存 / 供应链 领域分析 |
| **Aggregator** | 各 Agent 结果拼接为统一摘要（纯 Python，不耗 Token） |
| **Chart Advisor** | 按数据特征推荐最佳 ECharts 图表类型 |
| **Report Agent** | 生成 Markdown 报告 + 追问建议（流式推送） |
| **Reflection Agent** | 4 维质检，不通过自动重试（最多 1 次） |
| **Memory Node** | BGE-M3 向量嵌入 + pgvector 语义搜索 |

### 4.2 中间件栈

```
请求 → CORS → 审计日志(Audit) → 多租户(Tenant) → API 版本头 → FastAPI 路由
```

### 4.3 输出形态

- **双模式输出**：查询型 → 表格 + 关键洞察；分析型 → 完整报告
- **SSE 流式**：报告"打字机"效果
- **图表**：ECharts 5，规则兜底注入

## 7. 关键产品决策（结论速查）

> 完整论证（替代方案、数据支撑、结果）见 [`关键产品决策记录.md`](关键产品决策记录.md)（共 18 条）。面试讲"为什么"时用那一份。
>
> ⚠️ **本表"序"仅为阅读序号，不是任何文档的决策编号**。仓库内存在两套独立编号：`关键产品决策记录.md` 的 18 条（决策 14 = 假流式），与 `AI产品经理面试作战包.md` 的 16 条（决策 14 = n8n vs cron）。按**标题**去专文检索，不要按编号对号入座。

| 序 | 决策 | 一句话理由 |
|---|---|---|
| 1 | Multi-Agent 而非单 Agent | 上下文竞争（3000 token 数据库结构）+ 注意力衰减 + 故障隔离 + 迭代效率 |
| 2 | Reflection 重试 1 次 | 0 次→25% 报告有问题；1 次→修复率 60%；2 次边际递减（成本 3000-5000 token） |
| 3 | 流式优先 | 95%+ 查询是新问题，缓存命中率极低 |
| 4 | 数据库结构三层适配器 | 自动发现 → YAML 映射 → Prompt 生成，零驻场部署 |
| 5 | 双模式输出 | 查询型→表格+洞察；分析型→完整报告 |
| 6 | 经营看板作为首页 | 解决用户"冷启动焦虑" |
| 7 | 金丝雀评估闭环 | eval 结果落库（带 model_version），固定子集周期跑分，与基线对比超阈值自动告警（模型漂移检测） |
| 8 | 应用内 asyncio 定时兜底 | n8n CLI 导入的 cron 注册异常，改应用内定时（13:05 检查 + 7 天幂等窗口 = 实际每周一次），省 DeepSeek 配额 |
| 9 | PII 集中脱敏 2 拦截点 | sql_runner 结果出口 + 审计 query_params，下游天然安全，无需逐点处理 |
| 10 | 成本治理 | 分时定价错峰 + 金丝雀错峰调度 + 租户成本硬限额（T-04 待办） |
| 11 | 多租户用"加列 + PostgreSQL RLS" | RLS `FOR ALL`（USING + WITH CHECK）+ **FORCE** 强制；应用运行时用 `eia_app` 用户（`admin` 是 superuser+BYPASSRLS，FORCE 也绕过） |
| 12 | NULL tenant 用户回填默认租户 | 放弃"拒绝检索"：回填 + `users.tenant_id` 非空约束，避免跨租户命中且不破坏存量用户 |
| 13 | Reflection 从"主观自评"改"质量契约审查" | 4 项契约加权（确定性 2 项 + LLM 2 项）+ 双门槛；"可操作性"从 4% 占比重设计为 Alignment（20%） |
| 14 | RAG SQL 检索止损：DELETE | 端到端实测复用率 4%（决策线 20%），价值池仅 0.8%，删除 `search_similar_sql`；同题复用由缓存+历史详情兜底 |
| 15 | 发布即冻结 | V5 发布日 = 功能开发冻结日 |

## 8. 安全与合规体系

| # | 层 | 实现 |
|---|---|---|
| 1 | 认证授权 | JWT + bcrypt（Token 黑名单 + 会话鉴权）+ RBAC（3 角色 / 7 权限）+ 门店级 `user_store_access` |
| 2 | 多租户隔离 | contextvar 注入 `SET LOCAL app.tenant_id` → PostgreSQL RLS `FOR ALL` + **FORCE**，运行时用 `eia_app` 用户 |

| 5 | 隔离验证 | `tests/test_tenant_isolation.py` 5 场景全绿（A 查自己 / B 查 A 只看自己 / 无 tenant_id → 0 行 / int 注入拦截 / memory 无 tenant_id 拒绝检索） |

## 9. 评估体系与定时任务

### 9.1 评估闭环

- **eval 基线**：16 条固定子集，结果落库 `eval_runs`（带 `model_version`）
- **金丝雀跑分**：应用内 asyncio 定时（`app/scheduler.py`），每日 **13:05** 检查，最近 7 天已有 canary 记录则跳过 → **实际每周一次**；n8n 侧同工作流保留双保险（幂等跳过）
- **漂移检测**：与同模型基线对比超阈值自动告警（复用飞书/钉钉/企微通知链路）
- **监控面板**：金丝雀漂移趋势线（通过率/覆盖率/延迟 + drift 徽章），原生 + React 双版
- **质量监控页**：量·质·速·稳四象限 + 质检四维原因分布 + 兜底报告下钻

### 9.2 定时任务时刻表（⚠️ 改时间必看）

| 任务 | 时刻 | 位置 | 幂等窗口 |
|---|---|---|---|
| 告警检测 | **12:30** | n8n 工作流「V4 异常检测与预警」→ `/api/v1/alerts/check` | — |
| 告警兜底 | **12:45** | 应用内 `app/scheduler.py` | 20 小时 |
| 金丝雀跑分 | **13:05** | 应用内 `app/scheduler.py`（n8n 保留双保险） | 7 天 |

**约束**：兜底时刻**必须晚于** n8n（否则会把"n8n 刚跑过"误判成停摆、推假警报并重复检测）；改时刻需**两处同改**（n8n 节点 + `app/config.py` 的 `alert_check_hour/minute`）。时刻唯一事实源为 `app/config.py`。
