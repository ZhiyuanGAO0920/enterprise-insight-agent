# 关键产品决策记录

> 记录 V1→V2→V3→V4 演化过程中的关键决策，特别标注了"否决 AI 建议"的案例。
> 面试场景下，这些决策故事比罗列功能更有说服力。

## 决策 1：V2 为什么引入 LangGraph 而不是沿用 V1 的自研流水线？

**背景**：V1 用 Python 函数调用实现了 Planner → SQL Generator → Executor → Analyzer 的线性流程。

**AI 的建议**：用 LangChain 的 AgentExecutor，它是当时最成熟的方案，社区支持好，文档全。

**我为什么否决**：AgentExecutor 不支持并行扇出。我的核心场景是用户问"分析华东区经营情况"→ 需要 Sales/CRM/Finance 三个 Agent 同时查数据库，然后聚合结果。AgentExecutor 只能串行执行，三个 Agent 依次查询会让用户等待时间翻 3 倍。

**最终方案**：LangGraph StateGraph + Send API。Supervisor 决策后，Send 将三个 Agent 状态副本分发到独立执行分支，数据库查询并行完成后再汇合到 Aggregator。

**结果**：三 Agent 并行查询，总耗时从预估 45s 降到 15s。

## 决策 2：为什么用 DeepSeek 而不是 GPT-4o？

**背景**：选 LLM 供应商是整个项目的根基。

**AI 的建议**：GPT-4o 是行业标准，function calling 最稳定，生态最完善。

**我为什么否决**：
1. **成本**：DeepSeek 的 API 价格约为 GPT-4o 的 1/50。对于每次分析需要调用 5+ 次 LLM（Supervisor + 3 Agent + Report + Reflection）的系统，成本差距会被放大到不可接受。
2. **中文能力**：我的目标用户是中国的连锁零售老板，分析报告全部是中文。DeepSeek 的中文语义理解和生成质量在实测中不输 GPT-4o，甚至在"销售额""客单价""退款率"等零售术语的理解上更准确。
3. **API 稳定性**：DeepSeek 的 API 完全兼容 OpenAI 格式，langchain-openai 可以直接对接，迁移成本为零。

**结果**：单次分析 LLM 调用成本约 ¥0.04，即使每天 100 次分析，月成本不超过 ¥120。

**补充：模型选型实测对比**

在 20 条离线评估集上对三个候选模型进行了对比测试：

| 维度 | DeepSeek-V4 | GPT-4o | Claude Sonnet 4 |
|------|:--:|:--:|:--:|
| SQL 生成准确率 | 85% | 88% | 87% |
| 中文报告流畅度 | ★★★★★ | ★★★☆☆ | ★★★★★ |
| 中文零售术语理解 | 好（"客单价"理解准确） | 中（偏向英文直译） | 好 |
| 单次分析成本 | **¥0.04** | ¥0.60 | ¥0.80 |
| 月成本（100次/天） | **¥120** | ¥1,800 | ¥2,400 |
| Function Calling 稳定性 | 偶尔超时 | 稳定 | 稳定 |

**结论**：GPT-4o 的 SQL 准确率仅高 3%，但成本高 15 倍。对于每天 100+ 次调用的场景，15 倍的成本差意味着月费从 ¥120 变成 ¥1,800——这在规模化时会被放大到不可接受。选择 DeepSeek 作为主力模型，用 Prompt 优化和 RAG 增强来弥补那 3% 的准确率差距，ROI 远高于换更贵的模型。

**面试话术**："选模型不只是选'最好'的，是选'最适合这个场景和成本结构'的。对于 B 端 SaaS，毛利空间直接决定定价空间——模型成本差 15 倍，意味着同样定价下毛利差 15 倍。"

## 决策 3：为什么 Reflection 只重试 1 次而不是更多？

**背景**：质检 Agent 发现报告质量不达标时，是否应该反复修改直到通过？

**AI 的建议**：重试上限设为 3 次，确保质量。

**我为什么否决**：
1. **用户等待时间**：每次重试意味着多一次 LLM 调用（约 8-15 秒）。3 次重试 = 多等 45 秒，用户会关掉页面。
2. **边际收益递减**：实测中，第 1 次重试修复了约 80% 的问题。第 2 次重试只能额外修复 10%。第 3 次几乎无改善。
3. **"不够好但可用" > "永远在改"**：用户宁愿看到一份 85 分的报告，也不愿等 3 分钟后看到一份 90 分的。

**最终方案**：最多 1 次重试。如果仍未通过，标注"质检未完全通过"但仍输出报告。

**结果**：质检通过率约 85%，首次重试后提升到 95%，用户等待时间控制在 45 秒以内。

## 决策 4：V3 为什么选择响应式 Web 而不是微信小程序？

**背景**：移动端适配时，需要选择实现方案。

**AI 的建议**：做微信小程序，因为中国老板都在微信里。

**我为什么否决**：
1. **维护成本**：小程序需要独立的前端代码库，与 Web 版并行维护，开发量接近翻倍。
2. **发布流程**：小程序需要微信审核，每次 Prompt 优化或 UI 微调都要等 1-3 个工作日过审，迭代速度严重受限。
3. **实际使用场景**：老板在手机上的使用场景是"看一眼今日快报"或"快速查一个数据"，而非"在手机上写长篇分析报告"。响应式 Web 完全能满足这两个轻量场景。
4. **PWA 潜力**：响应式 Web 可以后续包装为 PWA，获得接近原生 App 的体验（离线缓存、主屏图标），无需微信生态依赖。

**最终方案**：响应式 Web（@media 768px 断点），后续可选 PWA 升级。

## 决策 5：为什么内嵌 Ollama BGE-M3 而不是用 OpenAI Embedding？

**背景**：V2 引入向量记忆检索，需要 Embedding 模型。

**AI 的建议**：用 OpenAI text-embedding-3-small，1536 维，质量最高。

**我为什么否决**：
1. **成本**：每次分析需要生成 1 次 Embedding 用于存储，1 次用于相似搜索。虽然单价低，但乘以历史数据分析量的累积效应，长期成本不可忽视。
2. **延迟**：调用远程 API 有网络延迟（200-500ms），本地 Ollama 响应时间 < 50ms。
3. **中文效果**：BGE-M3 在中文语义理解基准（C-MTEB）上排名前列，实测中文检索效果优于 OpenAI 的 text-embedding-3-small。

**结果**：零 Embedding 成本，检索延迟 < 50ms，相似分析匹配准确率约 79%。

## 决策 6：为什么 V1 做完就推倒重来而不是渐进改进？

**背景**：V1 已经能跑通"问题→报告"的完整链路，理论上可以在此基础上加功能。

**AI 的建议**：在 V1 代码基础上逐步增加 Agent 并行、Web UI、RBAC 等功能。

**我为什么否决**：
1. **架构债务**：V1 的线性函数调用架构从根本上不支持并行。要加并行，需要重写整个调度层。与其在旧架构上打补丁，不如用 LangGraph 重建。
2. **代码可维护性**：V1 的代码是快速验证期的产物，模块边界模糊（SQL 执行和 LLM 调用耦合在一起），继续在它上面加功能会让维护成本指数增长。
3. **时间窗口**：V1 验证了核心链路可行（花了约 1 周），推倒重来用 LangGraph 重建 V2 花了约 2 周。如果选择渐进改进，预计也需要 2 周但代码质量差得多。

**最终方案**：V2 全新架构（LangGraph），V1 代码归档作为参考。

**结果**：V2 代码结构清晰，V3 在此基础上只需增量修改即可扩展。

## 决策 7：产品输出为什么是"查询型 + 分析型双模式"？

**背景**：设计报告输出格式时，面临"统一格式"还是"按场景分流"的选择。

**AI 的建议**：统一使用完整分析报告格式，信息全面。

**我为什么否决**：
1. **场景差异**：用户问"各门店销售额排名"只需要一张表。如果给他 6 段分析报告，他需要翻到第 3 段才找到表格——信息过载反而降低效率。
2. **用户认知负荷**：查询型问题（"多少"、"排名"）期待即时答案，分析型问题（"为什么"、"怎么样"）期待深度解读。用同一种输出格式会让用户感觉"有时候啰嗦、有时候不够"。

**最终方案**：Supervisor 判断问题类型，查询型 → 表格输出，分析型 → 6 段报告（摘要 → 数据分析 → 图表 → 问题诊断 → 根因 → 建议）。

**结果**：查询型问题平均响应时间缩短 40%，用户不需要在长篇报告中搜索答案。

## 决策 8：为什么用户反馈设计是 👍/👎 而不是 5 星评分？

**背景**：需要收集用户对分析报告质量的反馈。

**AI 的建议**：5 星评分 + 文字评论，数据粒度更细。

**我为什么否决**：
1. **决策疲劳**：5 星评分要求用户在 5 个选项中选择，增加认知负担。B 端工具场景下，用户只想快速表达"好"或"不好"，然后继续工作。
2. **数据噪声**：5 星评分中，大部分用户会选 3 或 4 星（中间值），区分度反而不如二分类（有帮助 vs 不准确）。
3. **行动导向**：对于产品迭代来说，"这个报告不准确"比"这个报告 3 星"更有行动指导意义。二分类 + 可选原因字段，既能快速投票，又能收集具体问题。

**结果**：简化反馈操作，预期回收率更高，且反馈数据直接指向可行动的改进点。

## 决策 9：为什么 Feature Flag 默认全部关闭？

**背景**：V3 新增了 8 个功能开关。

**AI 的建议**：新功能直接上线，不需要开关，减少代码复杂度。

**我为什么否决**：
1. **灰度安全**：多轮对话、图表推荐等新功能可能引入 LLM 调用次数增加、响应变慢等副作用。Feature Flag 允许在出问题时一键回退，不影响核心分析功能。
2. **A/B 测试基础设施**：Flag 不仅是安全开关，还是后续 A/B 测试的基础设施（可以按用户分流到不同版本）。
3. **运维友好**：如果某个功能（如移动端 UI）在生产环境出现兼容性问题，运维可以立即关闭，不需要等代码修复和部署。

**后续调整**：经过 137 条测试验证后，V3 所有 Feature Flag 已从默认关闭改为默认开启。

## 决策 10：为什么库存和供应链 Agent 要新建 4 张表而不是复用现有表？

**背景**：V3 扩展库存和供应链分析时，发现数据库中没有相关表。

**AI 的建议**：用现有的 orders、store 表做推断分析（比如从订单退款率反推库存问题），不需要新建表。

**我为什么否决**：
1. **分析的准确性**：没有真实的 inventory 表，库存分析只能靠猜测。用户问"哪个商品有缺货风险"，Agent 无法给出准确答案。
2. **产品完整性**：一个号称覆盖"全业务域"的分析平台，如果缺了零售业最核心的库存和供应链数据，产品定位就站不住脚。
3. **种子数据的价值**：新建 4 张表 + 178 条种子数据，不仅让 Agent 有数据可查，还为 Demo 演示提供了真实的业务场景。

**结果**：4 张新表（supplier/product/inventory/purchase_order），5 个领域 Agent 全部就位。

## 决策 11：V4 为什么选 React 18 + TypeScript 而不是继续用原生 HTML/JS？（🆕 V4）

**背景**：V3 前端是三个独立文件（index.html + app.js + style.css），约 2000 行代码，功能可工作但维护困难。

**AI 的建议**：用 Next.js，SSR + 文件路由，生态最好。

**我为什么否决**：Next.js 需要 Node.js 服务端渲染。V4 是 FastAPI 后端 + Docker 部署，引入 Node.js 运行时增加一个容器的复杂度。而且我们的前端是 SPA 分析面板，不需要 SSR。

**最终选择**：React 18 + TypeScript + Ant Design 5 + Vite。不需要额外 Node 服务器，Vite 构建产物是纯静态文件，FastAPI 直接 serve。Ant Design 5 提供企业级 UI 组件（表格/表单/Modal），节省 80% UI 开发量。

**结果**：前端从 3 个文件 2000 行 → 组件化 TypeScript 架构，新增 XSS 防御、重入保护、管理员权限按钮、Schema 配置面板（数据库映射配置面板）。

## 决策 13：V4 为什么要做一键 Docker 部署？（🆕 V4）

**背景**：V3 部署需要手动安装 Python 依赖、配置 PostgreSQL/Redis/Ollama、运行迁移、拉取模型。首次部署平均耗时 2 小时。

**决策**：投入 3 天做 `deploy.sh` + `docker-compose.prod.yml` + 预打包 BGE-M3 模型。虽然这不是"核心 AI 功能"，但它决定了客户能否在 5 分钟内看到价值。如果一个产品部署需要 2 小时，客户在安装阶段就放弃了。

**结果**：部署时间从 2 小时 → 5 分钟。新增离线镜像导出/导入支持内网环境。

## 决策 14：V4.4 — 质量审核通过后才展示报告，但展示方式要"假流式"（🆕 V4.4）

**背景**：V4.3 之前，report_agent 的 LLM 流式输出直接实时渲染到 DOM。但 Reflection Agent 发现质量问题后会触发重试 → 新报告替换旧报告 → 用户看到报告闪烁/内容突变。

**AI 的建议**：继续实时流式渲染，重试时渐进替换文本（类似 LLM 的逐 token 替换）。

**我为什么否决**：
1. **用户感知差**：重试时新报告从第 1 个 token 开始替换旧报告，中间会有一段时间看到"新报告开头 + 旧报告结尾"的混合内容，用户无法判断是继续输出还是出错了。
2. **技术复杂度**：渐进替换需要 tracking 两个版本的 token 边界，且 DOM 差异更新逻辑复杂，边际收益低。

**最终方案**：两段式设计——
1. **缓冲阶段**：所有 LLM token 在内存中累积，质量审核通过前不渲染到 DOM
2. **渐进展示阶段**：审核通过后，将完整报告按 40~50 块逐步渲染（每次 40ms，总计约 2 秒），模拟流式感

**追问按钮的兜底设计**：DeepSeek 经常不按要求生成 `[FOLLOWUP:]` 标记。为此做双重保障：（1）追问指令改为独立 SystemMessage（更醒目）；（2）LLM 不生成时，从报告中检测关键词（"门店""区域""趋势""退款"等）自动生成追问问题。100% 展示率。

**结果**：无报告闪烁，追问按钮 100% 展示。
