## 1. 项目背景与评估目标

### 1.1 项目概况

Enterprise Insight Agent V4（EIA V4）是面向连锁零售的 Multi-Agent AI 经营分析平台。10 个 Agent 协作，用户用自然语言提问，60 秒内获得含数据概览、根因诊断、可执行建议的诊断报告。Demo 数据覆盖 100 门店 / 50,925 订单 / 5,000 会员 / 30 供应商，155 条测试通过。

### 1.2 评估目标

从**专业 AI 产品经理**和**资深开发师**双重视角，对项目进行全面审视，产出一份综合评估报告。报告核心服务于**面试备战**，具体包括：

- 提炼项目亮点和面试话术
- 预判面试官可能的追问角度
- 诚实标注潜在被质疑的风险点
- 提供防守策略和改进路线

### 1.3 目标受众

报告受众为作者本人（高志远），用于 AI 产品经理岗位面试准备。面试官关注产品决策逻辑、用户场景理解、AI 能力边界、商业化思考，技术追问保持在"懂技术的 PM"层面。

### 1.4 核心担忧维度

报告需重点覆盖以下四个面试中可能被质疑的方面：

1. **代码原创性质疑** — 面试官质疑项目是否 AI 生成、是否能证明对每个技术决策有深刻理解
2. **技术选型追问** — 面试官追问"为什么不用 RAG/GPT-4o/单 Agent"等技术选型的产品逻辑
3. **项目真实性质疑** — 面试官质疑 Demo 项目无真实用户、数据是造的
4. **商业化能力追问** — 面试官追问商业价值、市场空间、竞品差异、盈利模式

  - 技术架构 — Multi-Agent 编排合理性、技术选型权衡

### 2.2 AI 产品经理视角评估

**目标**：验证产品决策不是"事后编的故事"，而是有真实思考链路的。面试官最怕听到"因为流行所以用了 LangGraph"，这一节确认每条决策都能讲到"为什么"。

**内容**：

#### 2.2.1 决策逻辑链审视

逐条审查 13 条关键决策记录（来源：`docs/关键产品决策记录.md`），评估每条：
- 决策逻辑是否自洽（"为什么否决 AI 建议"的理由是否经得起追问）
- 是否有数据支撑（如"Reflection 重试 1 次→修复率 60%"的数据来源）
- 面试中的讲述力（能否在 2 分钟内讲清楚背景-挑战-思考-方案-结果）
- **标注高风险决策**：如"DeepSeek vs GPT-4o"如果被追问模型评测数据，是否能拿出具体对比

13 条决策清单：
1. Agent 编排框架（LangGraph StateGraph vs LangChain AgentExecutor）
2. LLM 选型（DeepSeek-V4 vs GPT-4o）
3. Reflection 重试次数（1 次 vs 3 次）
4. 移动端方案（响应式 Web vs 微信小程序）
5. Embedding 模型（本地 BGE-M3 vs OpenAI）
6. V1→V2 推倒重建 vs 渐进改进
7. 输出格式（双模式 vs 统一报告）
8. 反馈机制（👍/👎 vs 5 星评分）
9. Feature Flag 默认值策略
10. 库存/供应链表（新建 4 表 vs 复用现有）
11. V4 前端技术（原生 JS vs React/Next.js）
12. V4 LLM 续用 DeepSeek
13. 一键 Docker 部署投入

#### 2.2.2 AI 能力边界定义

评估项目对"AI 能做什么/不能做什么"的界定清晰度：
- Reflection 质检机制是否真正有效（4 维度是否合理、1 次重试是否有依据）
- 双模式输出（查询型→表格 / 分析型→报告）的产品判断是否成立
- "数据诚实"原则（禁止编造、必须 run_sql）的落地程度
- AI Kill Switch（灰度开关）设计是否真正可回退

#### 2.2.3 用户场景覆盖度

从连锁零售实际经营场景出发，评估：
- 5 个领域 Agent（销售/CRM/财务/库存/供应链）是否覆盖零售核心经营链路
- 102 条评估集的问题分布是否真实反映门店管理者日常提问
- 经营看板作为首页的"冷启动"解决方案是否有效
- 多轮对话/追问/FOLLOWUP 机制是否解决真实需求

#### 2.2.4 产品方法论成熟度

评估 7 条 AI 产品设计原则（来源：`docs/AI产品设计原则.md`）的实践深度：
- "够好就行" — 是否真的在成本/质量/速度间做了理性权衡
- "灰度开关" — 9 个 Feature Flag 的默认值策略是否合理
- "输出自适应" — 双模式是否真正降低了用户认知负担
- "数据诚实" — AI 输出与真实数据的一致性保障
- "Reflection 质检" — 质检维度的合理性和有效性
- "流式优先" — 95%+ 新问题的缓存策略是否合理
- "Schema 三层适配" — 零驻场部署的产品价值
- 与业界 AI PM 方法论（如 Google PAIR、Microsoft Responsible AI）的对比定位

### 2.3 资深开发师视角评估

**目标**：提前知道代码里有哪些"地雷"，面试官翻 GitHub 源码会看到什么。每个问题都附带"面试中如何解释"的建议。

**内容**：

#### 2.3.1 架构合理性

- LangGraph StateGraph 编排评估：11 节点拓扑是否合理，Send 并行扇出的扇入策略是否正确
- Aggregator 纯 Python 聚合设计（不耗 Token）的评价：头尾保留截断策略（前 70%+后 30%，上限 15000 字符）是否可能丢失关键信息
- 优雅降级链路评估：Agent 全失败→错误报告、Redis 不可用→放行、RAG 失败→跳过，是否过度防御或不够
- 模块级实例化问题：`llm = create_llm()` 和 `graph = build_graph().compile()` 在导入时执行的影响（LLM 配置变更需重启、测试隔离性差）

#### 2.3.2 代码质量审计

附具体文件和行号级发现：
- **`app/llm.py` 文档与实现矛盾**：顶部 docstring 称"CostTracker 使用 ContextVar 做 per-task 累计，无需加锁"，实际代码用 `_token_lock = threading.Lock()` + 全局变量 `_token_input/_token_output`。多请求并发下 `reset_task_tokens()` 可能清掉其他正在进行的分析累计（潜在竞态）。类 docstring 又说"用线程锁保护"。这是面试中最大的原创性质疑风险点。
- **56 处裸 `except Exception`**（27 个文件），部分 catch 后直接 `pass` 完全静默（如 `llm.py` CostTracker、`sales_agent.py` RAG 检索、缓存读写），虽是降级但可能掩盖真实问题
- **日志系统混用**：`supervisor/analysis/graph/audit/tenant` 用 structlog `get_logger()`，而 `report/reflection/sales/memory/chart_advisor` 用标准库 `logging.getLogger()`。structlog 的 `bind_context()` 注入的 trace_id 等字段对标准库 logger 不生效，导致部分 Agent 日志缺失链路上下文
- **魔法数字散落**：`MAX_SUMMARY_CHARS=15000`、`MAX_REPORT_CHARS=10000`、`_MIN_PHASE_DISPLAY_SEC=0.6`、`CHART_MAX_CHARS=8000` 等硬编码常量分布于各文件，未集中到 `config.py`
- **`encode_chart_markers` 手动状态机**：手动字符扫描解析 `[CHART:...]`，边界 case 多，维护成本高
- **函数内 import**：`analysis.py` 多处在函数体内 `import hashlib`/`from app.tools.question_enhancer import ...`，降低可读性
- **`on_event("startup")` 已弃用**：FastAPI 较新版本推荐 lifespan context manager

#### 2.3.3 安全设计评估

- **RLS 行级安全注入**（`app/tools/sql_runner.py`）：括号深度追踪算法评价、列名自动检测（`_detect_store_column`）、空权限 `WHERE 1=0` 防泄露设计、单引号转义防注入
- **SQL 安全检查器**（`app/tools/sql_checker.py`）：FORBIDDEN/RISKY 双层模式、字符串字面量剥离防误报
- **JWT + RBAC + 多租户 + 审计日志**：四层安全体系完整性评价
- **安全盲区标注**：`/analyze-stream` 缺少 rate_limit 依赖（与 `/analyze` 不一致）；Redis 不可用时令牌黑名单降级放行的风险评估

#### 2.3.4 测试覆盖盲区

- 155 条测试的分层策略评价（无依赖 SQLite / `@db` 真实 PG / `@e2e` 真实 LLM / 离线评估）
- **覆盖盲区**：无独立 Agent 单元测试（`test_workflow.py`/`test_agents.py` 不存在）、Aggregator（纯 Python 聚合）无专门单测、单个 Agent 的 LLM 行为主要靠 E2E 覆盖
- 102 条评估集的质量评估：50 lookup + 38 analysis + 14 edge 的分布是否合理
- 测试环境优雅降级（`_is_postgres_available()` 动态探测、PG 不可用时自动 skip）的设计评价
- conftest.py 的 mock 策略评价（mock `graph.ainvoke`/`graph.astream` 避免真实 LLM 调用）

#### 2.3.5 数据层与文档一致性

- **数字不一致**：AGENTS.md 称"17 ORM 模型"实际 `models.py` 中 16 个类；称"8 版 Alembic 迁移"实际 10 个版本（001-010）
- `supplier/product/inventory/purchase_order` 4 张表只在 alembic 003 用原始 SQL `CREATE TABLE` 建表，无 ORM 类 — Agent 通过 `sql_runner` 原生 SQL 访问。需判断是有意设计（适配异构客户库）还是遗漏
- `.env.example` 注释称"validated by 137 tests"，AGENTS.md 称 155 条 — 测试数随版本增长，文档注释滞后
- 前端 `index.html` footer 标注"REACT 18 · TYPESCRIPT · ANT DESIGN 5"但实际是原生 HTML/CSS/JS — 面试官翻源码会质疑

### 2.4 面试攻防手册

**目标**：让读者带着"面试官会怎么问"的预判走进面试室，每个问题都有准备好的回答框架和支撑数据。

**统一结构**：每个维度的子模块按「高频追问问题清单 → 当前回答薄弱点 → 防守策略与话术 → 数据/证据支撑」四段式组织。

#### 2.4.1 代码原创性质疑

- **高频追问**：
  - "这个项目是你自己写的还是 AI 生成的？"
  - "你能解释 graph.py 里 Send 并行扇出的实现原理吗？"
  - "为什么 llm.py 的 docstring 说用 ContextVar 但实际用了 threading.Lock？"
  - "sql_runner 的 RLS 注入是怎么实现的？"
- **薄弱点**：llm.py 文档与实现的矛盾是最大风险 — 面试官认为"如果是自己写的不会出现这种不一致"
- **防守策略**：准备 3-5 个能深度讲解的技术细节（RLS 括号深度追踪算法、FOLLOWUP 括号计数法、头尾保留截断策略），展示"只有亲手写过才会知道"的实现细节；坦诚承认 llm.py 的文档滞后是迭代过程中的遗漏，展示工程诚实度
- **证据支撑**：CHANGELOG.md 的 60 项修复记录（含分级：严重 6/高 12/中 24/低 12）、Prompt 迭代日志的演进痕迹、V1→V4 四版对比

#### 2.4.2 技术选型追问

- **高频追问**：
  - "为什么不用 RAG？Multi-Agent 的上下文竞争问题有量化数据吗？"
  - "为什么选 DeepSeek 而不是 GPT-4o？有评测对比吗？"
  - "LangGraph vs LangChain AgentExecutor，你的选择依据是什么？"
  - "BGE-M3 召回率 ~79%，这个数字怎么测的？"
  - "Reflection 重试 1 次的修复率 60%，怎么得出的？"
- **薄弱点**：部分决策的"数据支撑"可能是估算而非实测（如"上下文竞争 3000 token Schema"），面试官可能追问测量方法
- **防守策略**：将技术选型统一框架化为"成本-质量-延迟三角"，每个选型都能归入这个框架；准备"如果重来会怎么做"的反思（展示成长性）；对于估算数据坦诚说明测量方法
- **证据支撑**：13 条决策记录、CostTracker 成本追踪数据（¥0.04/次）、V1→V4 四版演进对比、DeepSeek vs GPT-4o 成本对比（¥1/Mtok vs ¥30/Mtok）

#### 2.4.3 项目真实性质疑

- **高频追问**：
  - "100 门店 / 50,925 订单的数据是造的，怎么能证明系统在真实场景下可用？"
  - "有没有真实用户用过？用户反馈是什么？"
  - "从 Demo 到真实落地，还差什么？"
  - "schema 三层适配器真的在真实客户上验证过吗？"
- **薄弱点**：项目目前是 Demo 驱动，没有真实用户数据和线上运行记录
- **防守策略**：将项目定位为"产品原型 + 技术验证"，而非"已上线产品"；准备"如果拿到真实客户，第一步做什么"的落地路径（Schema 三层适配器就是为此设计的）；强调 102 条评估集是对真实场景的模拟；用 n8n 定时调度 + 飞书/钉钉/企微通知展示"已具备生产集成能力"
- **证据支撑**：`customer_schema.yaml` 机制、`eval_set.json` 评估集（102 条）、n8n 工作流模板、Docker 5 容器生产部署配置

#### 2.4.4 商业化能力追问

- **高频追问**：
  - "这个产品的目标市场有多大？TAM/SAM/SOM 是多少？"
  - "跟现有 BI 工具（如帆软、Tableau）比，差异化在哪？"
  - "盈利模式是什么？客户愿意为这个付多少钱？"
  - "为什么连锁零售会选你而不是直接用 ChatGPT？"
  - "获客成本是多少？怎么触达目标客户？"
- **薄弱点**：商业思考文档（`docs/商业思考.md`、`docs/竞品分析.md`）可能偏理论，缺乏验证
- **防守策略**：用"AI 降低了分析门槛"作为核心差异化叙事；准备"3 种客户画像 + 对应定价"的具体方案；用 DeepSeek 成本优势（¥0.04/次 vs GPT-4o ¥1.2/次）讲商业可行性；强调 Schema 三层适配器降低了交付成本
- **证据支撑**：`docs/商业思考.md`、`docs/竞品分析.md`、CostTracker 成本追踪数据、多租户 + RBAC 架构（支持 SaaS 模式）

HTML 单页报告，部署到用户工作目录。

### 3.2 可视化元素

## 4. 评估方法论

### 4.1 数据来源

报告基于以下信息源的深度分析：

| 来源 | 内容 | 探索深度 |
|------|------|---------|
| 代码架构探索 | `app/` 全目录结构、核心文件（graph.py/state.py/supervisor_agent.py/report_agent.py/reflection_agent.py/llm.py/sql_runner.py/main.py/analysis.py） | 逐文件阅读 |

### 4.2 评估标准

- **产品思维**：决策是否有清晰的"为什么"、是否考虑了用户真实场景、AI 能力边界是否被合理界定
- **技术架构**：架构是否解决真实问题、是否有过度设计或设计不足、技术选型权衡是否合理
- **工程实践**：代码质量、安全设计、测试覆盖是否达到企业级标准
- **文档沉淀**：决策记录是否完整、迭代日志是否有价值、面试材料是否充分
- **商业思考**：市场分析是否有依据、竞争差异化是否成立、盈利模式是否可行
- **面试准备度**：当前材料和代码能否支撑 30 分钟深度对话、是否有明显的被攻击点

### 4.3 评估立场

- **诚实优先**：不回避问题，每个发现都附具体证据
- **面试导向**：所有评估结论最终指向"面试中如何应对"
- **建设性**：不仅指出问题，更提供可执行的改进建议
- **双视角**：PM 视角关注产品逻辑，开发师视角关注工程实现

## 6. 成功标准
