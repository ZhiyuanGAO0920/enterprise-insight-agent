🛡️ 1. 安全

P0 innerHTML 拼接 LLM 输出 — XSS 注入风险 app.js:759 · views.js:628
marked.parse() 将 LLM 输出转为 HTML 后，通过 sd2.innerHTML = fh 直接注入 DOM。 虽然 sanitizeHtml() 调用了 DOMPurify，但存在两个薄弱点：
① sanitizeHtml() 兜底逻辑在 DOMPurify 加载失败时直接返回原文 HTML（utils.js:78），等于完全放弃过滤；
② expandChartTags() 在 sanitize 之前就执行，将 [CHART:...] 转为 <div> 元素，绕过了 DOMPurify 的白名单过滤。
如果 LLM 被 prompt 注入输出 <img onerror=alert(1)> 或恶意 SVG，在 DOMPurify 不可用时将直接执行。
// utils.js:74-79 — 兜底返回原文，等于零过滤 function sanitizeHtml(html){ try{ if(typeof DOMPurify!=='undefined'&&DOMPurify.sanitize) return DOMPurify.sanitize(html); }catch(e){} return html; // ⚠️ DOMPurify 不可用时无任何过滤 }
✅ 修复建议：
1. sanitizeHtml() 兜底改为 esc(html)（纯文本转义），而非返回原文；
2. expandChartTags() 产出的 HTML 应在 marked.parse() 之前插入，然后整体交给 DOMPurify.sanitize() 过滤；
3. 为 DOMPurify 配置允许的标签白名单：DOMPurify.sanitize(html, {ALLOWED_TAGS: [...], ALLOWED_ATTR: [...]})，限制 div.chart-container 和 data-chart 属性。
影响：全用户修复难度：中预计工时：2h
P0 onclick 内联事件 + jsEscape 拼接 — CSP 违规 + 转义遗漏风险 index.html:52+64-68+72+102-104+149-154+159+161+200+208+212+223+237+242 · views.js:621+625
全文有 20+ 个 onclick 内联事件处理器，依赖 jsEscape() 手动转义拼接字符串。 风险：
① 若 jsEscape() 有遗漏（如未覆盖反引号模板字符串 ${}），攻击者可注入 JS；
② 违反 CSP（Content Security Policy）的 unsafe-inline 规则，浏览器无法禁止内联脚本执行；
③ 部分内联 onclick 已经被事件委托替代（app.js:159-182），但 HTML 中仍残留大量内联写法，两套机制并存增加维护混乱。
// index.html:52 — 内联 onclick <button class="intro-cta" onclick="transitionToLogin()">进入系统</button> // views.js:621 — 拼接 onclick 中的字符串参数 onclick="showFeedback('helpful')" // app.js:625 — 拼接 onclick，依赖 jsEscape onclick="downloadMD()"
✅ 修复建议：
1. 将所有内联 onclick 改为 data-action 属性 + 事件委托（已有 document.addEventListener('click', ...) 框架）；
2. HTML 模板中的按钮统一用 data-action="xxx"，JS 侧统一用 e.target.closest('[data-action]') 捕获；
3. 这样既符合 CSP，也消除了 jsEscape 拼接遗漏的风险。
影响：CSP 合规修复难度：中预计工时：3h

P1 localStorage 存储 JWT token — 无法防御 XSS 窃取 app.js:82+135 · index.html:16
JWT token 存在 localStorage 中，一旦 XSS 成功执行，攻击者可直接 localStorage.getItem('eia_token') 窃取 token。 index.html:16 的内联脚本也在 localStorage 中操作 token。对于 B 端企业级产品，应优先使用 httpOnly + Secure + SameSite=Strict 的 Cookie 存储 token，使 JS 完全无法读取。
✅ 修复建议：
1. 后端登录 API 设置 Set-Cookie: eia_token=xxx; httpOnly; Secure; SameSite=Strict; Path=/api；
2. 前端移除所有 localStorage.getItem('eia_token')，改由浏览器自动携带 Cookie；
3. 保留 eia_user 在 localStorage（仅存用户名，不含敏感信息）。
影响：认证安全修复难度：高预计工时：4h（需前后端联动）

⚡ 3. 性能

P0 ECharts 内存泄漏 — 不 dispose 旧实例 + resize 监听器累积 app.js:223-267 · utils.js:349-355
Dashboard 的 ECharts 实例通过 _dashCharts.t = echarts.init(...) 创建，但从未调用 echarts.dispose()。 问题：
① 每次切换到 Dashboard tab 都调用 loadDashboard()，虽然 if(!_dashCharts.t) 防止了重复 init，但若 DOM 元素被替换（如 innerHTML 重写），旧实例会持有已移除 DOM 的引用，形成内存泄漏；
② window.addEventListener('resize', ...)（utils.js:349）在全局注册 resize 监听器，遍历所有 .chart-container 元素调用 resize()，但不检查元素是否仍在 DOM 中；
③ Monitor 面板的 window._monitorChart 在每次重新加载时会 dispose()（app.js:507），这是正确的做法，但 Dashboard 和报告内嵌图表没有同样的保护。
// app.js:225 — 只 init，从不 dispose if(!_dashCharts.t)_dashCharts.t=echarts.init(document.getElementById('dashTrendChart')); // ⚠️ 若 dashTrendChart 的父容器被 innerHTML 替换， // 旧 _dashCharts.t 仍持有已移除 DOM 节点的引用 → 内存泄漏 // app.js:507 — Monitor 正确地先 dispose if(window._monitorChart)window._monitorChart.dispose(); window._monitorChart=echarts.init(el);
✅ 修复建议：
1. 在 loadDashboard() 开头先 dispose 所有已有实例：Object.values(_dashCharts).forEach(c => c?.dispose()); _dashCharts = {};；
2. initChartsInBubble() 中的报告图表，在重新渲染前也先 dispose：container._chart?.dispose(); container._chart = null;；
3. resize 监听器改为 ResizeObserver（仅观察存在的容器），替代全局 window resize。
影响：内存/长时间使用修复难度：中预计工时：2h
P1 ECharts 1MB 库在底部同步加载 — 阻塞首屏交互 index.html:253
echarts.min.js（~1MB）在 <body> 底部同步加载。虽然 onEChartsReady() 队列机制确保了图表延迟渲染，但 1MB 的同步脚本下载仍会阻塞 DOMContentLoaded 之后的 JS 执行约 1-3 秒（取决于网络）。注释说"echarts 已在 head async 预加载"，但 head 中并无 echarts 的 preload 标签。
// index.html:253 — 底部同步加载 1MB ECharts <script src="/static/echarts.min.js"></script> // ⚠️ 注释说"已在 head async 预加载"，但 head 中没有对应 preload

1. 在 <head> 加 <link rel="preload" href="/static/echarts.min.js" as="script"> 提前下载；
2. body 底部改为 <script src="/static/echarts.min.js" defer> 或 async，避免阻塞后续脚本；
3. 修正注释与实际代码不一致的问题。
影响：首屏加载修复难度：低预计工时：0.5h

♿ 5. 可访问性 (WCAG AA)

P1 系统性 ARIA 缺失 — 无法屏幕阅读器导航 index.html 全文 · app.js 全文
整个前端无任何 aria-label、aria-role、aria-live 属性。
具体缺失：
① 侧边栏导航无 role="navigation" + aria-label="主导航"；
② Tab 切换按钮无 role="tab" + aria-selected；
③ 聊天区域无 role="log" + aria-live="polite"（新消息到达时屏幕阅读器不会通知）；

⑤ 进度步骤无 aria-valuetext 状态描述；
⑥ 图表容器无 aria-label 替代文本（盲人用户完全无法感知图表内容）。
✅ 修复建议（渐进式）：
1. 优先：侧栏 + Tab + 聊天 + 模态框 加 ARIA role/label（2h）；
2. 次优先：图表容器加 aria-label="销售趋势图：近30天日均XX万" 概要文本（1h）；
3. 长期：SSE 进度步骤加 aria-live="polite"（0.5h）。
影响：WCAG AA合规修复难度：中预计工时：3.5h

💡 7. UX / 交互

P1 登录后返回用户仍显示欢迎页 Loading — 路径断裂 index.html:26 · app.js:95-131
index.html:26 的内联脚本在 token 有效时将 introOverlay 内容替换为 loading spinner，但如果 restoreSession() 的 API 请求失败（如 token 过期），introOverlay 已被改写为 spinner，无法回退到原始欢迎页内容。用户会看到永久性的"正在加载..."页面。
✅ 修复建议：
1. 不直接修改 introOverlay.innerHTML，而是动态创建一个 loading overlay 叠加在 intro 上；
2. 若 restoreSession 失败，移除 loading overlay，恢复原始 intro 内容并显示登录框。
影响：登录体验修复难度：中预计工时：1h
P2 Toast 自动消失无手动关闭 — 错误信息 5 秒后消失 utils.js:82-87
Toast 通过 CSS animation:fadeOut 在 2.5-5 秒后消失。对于错误 Toast（5秒），用户可能在阅读中途就被淡出，无法手动保持或关闭。对于重要错误消息（如"网络错误"），应提供关闭按钮或延长显示时间。
✅ 建议：错误 Toast 增加 × 关闭按钮，或改为可手动 dismiss 的 Notification Bar。
影响：信息可读性修复难度：低预计工时：0.5h
P2 Dashboard 6 列 KPI 在窄屏溢出 — 响应式断点不够 style.css:293
.dash-kpi-row 默认 grid-template-columns: repeat(6, 1fr)，仅在 max-width:1024px 时改为 3 列、max-width:640px 时改为 2 列。在 641-1023px 区间（平板竖屏），3 列 × 6 KPI = 2 行，每列可能过窄导致文字换行混乱。缺少 768px 断点（4列）。

影响：平板体验修复难度：低预计工时：15min
